00 / 核心判断

五句话看懂现状

  1. I
    工具形态已在 2026 上半年补齐到"与 Android 同代"。GUI IDE（DevEco Studio 26.0）、CLI（DevEco CLI 1.3）、终端 Agent（DevEco Code，基于 OpenCode）三种形态在 HDC 2026 前后一齐到位，时间上与 Android CLI 1.0、Xcode 26.3 接入 Agent 处于同一窗口。形态不再是短板，三条产品线之间的协同才是。
  2. II
    舆情最尖锐的部分不在 IDE 里，而在 IDE 之外。中文社区 2025Q4 起情绪最激烈的是上架审核与激励 ROI；英文社区最集中的抱怨是账号注册、实名与中文文档——"跑通 hello world 的门槛"。IDE 本身的问题（卡顿、内存、预览器、CodeGenie 排队）被视为"可忍受的工程问题"。
  3. III
    文档可查性是持续三年的慢性痛点。从 2024-11 到 2026-05，"指南 / API / Q&A / 最佳实践要交叉验证"、"示例更新不及时"、"since 版本标注自相矛盾"、"历史版本没有下载链接"的声音一直在。官网重前端渲染，对搜索引擎与 AI 检索都不友好，本次调研多次只抓到导航壳。
  4. IV
    生态位的结构性空白在"插件层"与"零安装入口"。存量 App 迁移的主入口是 RN / Flutter / uni-app / Kuikly 等跨平台框架，这些开发者的首选编辑器是 VS Code 与 Android Studio，而鸿蒙在 VS Code / JetBrains 市场里没有官方插件，也没有 Web IDE。DevEco Studio 对他们只是"宿主"。
  5. V
    AI 助手正处在"两条线并行"的过渡期。IDE 内的 CodeGenie（盘古 + DeepSeek，上下文小、云端排队）与终端里的 DevEco Code（第三方模型、开发者自配 Provider）尚未在 IDE 里形成统一入口；竞品（JetBrains、Xcode、Android Studio）已走向"IDE 做宿主、任意 Agent 做大脑"的范式。
  6. VI
    放大到 1100 万注册开发者，图景会变：真正写过鸿蒙代码的约 5–15%，而最大的人群是学习者，最有分量的人群是企业团队——两者都几乎不在前五节的样本里。学习者最在意"能不能找到工作"，企业团队最在意 CI / 自动化与大工程性能，南向开发者最在意"编译能不能过、有没有人回帖"，PC 与元服务开发者最在意个人准入。IDE 在鸿蒙开发者内部的满意度并不低（一份 n=526 的调研中 75.7% 满意），舆情的负面集中在门槛与商业化。详见 §06。

官方给出的性能口径

HarmonyOS 7 / DevEco Studio 7.0 Beta1 的官方更新速览称"代码索引效率提升 70%，编译构建效率提升 40%，整体内存占用降低 30%"；另一份新闻稿口径为"300 万行工程索引 10 分钟→2 分钟、内存 20G→7G、构建 4.5→3 分钟"。两套数字并存，且都以百万行级大工程为基准——而社区抱怨的卡顿多来自 8–16GB 内存的普通配置（见 §03）。这个"官方基准 vs 开发者机器"的落差，本身就是一个体验问题。

鸿蒙开发生态站在哪里

规模：中国第二 OS，全球长尾

官网与文档体系：一个域名，四套体系

developer.huawei.com/consumer/cn 是唯一实际主站，文档、Samples、Codelabs、下载、论坛、学堂、认证全部挂在该域下；developer.harmonyos.com 已重定向到主站；device.harmonyos.com 承担设备侧；openharmony.cn 是 OpenAtom 官网，源码已从 Gitee 迁至 GitCode / AtomGit；跨平台框架文档散落在 GitCode CPF-* 组织与 CSDN 托管的社区。AppGallery Connect 是独立控制台，账号统一但入口割裂。

与 Android Developers / Apple Developer 的信息架构差异：三家主站表层结构相似（文档—示例—工具下载—发布—博客），差别在动线连续性。Android 把"文档→Codelab→Studio→Play Console"在一个域内串成线，并以 Android CLI 把知识库暴露给 Agent；Apple 在 developer.apple.com 内统一 Xcode 下载、文档、WWDC 视频与 App Store Connect。鸿蒙的每一跳都换应用形态（Web→IDE→Web 后台），并且存在四个割裂点：

① 商业发行版（HarmonyOS API 文档）与开源版（OpenHarmony docs）双轨，API 版本映射需开发者自行对照；② 跨平台方案文档不在主站；③ DevEco Code / CLI 官方文档薄，社区博文成为主要说明书；④ 主站为重前端渲染，本次多次抓取只得到导航壳——这同时影响 SEO 与 AI 检索，而 DevEco Code 内置的 arkts_knowledge_search 目前是私有工具，尚未作为公共 API / MCP 开放。

05 / 体验优化方向

从舆情到动作：三个同心圆

按"谁能拍板"分三层：工具内是 DevEco 团队自己能做的；动线级要与官网、文档、AGC 团队协作；生态级是政策与审核。优先级 P0 / P1 / P2 依据舆情强度 × 影响面 × 竞品已验证程度给出，是建议而非结论。每条附可度量的指标，便于立项时定义"做到了"。

Ring 1 · 工具内 · DevEco 团队可直接推进

P0三形态一个入口：让 Studio 成为 Agent 的宿主

证据
CodeGenie（IDE 内）与 DevEco Code（终端）并行，开发者在社区互相推荐"从 CodeGenie 迁移到 DevEco Code"；DevEco CLI 已能向 Claude Code / Cursor 安装 Skills 与 MCP，却没有反向让它们进 Studio 的通道。
方向
在 Studio 内提供 Agent 选择器（CodeGenie / DevEco Code / Claude Code / Codex / 自定义 ACP），共享同一会话面板；内嵌终端一键启动 deveco；Agent 的 verify_ui 结果回流到预览器与 ArkUI Inspector，而不是停留在终端文本。
参照
JetBrains Agent-agnostic 聊天窗、Xcode 26.3 原生接入 Claude Agent / Codex、Android Studio Agent Mode 读 logcat 与截图。
指标
Studio 内 Agent 会话占全部 AI 会话的比例；从"Agent 改完代码"到"预览器看到结果"的中位时间。

P0把性能承诺翻译成开发者机器上的体验

证据
官方以"300 万行工程"为基准宣称索引 ↑70%、内存 ↓30%；社区卡顿来自 8–16GB 普通配置——打字、粘贴卡死，UI 线程阻塞，6.1.0 崩溃 100% 复现跨多版本遗留。
方向
低配自适应模式（检测内存 ≤ 16GB 时默认开启按需加载索引、降低预览器并发、延后非关键插件）；IDE 内可见的性能自检面板（索引耗时、内存水位、被阻塞的 UI 事件）取代文档里的"内存占用高优化方法"；把社区 100% 复现的崩溃用例纳入发布门禁。
参照
Android Studio 的 "Studio Bot 诊断"与内存设置向导；VS Code 的 Process Explorer / Startup Performance。
指标
16GB 机型上打字延迟 P95；UI 冻结（> 500ms）次数 / 小时；Release 版本崩溃回归数。

P1预览器与模拟器：先可靠，再快

证据
Previewer error 高频、刷新即报错；睡眠唤醒后窗口只显示一半；6.0.2 模拟器"未登录华为账号"无法启动；海外称缺本地模拟器是 blocker，Intel Mac 不支持；也有"预览近乎实时"的好评——说明能力在，稳定性是问题。
方向
预览器崩溃自恢复与状态保留；模拟器离线可用（登录只在需要云能力时触发）；平台支持矩阵（芯片 × 系统 × 模拟器 / 预览器）在下载页与 IDE 内一致呈现，而不是让开发者靠踩坑发现。
参照
Xcode Previews 的错误定位与"Resume"；Android Emulator 的快照恢复。
指标
预览器每千次刷新错误率；模拟器冷启动成功率；"无法启动"类论坛帖数量的月度趋势。

P1AI 助手的可用性透明：排队、上下文、额度都让人看见

证据
"昨天还能用，今天就一直加载"（云端排队）、"上下文不到 1K"、接大模型崩溃、DevEco Code 一小时无响应、免费模型 50 次 / 分钟限制只在社区帖里被发现。
方向
会话面板显示当前模型、上下文规模、剩余额度与排队状态；BYOM（自带 API Key / 本地模型）作为一等选项；请求失败时给出降级路径（切换模型、本地补全）而非无限加载；DevEco Code 与 CodeGenie 共用模型配置。
参照
Android Studio BYOM；Cursor 的 usage 面板；JetBrains Central 额度治理。
指标
AI 请求成功率与 P95 首 token 时延；"无响应 / 排队"相关帖占 AI 主题帖的比例。

P1Profiler：从"有工具"到"按症状进入 + AI 修复"

证据
"工具是有了，但会用和用好之间有段距离"；模板已有 14 种，7.0 又加一键内存泳道与跨语言泄漏定位，能力充足；正面评价来自已经会用的人（"联想到 JProfiler"）。
方向
以症状为入口（卡顿→Frame、内存涨→Allocation / Snapshot、启动慢→Launch）而非以模板为入口；Code Scanner 的资源泄漏结果与 Profiler 泳道互相跳转；发现→定位→AI 给出修复建议→一键应用的闭环。
参照
Android Studio Profiler 的 LeakCanary "Fix with Agent"；Xcode Instruments 的 SwiftUI 性能仪表。
指标
Profiler 月活 / Studio 月活；从打开 Profiler 到定位到代码行的中位时间。

P2ArkTS 迁移摩擦：把限制变成 quick-fix

证据
"一个 TS 100 多个特性不支持"、升级 API 后突然报一堆、"千把行代码能整理出十多个问题点"；学术研究指出 SOTA LLM 在 ArkUI 上"连可编译文件都生成不出"（低资源语言）。
方向
对每一条 ArkTS 静态限制提供可执行的 quick-fix 与迁移解释，而不只是报错文本；API 升级前的兼容性预检报告；把 ArkTS 语料与规则以 Skill / MCP 形式开放给第三方 Agent（DevEco CLI 已开始做）。
指标
TS→ArkTS 迁移工程的首次编译通过率；报错→修复的平均交互轮次。

P2补齐 Linux

证据
IDE、DevEco CLI、DevEco Code 三者都不支持 Linux；仅新增 Linux 版模拟器（面向云端测试）。企业 CI、服务器端开发者与海外开源维护者（Servo 构建文档明确指出"只有 Windows 和 macOS"）被排除在外。
方向
先从 CLI 与 Command Line Tools 的 Linux 版起步（CI 场景收益最大），再评估 IDE。
指标
Linux 上 hvigorw 构建成功率；CI 场景中使用官方 CLI 而非自研脚本的比例。
Ring 2 · 动线级 · 需与官网 / 文档 / AGC 协作

P0文档可检索：给人，也给 Agent

证据
三年持续的"交叉验证"抱怨；since 标注矛盾；示例过期；历史版本无下载；主站 SPA 渲染让搜索引擎与 AI 抓取只得到导航壳；DevEco Code 的 arkts_knowledge_search 是私有工具。
方向
文档服务端渲染或提供静态镜像；把指南 / API / Q&A / 最佳实践合并到同一条目视图（一个 API 一页，含示例与 since 版本）；示例代码随 SDK 版本 CI 编译验证；把知识库作为公共 MCP / API 开放，让任何 Agent 都能查到与 DevEco Code 相同的答案；历史版本下载页补全。
参照
Android CLI 把开发者知识库暴露给 Agent；MDN 的"一个 API 一页 + 兼容性表"。
指标
站内搜索零结果率；文档页"有帮助"评分；外部搜索引擎对文档页的索引覆盖率。

P0Hello World 的门槛：账号与准入

证据
海外开发者"注册 Huawei ID 都失败"、"不登录连 IDE 都下不了"、"区域必须设为中国否则组件安装出错"；安全厂商称境外几乎无法合法获取环境。
方向
IDE 与 Command Line Tools 下载免登录（登录只在签名 / 上架 / 云能力时要求）；注册流程的海外可达性专项测试；安装器自动处理区域相关组件源，而不是让开发者手动设为中国。
指标
从访问官网到第一个 HAP 运行在模拟器上的中位时间（分中国 / 海外 IP）；注册漏斗各步流失率。

P1发布动线：从 IDE 直达 AGC

证据
IAP 开通需邮寄材料、权限每次重新生成 Profile、"iOS 在 Xcode 勾选就直接开通"；微信开发者工具已把上传审核放进 IDE；7.0 线已有"自动重签名并上传 AGC"起步。
方向
在 Studio 内完成签名、权限申请、上传、审核状态查看；权限与 Profile 的变更自动同步而不是手工重生成；把上架预检（DevEco Testing）前置到构建阶段。
指标
从"构建通过"到"提交审核"的操作步数与中位时间；因签名 / Profile 问题被打回的比例。

P1进驻开发者已有的 IDE：官方 VS Code / JetBrains 插件

证据
跨平台迁移是存量 App 的主入口，这些团队用 VS Code / Android Studio；生态位地图整行空白；DevEco CLI 已具备 LSP + MCP 服务，技术上具备做轻量插件的基础。
方向
基于 DevEco CLI 的 serve 能力发布官方 VS Code 扩展（ArkTS 语言服务、构建 / 运行 / 日志、预览器嵌入），让 RN / Flutter / uni-app 开发者不切换编辑器就能调试鸿蒙目标；JetBrains 市场同理。
指标
插件安装量；跨平台工程中"未打开过 DevEco Studio 却完成上架"的比例。

P2零安装入口：面向新手与教学的 Web 体验

证据
安装包 10GB+、路径过长报错、学生"B 站找不到想要的教程"；生态位地图 Web 一行全空；Google AI Studio 已能直接发布到 Play。
方向
浏览器内可运行的 ArkUI Playground（预览器 Web 化）与 Codelab 一体；作为学堂与认证的默认练习环境。
指标
Codelab 完成率；新手从注册到第一次预览的时间。
Ring 3 · 生态级 · 政策与审核

—审核一致性与反馈闭环

证据
"被审三次以上没过、同样的软件 Android 和 iOS 都上架了"、"只能靠申诉才能上架"、"上架难度 5 倍"；论坛"浏览量几千回复 0"；官方对文档反馈"本周更新"式响应存在但不成体系。
方向
公开、可检索的审核规则与拒审原因编码；独立开发者通道；论坛问题的官方响应 SLA 与状态可见；把 IDE 内的反馈按钮与 issue 系统打通并回流版本说明。
指标
上架一次通过率；论坛官方响应率与中位响应时长；激励计划参与开发者的 6 个月留存。

一个整体的判断：2026 年的 DevEco 已经不缺形态，缺的是连续性——三种 AI 形态之间的连续、官方性能口径与开发者机器之间的连续、文档四套体系之间的连续、IDE 与 AGC 之间的连续、以及"注册→hello world→上架→拿到激励"这条主动线的连续。舆情里最重的几句话（"一比一复刻"、"邮寄材料"、"注册不了 Huawei ID"、"交叉验证"）都落在断点上，而不是落在某个功能缺失上。

06 / 放大到全体开发者

1100 万注册开发者里，都是谁

07 / 接手判断

为什么是现在，为什么是终端

四个事实的交汇

  1. A
    主战场已经由 IDE 移向终端与 Agent。HDC 2026 同时发布 DevEco Code（终端 AI Agent）与 DevEco CLI；HarmonyOS 7 提出 Agentic 自进化架构，主张"意图即服务"。应用形态从 App 走向 Agent，开发工具形态随之从 IDE 走向终端。这不是趋势判断，是已经发生的产品事实（§01）。
  2. B
    商业逻辑落在漏斗上。注册开发者 1100 万，上架应用与服务 40 万款，中间是巨大的转化落差；把镜头拉到分层结构，真正写过鸿蒙代码的约 5–15%（§06）。从注册到产出之间的核心变量，正是工具与文档体验。终端愿意为这条线投钱，商业逻辑在这里。
  3. C
    新面没有既得格局。DevEco Code 基于开源 OpenCode 扩展——交互范式是继承来的，不是设计出来的。既没有人捍卫既有格局，也确实存在明显的设计空位。这与在成熟 GUI 上争取重设计是两件事。
  4. D
    此前的堵点不在设计质量，在于成果未能进入产品版本。终端形态是设计能够直接落地的入口，也是接手后与既往打法的根本差别：不在成熟 GUI 上争取重设计，在新面上先做出可运行的东西。

09 / 主攻方向与 90 天

四个核心设计点，各自服务谁

聚焦鸿蒙开发者从上手到交付的端到端场景，通过 4+ 核心设计点保障开发者在终端形态下的信任与效率。下表把每个设计点接到 Part I 的人群与证据上——这也是对外说服时的引用顺序：先给证据，再给设计。

核心设计点要解决的问题主要受益人群（§06）支撑证据（§03 / §06）
终端 Agent 的执行过程可见与可干预自动化执行不可控独立开发者、学习者DevEco Code "为什么这么慢——一个简单页面一小时无响应"；CodeGenie "昨天还能用，今天就一直加载"（云端排队）；官方称故障修复成功率超 80%，意味着约 20% 需要人接管，界面必须给出信任校准
多文件改动的审阅与回退改动结果难核验企业团队、独立开发者小红书鸿蒙工程师："Code Linter 还不能与 Git Prehook 关联，导致无法在流水线上自动检查"；DevEco Testing "缺乏脚本化能力，需要人工操作辅助"——企业团队的核验诉求已经很具体
Skill 的发现与复用路径能力散落难复用企业团队、ISV美团自研本地工具链 Meat、快手 QuickTransformer、货拉拉 AspectPro——头部团队各自造轮子；官方已有 70+ Skill 但发现路径未成形；deveco-toolbox 归档说明社区愿意向官方收敛
开发者文档由人读重构为 Agent 可检索文档命中率低全部七层——唯一在每层都出现的抱怨三年持续的"指南 / API / Q&A / 最佳实践要交叉验证"；PC 适配者"5 个核心问题在官方文档里 0 命中率"；DevEco Code 的 arkts_knowledge_search 目前是私有工具，尚未作为公共 API / MCP 开放

第四点值得单独说：在 Agent 时代，文档的第一读者从人变成了 Agent——DevEco Code 的能力之一就是文档检索，CodeGenie 用 RAG 读官方文档。这与"设计交付物的第一读者已经是开发者的 AI 而不是前端工程师"是同一个判断的两个面。把官网与文档重新定义为"Agent 可消费的知识界面"，一块看起来边缘的存量业务就变成了战略叙事的一部分，也是把留下的官网侧同事凝聚起来的方式。

一条来自 Part I 的提醒：§05 把优化方向分成三个同心圆——Ring 1 工具内可自主推进，Ring 2 需与官网 / 文档 / AGC 协作，Ring 3 是审核与政策。在没有组织杠杆的前提下，90 天的目标只应该从 Ring 1 与"体验治理"里选：Ring 2 的文档 Agent 化虽然价值最高，但依赖跨团队协同，适合作为叙事主线与半年目标，不适合作为"打破从未落地记录"的第一件事。第一件事要选一个自己就能做完、且能被看见的。

90 天骨架

  1. Week 1–3摸清现状与建立事实基础

    与终端侧对齐 DevEco Code / CLI 的设计归属与边界；与 ZJ / CY / JHY 各聊一次，摸清开发侧上层反对的具体内容（不在路标 / 风险 / 不认可设计介入产品决策，是三种不同的问题，对应三种不同的解法）；本报告作为对内汇报与对外协同的开场。

  2. Week 3–6选定第一件能自己做完的事

    从 4 个核心设计点里选执行过程可见与可干预——它在 Ring 1、有现成构件（DevKit TUI 设计系统的进度 / 状态 / 中断模式）、且有直接的开发者证据。产出：一份 TUI 体验规范 + 可运行参考实现，而不是效果图。

  3. Week 6–10推进入版本

    以参考实现的形式提交，走"代码先进、图片从代码导出"的既有路径；同时启动体验治理的度量口径定义（五触点一致性），这条线不需要开发侧接受重设计就能起步。

  4. Week 10–13沉淀叙事与外部可见度

    把第一件落地的事 + 开发者证据 + 治理框架合成一次汇报；对外可见度的天然舞台是 HDC，选题机制与窗口期需要提前确认。

首个季度锁定一项能力进入产品版本，扫清这条线长期未落地的记录。量化目标待与终端侧口径对齐后补充。
