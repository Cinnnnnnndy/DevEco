生成中状态的位置

返回研究分类 启动页

DevEco Code 里，Agent 生成内容时下面那行「进行中」上下跳。这一页只答三件事：为什么跳、同类产品把这一行放在哪、怎么改；末尾是可直接转成测试的验收条件。

跳的不是「内容在长」 规范里算位移的是被推动的邻居，不是变大的那个元素。
状态行不该待在内容流里 待在流里，位置就由内容长度决定——生成多长，它就让多远。
拆成两处，就都不跳 固定处只说「还在跑 / 怎么停」，流动处只说「做到第几步」。

01 它为什么会跳

四种机制

「上下跳」至少要两条同时成立：一条让它往下走，一条让它弹回来。只修一条，问题会从「被推下去」变成「弹回来」。

机制触发点看到的样子管的是
M1 被推下去 状态行的 DOM 排在生成块之后，内容每长一行就顶它一行 慢慢往下滑，越生成越远 「下」
M2 弹回来 过程收成一行摘要、占位骨架被真内容替换、思考块折叠——高度回落 突然往上跳一段 「上」
M3 后到的信息 用时、token 数这类结尾信息补在状态行上方那一层 已经稳定了又掉一格 「下」的第二次
M4 滚动打架 每来一段就滚到底；用户往上翻历史时，跟随逻辑又把它拽回底部 整块来回窜，眼睛抓不住 放大 M1

判据：位移的定义里就有答案

只有当已有元素改变起点位置时才算布局位移。新元素加进 DOM、或已有元素改变大小，本身都不算——只要这个变化没有导致其他可见元素改变起点位置。 （web.dev《Cumulative Layout Shift》· 见第 7 节）

所以内容在长本身不是问题，位置会变的那个邻居才是。把责任放在「生成内容太长」上会修错地方；要改的是让状态行的位置不由内容长度决定。

另一件容易误判的事：浏览器的滚动锚定救不了这个场景。它只补偿视口上方的变化，而状态行与生成内容同屏可见。 （W3C《CSS Scroll Anchoring Level 1》· 见第 7 节）

折叠本身没错，错在这一帧没人接住高度

过程收成一行是好设计（结论先行）。要改的不是折叠，而是让收缩发生在一个不变的框里，或在收缩的同帧把滚动位置补回去。

02 这根行为什么特别不能动

三条理由

不是所有会动的元素都算缺陷。这一行例外：它全部的价值就是「随手一瞥」，位置一乱就没了。

理由为什么
它是「还在跑」的唯一凭据 Agent 干活时人常在看别处，回来第一眼要找的就是它。位置一动，「回来」就从「看一眼」变成「先找一遍」。
它承载「怎么停下来」 停止 / 打断挂在这一行上。会移动的点击目标就是会跑的靶子；点空之后人的第一反应是再点一次。
它是给人扫的，不是读的 在跑 / 在等你 / 在验证 / 完成——扫描依赖固定位置，阅读才依赖上下文。

产品自己的规范早就这么写了——只是没写「位置」

仓库里的既有条文排起来看：「位置稳定」一贯如此，只在「生成态」这一条上漏了。

  • 状态胶囊本来就设计成原地换色。.ai-status 的过渡只有 background / color：八个状态在同一处换颜色、不换位置。 （deveco-intui-kit/src/ai.css · 第 2 节「进行态」）
  • 「一个状态只留一处在动」。它原本只管动效、不管位置；这次补全成「一处在动 = 一个动效 + 位移为零」。 （ai.css · 另见 docs/ai-system.html）
  • 缓动也不许回弹。--ai-ease:cubic-bezier(.2,.8,.2,1) 的注释就是「只减速，不回弹」。状态行上下弹回，正是这条排除的动。
  • 会变的东西先把空间占住。启动页的 html{scrollbar-gutter:stable} 就是这个办法，注释写着不加它会「整页横向跳一下」。 （site/launcher.css）
  • 同一个产品里已经有一处做对了。生成中的输入框用 .ai-field[data-state="generating"]：固定在面板底部、min-height:38px 预留高度，从来不跳——它在 composer 里，不在内容流里。本页推荐的就是这个位置。 （ai.css · 第 3 节）

03 别的产品把这一行放在哪

四个同类产品

只列能查到出处的一手实现：Codex CLI、Claude Code、Gemini CLI 的源码 / 官方文档，加一个形态最接近的 IDE 面板 Cline。 四个里没有一家把状态行排进内容流。

产品状态行在哪位置由谁决定出处
Codex CLI 输入框上方一行，是 bottom pane 自己的 widget，不写进对话记录 面板布局 源码注释写明目的：「保持一行，避免 bottom pane 的纵向布局抖动」，「打断提示保持在固定的视觉位置」；另有测试专门防止附加文字挤走控件。 （codex-rs/tui/src/status_indicator_widget.rs）
Claude Code footer 里自己的一行：状态行渲染在 footer 徽标上方，且不替换徽标 footer 布局 官方文档原句「renders in its own row above the built-in footer badges」；esc to interrupt 是 footer 提示。 （Claude Code 文档 · Status line）
Gemini CLI footer 的 StatusRow，固定最小高度 1 行 固定行高 常量 STATUS_MIN_HEIGHT: 1：没有状态时也渲染一个 1 行的空盒子占位；长状态用碰撞检测让位，提示条改用绝对定位测量，注释写「防止布局回路」。 （packages/cli/src/ui/components/StatusRow.tsx）
Cline（VS Code 面板） 思考行锁在 150 / 200px 高的内滚框里，内滚不撑外框 框高 跟随滚动由一个用户意图状态位控制（上滚即置位）；只在折叠时补一次滚底，展开时绝不滚；变高用平滑、变矮用瞬时。 （useScrollBehavior.ts / ThinkingRow.tsx）
DevEco Code（现状） 排在生成块正下方，跟着内容走 内容长度 要修的四家里唯一把位置交给内容长度的一种。

归纳成三类，以及该选哪一类

落点只有三类：外壳常驻（顶栏 / 终端标题 / Xcode 27 的侧栏与工具栏标记）、面板固定行（输入框上方那条带）、内滚框（内容自己滚，外壳不动）。 前两类靠布局定位置，第三类靠固定高度定位置——都不需要预测内容会长多高，也不需要滚动补偿。

对 DevEco Code：面板固定行为主，外壳胶囊兜底。产品自己的生成中态已经在输入框上方这么做了，沿用即可；顶栏胶囊只留「有别的 Agent 在等你」这类最挡路的一件。

04 改法

A–C 必需 · D / E 配套

A 治「被推」，C 治「弹回」，B 是 A 的前提；D 管滚动，E 管字宽。

改法做什么治哪条代价是否必需
A 移出内容流 状态行不排在生成块之后，改为面板固定一处的常驻行 M1 M3 状态离最新一行内容远了一点；固定行紧贴内容区下沿即可 必需
B 让生成区自己滚 内容区给定高度 + 自己滚动，外壳不随内容重排 M1（前提） 要定「贴底高度」与窄屏下的回落 必需
C 收缩时接住高度 折叠 / 换占位时用等高占位或滚动补偿，让视口里的锚点不动 M2 折叠必须在一帧内完成 必需
D 粘底策略 只在用户本来就贴着底部时跟随；上滚就停止跟随，并给「回到最新」 M4 多一个入口按钮 B 的配套
E 预留与等宽 会变宽的数字用等宽数位；不定态进度条用固定轨道宽度 微抖 几乎为零 已做过一半

E 已经做过一半，别再当新问题提

状态里的数字已用 font-variant-numeric:tabular-nums，3 / 6 涨到 10 / 16 宽度不变。 残余的跳动不来自字宽，别去调字号和间距——那会把注意力从真正的原因上引开。（ai.css · .ai-status .t）

顺带排除一个反直觉的方向

「让状态行跟着最新内容走，这样离注意力近」等于主动选回现状：位置重新交给内容长度，而且生成越快跳得越频繁。 人真正想要的是「别让我找它」，固定位置就能满足。

05 落到 DevEco Code

五条改动

不改状态机的八个状态、不改颜色分工，只改「哪一行放在哪」和「收缩时怎么收」。

  1. 状态行固定在面板底部那一行（现有生成中态那条带，输入框上方），不放在内容末尾。它装状态机那一句（生成中 / 在等你 / 在设备上验证）+ 已用时 + 停止，用现有 .ai-status 原地换色，不需要新组件。
  2. 细粒度步骤留在内容流里。「正在写第 3 / 6 步」本来就该跟着内容走——它描述的是内容本身。
  3. 完成时同帧替换，把高度接住。过程收成一行摘要、占位换真内容都在一帧内完成；内容区用 min-height 预留常见高度，避免「先塌再长」的两拍。
  4. 粘底，而不是每次都滚到底。只在用户贴底时跟随；上滚就停止并显示「回到最新」，滚回底部自动恢复。
  5. 保持既有分工：「在等你」才允许用琥珀色抢注意力，其余进行态安静；一屏只留一处渐变、一处动效。

四帧对照：同一段内容，两种放法

现状 · 开始
进行中 · 1 / 6停止
状态行落在最后一行内容下面，正好压在基准线上。
现状 · 生成到一半
进行中 · 4 / 6停止
被推下去 4 行。虚线是原位置；越生成越远，可能已被滚出视野。
现状 · 生成结束
完成 · 6 步收起

自带实测：两种放法同时跑一遍

两块跑同一段内容（6 步 → 收成一行），各自实时量状态行的位移。数字是页面自己算的，不是写死的。

06 验收条件

六条，可勾

写成能被测的句子，而不是「感觉不跳了」。AC-1 可以直接变成一条自动化断言。

  • AC-1 生成全程，状态位的 getBoundingClientRect().top 相对面板的位移 = 0 逐帧采样；允许 1px 亚像素误差。第 5 节那块实测就是这条断言的最小实现。
  • AC-2 生成期间用户上滚后不再自动跟随，出现「回到最新」；滚回底部后跟随自动恢复 覆盖 M4。用「用户上滚过没有」这个状态位判断，而不是「距底部小于 N px」——Cline 用的就是前者。
  • AC-3 过程折叠 / 占位替换的那一帧，视口内已知锚点的 top 位移 ≤ 1px 覆盖 M2。折叠必须同帧完成，不许「先塌后长」的两拍。
  • AC-4 停止 / 打断在生成全程可点，且它自己的 bounding rect 不变 移动的点击目标 = 点空；同时是可达性要求。
  • AC-5 开「降低动效」后 AC-1 仍成立；此时「动的信息」改为文字（步骤数 / 已用时） 沿用状态机的既有原则：降低动效时不靠动效传进度。
  • AC-6 状态行不做位置动画（不用 transition 过渡 top / transform）；状态变化只换色与图标 与 .ai-status 现有的换色过渡、以及「只减速、不回弹」的缓动原则一致。

局限：缺一份产品内现场证据

现象发生在 DevEco Code 产品里，不在本仓库的界面稿里。机制（M1–M4）、判据与四个同类产品都有一手出处；但 「这一次到底 M1 还是 M2 在主责」需要一次产品内录屏或截图——尤其完成那一刻是「收成一行」还是「占位被替换」，两者对应不同的修法顺序。 补证据的最小做法：录一次带时间轴的生成过程，必须含「最后一段内容落完」与「过程折叠完成」前后两帧，各取一图量状态行与相邻元素的 top。

待确认（三条）

  • 收缩方式：折叠、换占位，还是两者都有？决定 A / C 谁先做。
  • 面板底部那条带现在有几个占用者（生成中态、上下文 / 模型信息、快捷键提示）？需要一次同屏清点，避免新状态行挤走旧的又跳一次。
  • 多 Agent 时这一行显示谁？既有规则是「胶囊只推最挡路的一件」，是否沿用到面板固定行要定下来。
