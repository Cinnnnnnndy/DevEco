AI 干完的活，怎么验：准出标准、无人值守时段的成果、看不见的结果

10-29 四层汇报后领导追问的三个问题：用户在 AI 协作中如何形成准出标准、减少检查成本；AI 在非工作时段产出的成果如何检验；后端逻辑、脚本、配置这类不是界面的结果，怎么管控、理解和验证。下午评审又追问了一点：AI 代码的冗余、规则检查和二次编辑问题是否突出，只看应用结果够不够，本页第四问回应。本页对照 Claude Code、Codex、Cursor、Devin、GitHub Copilot、Jules、Kiro、Xcode 27，加上 Antigravity 作补充，看每家在这三件事上做了什么、共同的做法是什么、还空着什么，最后落到 DevEco 27X 的「验得了」怎么做。

结论三个问题的本质总表问题一 · 准出标准问题二 · 无人值守的成果问题三 · 看不见的结果追问 · 代码质量还要不要查各产品还空着什么对 DevEco 27X 的启示待验证来源

结论

  1. 行业的答案是把「检查代码」换成「检查证据」。2025 年大家还在让人读 diff；2026 年各家都在让 Agent 自己先跑、先审、先录：Copilot 开 PR 前先自审并跑代码扫描、密钥扫描、依赖漏洞检查官方，Cursor 云端 Agent 交付时附视频、截图、日志官方，Devin 在 CI 变绿后自动录一段带标注的操作视频官方。人的检查成本降下来，靠的是人只看证据和例外。
  2. 准出标准有两个来源：这次任务写的，和仓库里沉淀的。这次任务的标准靠「先写再做」：Kiro 把需求写成 EARS 句式的验收条件，再生成属性测试逐条验官方；Claude Code、Xcode 27 用计划模式让人先改计划再动手官方。长期的标准写进仓库：AGENTS.md / CLAUDE.md 里的测试命令、Copilot 的自定义 Agent、Devin 的 Skill，第一次人教，以后 Agent 自己照着验。减少检查成本的关键在第二种：Kiro 自主 Agent 会把 PR 评审意见记下来用到以后的任务官方，Devin 测完会提 PR 改自己的测试 Skill官方。
  3. 非工作时段的成果，各家用同一套四件事管：隔离、证据包、只报例外、事后可查。Codex 定时任务默认跑在独立 worktree、结果进「Scheduled」收件箱、有发现才标未读官方；Claude Code Routines、Cursor Automations、Kiro 自主 Agent 都在云端沙箱里跑、产出草稿 PR官方。共同点是：夜里的活不直接落到主干，早上看到的是一份打包好的证据，不是一堆日志。
  4. 看不见的结果，做法是把它翻译成看得见的东西。四条路：让它跑起来出证据（Codex 引用终端日志和测试输出官方）；把不可见变成可观察（Cursor Debug Mode 插日志点、让你复现、再删掉官方，Cursor Agent 为一个后端漏洞专门写演示页去复现官方）；讲给人听（Devin Review 按逻辑重排 diff，Antigravity 交付 Walkthrough 文档，Jules 出音频摘要）；管住边界（权限、网络、密钥按任务配置，敏感文件改动必须人审）。
  5. 空位在「设备与平台」这一段。各家的证据止于浏览器和单元测试：Devin、Cursor 录的是网页，Xcode 27 能在模拟器里点、能把流程转成 UI 测试，但仍是一次一台官方。没有一家把多设备、分布式、上架合规当成准出关卡，也没有一家把「夜里跑完的结果」做成多设备对比。这正是 27X「验得了」可以领先的地方：准出标准里写进鸿蒙特有的关卡（ArkTS 检查、一多、上架体检），证据里放多设备截图和录屏，夜里在云端模拟器跑，早上只看异常。
  6. 看结果不等于不查代码。结果对回答「这次做对了没有」，代码质量回答「下次还改得动吗」。数据显示 AI 代码的重复和问题密度确实更高（GitClear：2024 年重复代码块增加 8 倍；CodeRabbit：AI 参与的 PR 问题数是人写的 1.7 倍社区），访谈里也有「偷偷塞东西，审又审不动」。行业的做法不是让人回去逐行读，而是把代码质量也变成机器关卡：AI 审 AI、AI 代码用更严的质量门禁、只看增量和越界。DevEco 要把 ArkTS 规范和鸿蒙最佳实践做成这道关卡。

三个问题，各自在问什么

三个问题看起来是三件事，其实是同一条链上的三个点：标准定得清楚，才能在没人看的时候自动验；验出来的东西要人看得懂，才算验过。

问题一

准出标准：「做完」由谁说了算

AI 说「完成了」不等于完成。难点不在写标准，而在标准从哪来：用户每次手写太累，不写又只能逐行看 diff。所以真正要回答的是：标准怎么从一次任务里长出来，又怎么沉淀下来下次不用再写。

衡量：每个任务人要看几处、花几分钟；第二次同类任务要不要再说一遍。

问题二

无人值守时段：没人盯的时候出的活

夜里、开会时、后台跑的任务，过程没人看，只剩结果。风险有两个：改坏了没人拦，以及早上一堆结果没法一件件看。所以要回答：在哪里跑才不会伤到现有工作，交回来的是什么形态，哪些要人看、哪些不用。

衡量：一晚上的结果早上几分钟看完；有没有未经审批落到主干的改动。

问题三

看不见的结果：没有界面可点

界面改了能截图，后端逻辑、脚本、配置、数据迁移、权限声明改了，人没有东西可看。难点是看懂和敢放行：既要把结果翻译成人能判断的形式，又要给高风险的改动划边界。

衡量：不读代码能否判断对错；敏感改动有没有被单独拦下来。

问题一 · 准出标准怎么形成，检查成本怎么降

把九家的做法归一下，是四种机制。前两种决定「标准是什么」，后两种决定「人要看多少」。

① 先写标准再动手

做之前把「怎样算做完」写下来，并且写成能被机器验的形式。Kiro 最彻底：EARS 句式每条都有条件和可观察的结果，然后转成属性测试；Claude Code、Xcode、Jules、Antigravity 用计划当轻量版标准。

代价：小任务也走全套会很重。Kiro 后来加了不经审批的 Quick Plan社区，说明「按任务大小分级」是必须的。

Kiro · Claude Code · Xcode 27 · Jules · Antigravity

② 标准沉淀进仓库，下次不用再说

测试命令、规范、团队怎么验，写进 AGENTS.md / CLAUDE.md / 自定义 Agent / Skill。更进一步是自己长：Kiro 自主 Agent 把评审意见记成以后的规则，Devin 测完提 PR 改测试 Skill。

这是降检查成本最根本的一条：同一类问题人只指出一次。

Codex · Claude Code · Copilot · Devin · Kiro

③ 自动关卡：Agent 自己先过一遍

人看之前，先让机器拦一道：Claude Code 的 Stop hook 不过测试不让说完成；Copilot 先自审、再跑三种安全扫描；Jules 的 Critic、Kiro 的验证 Agent 都是「另一个 AI 来挑刺」。

要点：审的那个和写的那个分开，审出来的先自证再报，否则噪音会把人淹没（Claude Code Review 先验证再报，误报 <1%）。

Claude Code · Copilot · Jules · Kiro · Cursor Bugbot

④ 只给人看证据和例外

交回来的不是 diff，而是证据包：测试输出、日志引用、视频、截图、基准前后对比；问题按严重度排，没问题的不打扰。

注意：Devin 官方自己说录屏只覆盖一条核心流程，是「冒烟检查」，不能替代测试。证据要和标准一一对上，不然只是「看起来做了」。

Codex · Cursor · Devin · Copilot · Antigravity
一句话：准出标准不是用户每次填的表，而是「任务里写的几条 + 仓库里攒下的规则 + 平台自带的关卡」三层叠出来的；人只确认第一层，第二层靠纠正一次就记住，第三层工具默认就有。

问题二 · 非工作时段的成果怎么检验

2026 年各家都上了「你不在也在跑」的能力：Codex 定时任务、Claude Code Routines（2026-04）、Cursor Automations、Kiro 自主 Agent（2025-12）、Copilot、Jules、Devin 本来就是异步的。检验方式高度一致，可以归成四件事：

  1. 隔离：夜里的活不落到主干。独立 worktree（Codex）、云端沙箱或虚拟机（Claude Code、Cursor、Kiro、Devin）、只能推专用分支（Copilot 只推 copilot/ 分支，且发起人不能自批）。最坏情况也只是「扔掉一个分支」。
  2. 护栏事先配好：因为没人能当场批准，网络、密钥、能执行的命令必须事先按任务配置。Codex 文档明写定时任务「用你的默认沙箱设置无人值守运行」；Kiro 每个任务单配网络和密钥。
  3. 交回证据包，只报例外：Codex 结果进收件箱、有发现才标未读；Devin 在 CI 变绿后才录屏；Cursor 附视频并允许接管那台机器亲手试。早上看到的是「哪几件要你看」，不是「昨晚做了什么」。
  4. 过程可回看：Copilot 会话日志、Devin 会话回放、Antigravity 的 Walkthrough。平时不看，出问题时能还原 Agent 当时为什么这样做。

问题三 · 不可视结果的管控、理解与验证

后端逻辑、脚本、配置、数据、权限声明，这些改动没有界面可截。各家的共同思路是：不要求人读懂代码，而是把结果换成人能判断的东西。归成四条路，从「验」到「懂」到「管」：

① 跑起来，用运行证据说话

Codex 交付时引用具体的终端日志和测试输出，你点到哪一步看哪一步；Copilot 的自定义 Agent 先量基准、改完再量，交的是数字差；Kiro 用属性测试在大量生成输入上验逻辑，比几条手写用例覆盖得多。

适合：算法、接口、性能、数据处理

② 把不可见变成可观察

Cursor Debug Mode 是代表：Agent 不猜，先插日志点，让你按它给的步骤复现，读运行时数据定位，修完再复现一次，最后把日志点删干净。Cursor 云端 Agent 还会为一个后端漏洞专门写演示页、跑攻击流程、录视频。Xcode 把预览渲染当成产物。

适合：偶现问题、状态逻辑、安全问题

③ 讲给人听

Devin Review 把大 diff 按逻辑重排讲解；Antigravity 交 Walkthrough 文档，并能在上面批注让 Agent 改；Claude Code 有解释型输出风格；Jules 能出音频摘要。关键是讲「改变了什么行为」，而不是复述改了哪几行。

适合：配置、脚本、架构调整、跨模块改动

④ 管住边界：哪些改动必须人看

Claude Code hooks 和权限规则能指定「改这些文件、跑这些命令要先问」；Copilot 在流程里跑密钥扫描和依赖漏洞检查；Kiro 每个任务单配网络和密钥；Codex 按审批模式分级。看不见的结果不一定都要人懂，但高风险的那类必须单独拦。

适合：权限、签名、密钥、依赖、数据迁移
缺口：四条路里，①②已经比较成熟，③多数产品还停在「总结一段话」，④是按文件路径和命令配的，没有一家按「改动的业务含义」分级，比如「新增了一项敏感权限」「改了签名配置」「改了数据库表结构」。这类判断需要平台知识，通用工具做不深。

追问 · 代码冗余、规则检查、二次编辑：只看应用结果够不够

评审时的追问：AI 能把功能跑通，但代码冗余、规则检查、二次编辑这些问题在真实工作里是否突出？随着代码大量生成、持续迭代，代码质量检查是否还需要，而不只看应用结果？回答：需要，而且越往后越需要；但检查的方式从「人读代码」变成「机器先查、人只看增量和越界」。

问题是真的：外部数据与访谈

  1. 重复变多、重构变少。GitClear 分析 2.11 亿行代码：2024 年 5 行以上的重复代码块增加 8 倍，代表重构的「移动行」下降 39.9%，复制粘贴的行数首次超过移动的行数社区。这正是「二次编辑」难的来源：同一段逻辑散在多处，改一处漏一处。
  2. 问题密度更高。CodeRabbit 抽 470 个开源 PR（2025-12）：AI 参与的 PR 平均 10.83 个问题，人写的 6.45 个，约 1.7 倍；逻辑与正确性问题最多，命名不一致约翻倍，格式问题 2.66 倍，严重与重大问题也更多社区。样本小、来自做审查工具的厂商，只作量级参考。
  3. 快了，但更不稳。DORA 2025（近 5000 人）：AI 使用已和交付吞吐正相关，但交付不稳定性继续上升，「快速失败、快速修复」抵消不了社区。Stack Overflow 2025（4.9 万人）：66% 最烦「差一点就对」，45% 说调试 AI 代码比预期更费时间社区。
  4. 访谈里同样有。「Opus 哪怕很聪明，他也会偷偷给你塞一些乱七八糟的东西」「我自己也看不下去」（2 份）；规矩每次重讲、记不住 MVVM V2、不用 router 这类习惯（4 份）；WPS 的 Auto-PR 约 20-30% 可用，并专门配了安全和质量 review 子 Agent；鸿蒙写超过五六个文件第一次编译肯定不通过（出自 2026-10 的 12 份用户访谈聚类）。

为什么只看应用结果不够

结果验的是这一次，质量决定下一次

应用跑通只说明当前这条路径对。冗余、绕过规范、塞进来的无关改动，当下看不出来，到第二次、第三次让 AI 改时才爆：要改的地方变多，AI 读到的上下文更乱，出错率跟着上升。持续迭代下，代码质量是AI 自己下一轮的输入质量。

人不读代码之后，更要有人替他读

访谈里多数人已经很少读代码，只看「改的文件有没有越界」。这不是不需要检查，而是检查要换人做：规则检查、重复检测、复杂度、越界改动交给机器和审查 Agent，人只看它挑出来的几处。

做法代表管的是什么

对 DevEco 的建议

  1. 验收卡加一层「代码健康」。和编译、多设备、上架体检并列：ArkTS 规则检查（Code Linter）、鸿蒙最佳实践（V2 状态管理、Navigation、断点布局、废弃 API）、增量重复、复杂度、越界文件。默认只报这次新增的问题，不翻旧账。推断
  2. 鸿蒙规则开放给外部 Agent。把上述检查做成 MCP / Skill，Claude Code、Codex 生成鸿蒙代码时自己先过一遍；规则随 SDK 版本更新，解决「文档改版四次」的问题。承接 23 开放 MCP 与 Skill。
  3. 二次编辑靠「记住规矩 + 定期收拾」。用户纠正一次（如「别用 router」）就沉淀成工程规则；夜间跑一轮清理任务（合并重复、删死代码、补测试），像问题二一样只把要你看的报出来。
  4. 改动标出处，审查只看要看的。每处改动标是哪个 Agent、哪次任务写的，按风险排（31 Agent 工作台已有雏形）；高风险或越界的才要人读代码。
  5. 可配指标：AI 改动一次编译通过率、新增规则违规数、增量重复率、AI 代码在两周内被重改的比例（二次编辑成本）。推断

各产品要点

Kiro

规格驱动 · 自主 Agent（2025-12 预览）
  • 每个功能三份文件：requirements.md / design.md / tasks.md，前一份批准了才写下一份社区；验收条件用 EARS：「WHEN [条件] THE SYSTEM SHALL [行为]」，天然可测官方
  • 需求分析在写代码前查矛盾、歧义和遗漏官方；有 Bugfix Spec（根因、修复设计、需保持的行为）和不经审批的 Quick Plan社区
  • 自主 Agent：每任务独立沙箱、最多 10 个并行、另有验证 Agent；PR 解释实现决策；评审意见会保留并用到以后的任务官方

Claude Code

CLI / IDE / Web / Routines / Code Review
  • Stop hook：Agent 宣布完成时触发，可强制跑测试，不过就让它继续，社区里常用来防「假完成」官方社区
  • Code Review（2026-03 预览，Team / Enterprise）：PR 打开时多 Agent 并行找问题，先验证再报、按严重度排，不自动批准；内部数据：有实质评审意见的 PR 从 16% 升到 54%，被判错的 <1%，平均约 20 分钟官方
  • Routines（2026-04）：保存的任务 = 提示词 + 仓库 + 工具，定时 / API / GitHub 事件触发，在云端跑，不需要你开着电脑官方

Codex

CLI / App / Cloud
  • 云端任务以终端日志和测试输出的引用作为可核查证据官方；AGENTS.md 写明怎么测，测不过它会说
  • App 定时任务：Git 仓库里可选本地或独立 worktree，「worktree 让定时任务的改动和你没做完的本地工作分开」；「Scheduled 视图就是你的收件箱」，有发现的标未读官方
  • 官方建议先在普通对话里手动跑、看头几次定时结果再调整，等于是「先人验几次，再放手」官方

Cursor

IDE · 云端 Agent · Bugbot · Debug Mode
  • 云端 Agent（2026-02-24 博客）：各自一台虚拟机，能构建、运行并测试自己的改动，产出视频、截图、日志，「迭代到验证通过，而不是交第一版」；可远程接管桌面亲手试官方
  • 例子：临时绕过功能开关做本地测试、推之前还原；为漏洞写演示页并录视频；花 45 分钟走查文档站并总结测过的功能官方
  • Debug Mode：多假设 → 插日志点（发往本地调试服务）→ 让你复现 → 小改 → 复现确认 → 移除全部插桩官方

Devin

云端 Agent · 测试与录屏
  • PR 建好后建议测试，可设为预先批准自动测；顺序：读 PR 与代码 → 发测试计划 → 全屏录制并在关键时刻加标注官方
  • 录屏在 CI 变绿、评审意见处理完之后才做；视频关键处放慢、跟随点击缩放、压缩空闲时间官方
  • 官方定位为「简单的冒烟检查」，全面覆盖仍靠测试套件和 CI；测完可能提 PR 更新测试 Skill官方

GitHub Copilot

coding agent / cloud agent
  • 2026-02：开 PR 前用 Copilot code review 自审并改，改完才请你评审；代码扫描、密钥扫描、依赖漏洞检查在流程内跑（这几项原本属于收费的 Advanced Security）官方；2026-04 验证工具提速 20%官方
  • 会话日志里能看到扫描与自审步骤；自定义 Agent 放 .github/agents/ 并可在组织内共享官方
  • 风险控制：防火墙、只推 copilot/ 分支、发起人不能批准、Actions 要人放行官方

Jules

Google · 异步编码 Agent
  • Critic（2025-08）：生成时对所有改动做对抗式评审，问题退回重写；按用户语境和意图判断，不是固定规则；计划把 Critic 做成能用代码解释器和搜索的完整 Agent官方
  • 人批准前不做永久改动；PR 附推理与 diff官方

Xcode 27

WWDC26 · Agentic Coding · Device Hub
  • 构建错误直接回给 Agent；预览在当前运行目标上渲染成产物；演示里写了 12 个测试并全部跑过官方
  • 右侧产物面板：diff、新文件、渲染的预览放一起审后再接受；/plan 可逐行改计划官方
  • 实验室（非官方转述）：Agent 在模拟器里点、滑、输入，读无障碍树和截图，把走通的流程转成可重复 UI 测试；可跑一小时以上社区
  • 没有专门的后台 Agent 模式、没有内置验收条件；Device Hub 能统一管模拟器与真机，但没看到多台同时验证待确认（另见 Xcode 27 新特性研究）

对 DevEco 27X 的启示

27X 的「验得了」原本讲的是能力（多设备、分布式、上架体检）。这三个问题提醒我们：能力之外，还要把「怎么算验过」做成产品。按看得见 / 验得了 / 退得回 / 接得进四个特征落：

  1. 验收卡：把准出标准做成任务的一部分（回答问题一）。每个任务开始时，Agent 从需求和工程状态生成一张验收卡，分三层：任务条件（这次要满足的几条，用户可改，借鉴 Kiro EARS 但不要求用户写格式）、工程规则（团队沉淀的，纠正一次就记进去，借鉴 Kiro / Devin）、鸿蒙关卡（编译、ArkTS 检查、一多布局、上架体检、权限用途，平台默认带，这是别家没有的）。完成时每条标「已验 / 要你看 / 跳过」并附证据。小改动只走鸿蒙关卡，不走全套。推断 承接 31 Agent 工作台 的证据页签、02 场景化体检。
  2. 证据带设备：检查成本降在「不用自己上真机」（回答问题一）。别家证据止于网页录屏，DevEco 的证据应该是多设备并排截图和录屏、改前改后性能数字。人看的是「折叠展开态 ✗」这样的结论和对应画面，不是 diff。承接 16 真机多设备、17 模拟器多端。
  3. 夜间跑在云端模拟器，早上看「要你看」清单（回答问题二）。照行业共识做四件事：隔离（独立工作区 / 分支，不碰本地未提交改动）、护栏事先配（网络、签名证书、密钥按任务配，夜间任务不允许改签名和发布）、证据包、过程可回看。DevEco 多一步：按「要不要你决定」排，而不是按「有没有结果」；夜里在 27 云端模拟器多开跑，需要真机的白天排队复测，结果推到 25 手机客户端可直接看。
  4. 不可视结果：按鸿蒙业务含义分级管（回答问题三）。把改动翻译成「行为变化」：新增 / 删除了哪项权限、module.json5 改了什么能力、签名与 bundle 配置有没有动、数据结构是否兼容旧版本。高风险类（权限、签名、隐私、数据迁移）默认必须人看，并给一句人话说明影响；其余自动放行。这是通用工具做不深、DevEco 有平台知识能做的。推断
  5. 不可视结果：借 Debug Mode 的思路做 HiLog 插桩验证（回答问题三）。逻辑类问题让 Agent 插 HiLog 点、在设备上复现、读运行时数据定位、修完复测、自动清理插桩；性能和冻屏类直接出可读报告（已有 28 冻屏分析报告作样板）。
  6. 把验证开放给外部 Agent（接得进）。Claude Code、Codex、Cursor 都在让 Agent 自己验，但它们不懂鸿蒙。把编译、ArkTS 检查、多设备截图、上架体检开成 MCP / Skill，让外部 Agent 跑完 DevEco 的关卡再交付，验收标准就跟着 DevEco 走。承接 23 开放 MCP 与 Skill。
  7. 退得回是放心放手的前提。夜间和后台任务要能整任务丢弃、按步骤回退（14 AI 协作时间轴）；用户敢让 AI 夜里干活，前提是「最坏也只是扔掉」。
建议给领导的一句话：「行业已经从让人看代码转到让人看证据；DevEco 的不同在于证据带设备、关卡带鸿蒙规则——准出标准由任务条件、团队规则、鸿蒙关卡三层叠出来，夜里在云端多设备跑，早上只看需要你决定的那几件。」
可配的效果指标（口径待和产品线对齐）：每任务人工检查处数与时长、夜间任务早上处理时长、上架体检一次通过率、真机前暴露的问题占比、高风险改动漏审数。
