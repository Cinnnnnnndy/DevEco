一、总结论

读者只读这一句AI 让“写”几乎免费，代价转到人身上：验证要时间、盯着要注意力、信与不信要校准，三者成循环；打破循环要让验证变便宜，而验证的前提是意图清楚，所以意图要拆成字段、用合适的媒介表达、并作为有版本的对象被管理；交互方式由“意图有多明确 × 风险有多高”决定，信任用行为而不是问卷来测。

二、基准记号

全篇用三组记号描述“人付出了什么”和“意图处在什么状态”，后面每个机制都写成它让这些量怎么变。记号是本笔记自定的分析工具。🔸

一次 AI 交付，人要付出的时间
  T人 = T读懂 + T验证 + T切换                 ← 第五章：验证瓶颈压在前两项，注意力瓶颈压在 T切换

信任校准偏差
  Δ = 采纳率 − 实际正确率                      ← Δ>0 过度信任；Δ<0 信任不足；目标 Δ≈0

意图对象与版本
  I(v) = ⟨ 对象, 方向, 程度, 边界, 理由 ⟩ 的第 v 版   ← 第六章拆字段，第七章加版本
  E(t) = Agent 在时刻 t 实际执行所依据的意图
    用户改主意：I(v) → I(v+1)，E 应跟上        ← 意图变更，记版本
    Agent 跑偏：I(v) 不变，E(t) ≠ I(v)          ← 意图漂移，要告警

三、用语约定

本笔记用语指什么别名 / 易混点
验证人判断 AI 产出是否满足意图的全部动作：读、跑、测、比对不等于代码评审，看运行结果也算
注意力一次任务中被占用、无法用于思考的时间和次数不是工作时长，等着、盯着也算
信任 / 信任校准信任是不经检查就接受的程度；校准是让它对齐实际可靠度目标是 Δ≈0，不是信任越高越好
意图字段对象（哪个）、方向（什么样）、程度（多少）、边界（不能动什么）、理由（为什么）为 UI 类需求设计，架构类决策需调整
意图变更用户主动修改目标或约束纪要里与“漂移”混用，本笔记严格区分
意图漂移Agent 的执行偏离当前有效版本的意图INTENTFLUX 的定义更窄：已撤回的意图仍影响结果
介入 / 被动建议介入：AI 未被调用时主动给建议；被动建议：用户发起请求后得到的建议文献的 proactive / reactive。纪要把后者写成“响应式建议”
Background / Personal Agent后台常驻、长期记忆的 Agent / 个人助理型 Agent纪要写作“Good Agent”“Person Agent”，推测是转写误差 🔸
循环任务Claude Code 里用 /loop 建立、按间隔重复执行的提示词与桌面端定时任务、云端 Routines 不同

四、常见误解

❌ 测试都通过了，说明 AI 写对了
测试和代码出自同一个 AI 时，同一种误解会同时进入两边。
✅ 测试只能证明“和测试一致”
测试要有独立来源：人写的验收标准、真机运行记录，或另一路生成后由人确认。🔸 推断
❌ 信任问题就是用户不够信任 AI
于是设计目标变成“提升信任”。
✅ 问题是信任没校准
过度信任和信任不足都有害，目标是 Δ≈0。经典定义：合适的信任即信任等于系统的实际可信度。🔍 多源
❌ 给出解释和置信度，就能让人合理依赖
✅ 不一定
有研究指出解释或置信度不能稳定带来合适的依赖，有时反而加重过度依赖。详见第八章。⚠️ 单一来源，仅读到检索摘要
❌ AI 理解偏了，是因为提示词写得不够详细
于是不断加字。
✅ 有些字段文字天生填不准
“这个按钮”“醒目一点”分别缺对象和程度，加字只能描述，不能指认，也没有刻度。🔸 推断
❌ 有了截图和参考图，就不需要文字了
✅ 图填不了“理由”
AI 知道要什么样，却不知道为什么，遇到图里没覆盖的情况就会走偏。🔸 推断
❌ AI 问得越多，对得越齐
✅ 每次提问都是一次打断
值得问的是“答错代价大、又无法自己推断”的字段。🔸 推断
❌ 纪要的说法
“中途介入 62% 被关闭，任务结束后的响应式建议虽耗时更长但接受度更高。”
✅ 原文的说法
在工作流边界（如提交后）的介入参与率 52%；任务中途的介入 62% 被关闭。时机合适的主动建议理解只需 45.4 秒，用户自己发起的被动建议要 101.4 秒。耗时更长的是被动建议，不是任务结束后的建议。✅ arXiv 2601.10253 摘要
❌ 先发问卷，就能了解用户对 AI 的信任
✅ 自评信任和实际依赖常常脱节
有研究用设陷阱的编程任务测量实际依赖，发现问卷报告与编码行为不一致。信任要用行为指标测。⚠️ 单一来源（TU/e 硕士论文，读到检索摘要）
❌ 展开证据一定能提升信任校准
✅ 要同时测过度依赖
解释或置信度可能反而加重过度依赖。“证据展开”这个实验条件需要同时测 Δ 的正负两侧。⚠️ 单一来源（“When Help Hurts”检索摘要）

五、三个瓶颈：验证效率、注意力、信任

生成变便宜之后，人的判断力成了流程里最稀缺的资源。开发者从写代码的人变成审查和监督的人，三个瓶颈是这个新角色的三种消耗。

5.1　验证效率瓶颈：生成很快，验证跟不上

发生在哪里：每一次接收 AI 产出时。效果持续到哪里：不验证就合入的错误会一直留在代码里，到运行或线上才暴露。

机制：代码不是自己写的，人没有它的心智模型，T读懂 从近似 0 变成必须付出的成本。生成越快，待读的量越大。🔸 推断

常见表现

  • diff 太大没法认真看，“看起来没问题”就合进去了。
  • 测试也是同一个 AI 写的，等于自己验证自己。
  • 能编译、能跑，但边界条件或业务逻辑里藏着隐蔽错误。

方向：让产出本身容易验证

  • 小步改动，每步附可执行的证据：测试结果、预览截图、真机运行记录。
  • 在 diff 里标出高风险的几处。
  • 编译、类型检查、lint 前置自动跑完，人只判断机器判断不了的部分。

怎么衡量：从生成到被接受或拒绝的时长；被接受后又返工的比例。

5.2　注意力瓶颈：人变成了 Agent 的“保姆”

发生在哪里：Agent 执行期间。效果持续到哪里：每次打断之后，人回到原任务还要重建上下文，消耗不止打断那一刻。

  • 等结果时不知道该不该切去做别的。
  • 频繁的权限确认打断思路。
  • 同时开几个 Agent，来回切换上下文。
  • 要读大段 AI 输出和推理过程。

方向：给注意力做预算

  • 只把真正需要人判断的决策交给人，低风险操作批量授权。
  • 在任务边界通知，而不是每一步都通知。外部研究支持这一点：任务中途的主动介入有 62% 被关闭，详见第八章。✅ 原文摘要
  • 摘要分层，先结论再细节；任务能随时中断、随时接上。

怎么衡量：一次任务被打断的次数；等待和切换上下文的时间。

5.3　信任瓶颈：信任没有校准

发生在哪里：人决定“检查多细”的那一刻。效果持续到哪里：信任是跨任务累积的。一次严重翻车，可能让一个开发者长时间不再用某个功能。🔸 推断

  • 过度信任：接受 AI 编出来的 API 或过时写法。HarmonyOS 这类训练数据少的生态里尤其明显。🔸 推断，待用户研究验证
  • 信任不足：把 AI 的产出全部重写，或干脆不用。

方向：让信任有依据，出错能挽回

  • 说明结论来自哪份官方文档、哪个 API 版本。
  • 提供检查点和一键回滚，划清权限边界。
  • 让开发者看到 AI 在自己项目里的历史表现。
  • 给出把握程度要谨慎，见上面的常见误解。

怎么衡量：Δ = 采纳率 − 实际正确率；一次失败后的弃用行为。

5.4　三者的关系

一项措施同时作用在哪几个瓶颈上

措施验证注意力信任关系
附可执行证据↓ T验证—Δ 有依据叠加：一处投入，两处收益
批量授权低风险操作—↓ T切换依赖 Δ≈0有依赖：信任没校准时批量授权会放大过度信任
任务边界才通知—↓ T切换—独立
标注来源与版本↓ T验证—Δ 有依据叠加
给置信度可能 ↓—可能使 Δ 变大互斥风险：省了验证，换来过度信任

5.5　手算示例

假设一个 300 行的改动，用基准记号比较两种交付方式。数字是演示用的假设值，不是实测。🔸 假设值

方式 A：一次交付 300 行，只附一句“已完成”
  T读懂 = 300 行 × 6 秒/行 = 1800 秒 = 30 分钟
  T验证 = 自己跑一遍、查边界 ≈ 15 分钟
  T人   ≈ 45 分钟

方式 B：拆成 3 步，每步 100 行，附测试结果与截图，标出 2 处高风险
  每步只细读高风险处：2 处 × 20 行 × 6 秒 = 240 秒 = 4 分钟
  其余略读：80 行 × 1.5 秒 = 120 秒 = 2 分钟
  看证据：1 分钟
  每步 7 分钟 × 3 步 = 21 分钟；确认打断 3 次 × 1 分钟 = 3 分钟
  T人   ≈ 24 分钟

复核：45 − 24 = 21 分钟，约省 47%；
另一条路径：B 中细读行数 = 3 × 40 = 120 行，A 为 300 行，细读量降为 40%，与时间降幅同一量级 ✓

这个算例要说明的不是具体数字，而是省下的时间来自哪里：来自“只细读高风险处”和“有证据可看”，而不是来自拆步本身。拆步还额外带来了 3 次打断。

六、意图表达：文字装不下的部分

6.2　手算示例：候选理解还剩多少

用演示里的登录页算一遍，看每种方式把“AI 要猜的空间”缩小了多少。

页面上可被“这个”指代的元素：标题、账号框、密码框、忘记密码、登录按钮、注册入口 = 6 个
“醒目”的方向：变大 / 换色 / 挪位置 / 加浮起 = 4 种
“一点”的程度：设为 3 档（一点点 / 明显 / 非常）

只用文字：  6 × 4 × 3 = 72 种组合，AI 只能押一种
指出来：    1 × 4 × 3 = 12 种
再挑方向：  1 × 1 × 3 =  3 种
再调程度：  1 × 1 × 1 =  1 种

复核：72 ÷ 6 = 12 ✓；12 ÷ 4 = 3 ✓；3 ÷ 3 = 1 ✓

“指出来”这一步一次就砍掉了 5/6 的猜测空间，是性价比最高的一步。元素数和档数是演示设定，真实页面元素更多，指点的收益只会更大。🔸 演示设定

6.4　反过来：AI 怎么让人看懂它的意图

AI 用大段文字解释自己，正好撞上 第五章注意力瓶颈。每类要表达的内容，都有更省注意力的形态。

AI 要让人知道只用文字更好的形态
我理解成了什么“好的，我将修改登录页的主按钮样式……”把理解的对象在界面或代码里高亮回显
我打算怎么做描述步骤的长文字可勾选、可编辑的计划清单
会改动什么“我将修改以下 6 个文件……”改动前后对比预览，标出高风险的几处
我有多大把握“这应该可以解决问题”对不确定的 API 注明来源文档和版本（直接给置信度有风险，见 第五章常见误解）
进行到哪一步了滚动不停的日志状态时间线，只在需要人决策的节点亮起
做完了，对不对“已完成，所有功能正常”能运行的证据：测试结果、截图、真机录屏

外部证据：Chen 等人（2025）让大模型针对问题生成交互界面，与对话式回答相比，人类偏好最多高出 72%。✅ arXiv 2508.19227 摘要 偏好随领域变化：数据分析类约 93.8%，偏理论、数学解释的问题约 50%。⚠️ 单一来源（二手综述页），待读原文 Table 这提示“推理和论证”类内容不一定适合转成界面。

6.5　对齐的三个时刻

动手前 ── 对齐理解：复述、计划、提问          ← 改一句计划，比改五百行便宜
  └ 进行中 ── 发现偏离时纠正：漂移检测、就地说明   ← 第七、八章“意图状态管理”
       └ 完成后 ── 对照验收标准核对：证据、预览       ← 回到 第五章验证

操作代价越高、越难回滚，越应该把对齐放在动手前。🔸 推断

七、课题会要点（2026-11-19）

课题全称“AI 时代软件开发以及软件新形态下人机交互的意图对齐、信任交付以及系统交互”。会议把 第六章的意图推进到“有版本的对象”，并把信任放在全链条的主线位置。

7.1　会议要点

  • 核心判断：软件开发的竞争焦点从“谁写得更快”转向“谁更懂任务、更可控、结果更可信”，正好对应课题名里的意图对齐、系统交互和信任交付，也对应 第五章三个瓶颈。
  • 角色变化：开发者从执行转向规划与验证；软件工程与开发者体验合成一套人机协同系统，要从人和 AI 两个主体建理论框架。架构师和泛开发者的交互需求不同。
  • 人因工程：把注意力瓶颈、认知状态、信任依赖这类人因机制，转成 AI 可执行的交互策略，优化单次和长期回报。
  • 可视化：用户不愿读长文字，要用架构图、交互预览快速对齐意图、展示结果。

Agent 形态谱系

交互形态沿“代码建议 → 连续任务执行 → AI 自主驱动的自动工单”演进，形态每进一步，人机协作关系就变一次。当前主流是 Code Agent，其余形态在探索中。

7.2　三个研究缺口

缺口 1：意图识别与状态管理

目标：把自然语言变成可检查的意图对象，在多轮任务中持续维护目标版本和约束。

① 分类澄清   交付行为（创建 / 修改 …）+ 任务语义（目标 / 范围 / 约束 …）
② 结构化     大模型 + 多模态（图文、OCR）抽取关键意图字段 → 执行中检测漂移
               例：做游戏时游戏类型被悄悄改掉
③ 辅助决策   上下文补全 + 领域知识悬浮提示（如背单词应用的记忆曲线）+ 歧义冲突检查
               → 与华为专家对齐，优化澄清与变更检测

难点：多轮任务中区分“用户变更”和“Agent 偏离”；长链路复杂系统开发中的记忆与漂移检测。

缺口 2：自适应交互与交付

  • 介入时机：按任务风险和用户状态，在低打扰和高打扰策略之间切换；利用运行结果和代码评审归纳判断最佳介入点。
  • 可视化交付：把方案、代码、总结转成 HTML 页面、思维导图、性能对比图；建场景化组件库，让 AI 像搭积木一样选控件生成 UI。
  • 多模态输入：语音、截图降低表达门槛，补充细节。
  • 自适应界面：用前端结构化窗口维护意图版本状态，按澄清状态和风险调整界面（弹确认、展示证据）。

8.1　介入时机：62% 的出处

Kuo、Sergeyuk、Chen、Izadi，IUI 2026。15 位开发者在生产级 IDE 中使用主动式 AI 助手五天，分析了 229 次 AI 介入、5,732 个交互点。✅ arXiv 2601.10253 摘要

同方向：Pu 等人（CHI 2025）的 Codellaborator 做了被试内研究（N=18），发现主动 Agent 比只靠提示更高效，但带来工作流打断；“在场提示”和交互上下文能缓解打断。✅ arXiv 2502.18658 摘要 检索摘要另给出 398 次主动介入中 212 次（53.3%）带来有效互动。⚠️ 单一来源

Chen 等人（CHI 2025）的随机实验发现主动式编程助手对效率和体验有显著好处，并指出影响其使用效果的若干细节。✅ arXiv 2410.04596 摘要

对课题：三项研究一致指向“把介入锚定在任务边界上”。会议的“风险 × 用户状态”可以作为边界之上的第二层判断。

8.2　意图形式化：会议缺口 1 的同名研究

微软研究院 Lahiri（2026-03）把“意图形式化”——把非形式化意图翻译成可检查的形式化规约——称为 AI 编程时代决定软件“更可靠还是只是更多”的关键挑战。核心瓶颈是验证规约本身：除了用户，没有判定规约正确的“神谕”，需要轻量交互和测试这类代理产物。文章给出一个按可靠性需求递进的谱系：用轻量测试排除误解 → 完整功能规约与形式验证 → 用领域专用语言直接合成正确代码。✅ arXiv 2603.17150 摘要

早期实现 TiCoder：AI 生成测试让用户确认意图，用 1 到 5 次模拟用户查询，pass@1 准确率在 MBPP 上绝对提升 22.49%–37.71%，在 HumanEval 上提升 24.79%–53.98%。✅ arXiv 2208.05950 摘要（当前版本） 早前检索摘要中“平均 1.5–1.7 次交互即可找到符合意图的测试”的说法来自旧版本，本轮未核到，不再引用。

意图漂移评测：INTENTFLUX 把漂移定义为“已被取代的意图仍影响最终答案或工具调用”，报告代码类任务表现明显下降；Drift-Bench++ 评测意图变化与误沟通下的交互对齐。⚠️ 单一来源，只读到检索摘要

对课题：缺口 1 的“结构化意图字段”可借用 Lahiri 的谱系，按风险选形式化的重量；“与华为专家对齐”本质上是在做规约验证。

8.3　信任校准

  • 经典定义（Lee 和 See）：合适的信任即信任等于系统的实际可信度。🔍 多篇论文引用一致
  • “When Help Hurts”（ACM）：解释或置信度不能稳定带来合适依赖，有时加重过度依赖；“信任冲击”后可能出现过度或不足依赖。⚠️
  • TU/e 研究：问卷报告的信任与实际编码行为脱节，经验水平影响信任。⚠️
  • KTH 研究：把验证行为当作信任校准的可观察机制。⚠️
  • 多篇研究提到信任随任务复杂度和风险变化，支持“按情境定信任标准”。🔍

对课题：问卷适合测态度和场景偏好；信任本身用会议自己提到的委派频率、干预次数、验证行为来测更可靠。

8.4　生成式 UI

  • Chen 等人（2025）：生成式界面相对对话式界面，人类偏好最多高出 72%。✅ arXiv 2508.19227 摘要 分领域差异（数据分析约 93.8%，理论解释约 50%）⚠️ 二手综述页
  • Google Research（2026）：生成式 UI 相对 markdown 和纯文本被压倒性偏好，并把“从固定组件库选控件填内容”单独称为 Templated UI。⚠️ 检索摘要
  • GenerativeGUI（CHI 2025 EA）：生成界面相对纯文本对话降低认知负荷。⚠️ 检索摘要

对课题：会议的“场景化组件库”就是 Templated UI 路线，取舍见下面的成本与收益。

十一、例外与边界

  • 小改动（几行）里 T读懂 本来就小，三个瓶颈都不明显。框架适用于 Agent 一次产出较多代码或长时间自主执行的场景。
  • “验证杠杆最大”在高风险领域可能不成立：医保、金融这类任务，即使验证很便宜，也可能出于合规必须人工逐项审，信任和权限边界才是主约束。第七、八章会议讨论的“按情境定信任标准”正好对应这个例外。
  • 资深开发者和新手的 T读懂 差距很大，同一项措施的净效果可能相反。
  • 纯后端逻辑、脚本、配置没有可指点的界面，“指出来”退化成选中代码行，“挑”和“调”的收益也小。这类任务还是要靠文字和测试用例表达意图。
  • 资深开发者可能更愿意自己写清楚，不想从选项里挑；挑选更适合方向不明确的探索阶段。
  • 五个字段是为 UI 类需求设计的。对架构类决策，“理由”和“边界”的权重会远大于前三个。
  • Kuo 等人的研究对象是“代码质量建议”这一种主动功能，15 人、5 天。结论能否推到 Agent 长任务中的打断，需要验证。
  • “意图明确度 × 风险”的矩阵假设两个维度独立；实际上高风险任务往往意图也更难说清，两者可能相关。
  • “行业规范”的目标与“动态信任”有张力：规范要稳定，动态信任要随人随情境变。

附录 A　Claude Code 的 /loop

/loop 是 Claude Code 内置的 skill，让同一条提示词在会话开着时按间隔重复执行，把“人隔几分钟切回来看一眼”交给 Agent。它是“给注意力做预算”的一个现成实现。

写法行为证据
/loop 5m check the deploy固定间隔，每 5 分钟跑一次；单位 m / h / d🔍 官方文档经检索摘要
/loop check the deploy不写间隔，由 Claude 每轮决定下次何时再看🔍
/loop运行内置维护提示词；有 loop.md 时运行它（项目级 .claude/loop.md 优先，其次 ~/.claude/loop.md）🔍
/loop 20m /review-pr 1234提示词可以是另一个命令🔍

运行规则

  • 只在会话开着且空闲时触发，到点时正忙则空闲后只补跑一次。🔍
  • 7 天过期：循环任务创建 7 天后最后跑一次，然后删除自己。较早的第三方文章写 3 天，已过时。✅ 官方文档“seven-day expiry”段
  • 停止方式分两种：Claude 自定间隔的循环，在空输入框按 Esc 即停；固定间隔的循环（如 /loop 5m），Esc 和 Ctrl+C 停不了，要让 Claude 取消。✅ 官方文档“Stop a loop”段
  • 有抖动：最多为周期的 10%，上限 15 分钟。🔍
  • 要跨重启长期运行就换工具：桌面端定时任务（macOS、Windows），或云端 Routines（/schedule）。🔍

放进三个瓶颈看

注意力：轮询交给 Agent，“空闲才触发、错过只补一次”是在避免它反过来打断人。验证：人不盯着，每轮产出就更需要“结论 + 依据”的形态。信任：无人值守本身是一种授权，7 天过期和固定间隔需显式取消，都是在给放手划边界。开发者敢不敢开 /loop、开多久，可以当作信任程度的行为信号。🔸 推断
