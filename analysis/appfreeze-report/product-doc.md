> 输入：两份低保真 HTML 报告（同一次冻屏、同一份 faultlog，不同输入条件下由 DevEco Code DFX 故障分析生成）

## 技术栈概览

低保真是一份单文件静态 HTML：GitHub Markdown 风格样式（`#1f2328` 正文 / `#f6f8fa` 底 / `#0969da` 强调）、`max-width:960px` 单栏长页、仅浅色（`color-scheme: light`）、零 JS、零可交互元素。内容由 Agent 的 Markdown 输出渲染而来（两个 `<h1>`、表格、`<pre>` 原始日志、diff 着色 class `diff-ins/diff-del`）。
同仓已有兄弟需求 **22 冷启动分析报告**（`demos/22-coldstart-report/`），它跑在 DevEco Studio 编辑区标签页里、用 `deveco-intui-kit` token，有总分、瀑布、根因卡、代码分屏——冻屏报告的目标形态应与它同构。

## 功能定义〔综合 B·U〕

**一句话**：给鸿蒙应用开发者的冻屏（AppFreeze）诊断报告——**先给判决（是什么、在哪、怎么改），再给可核验的卷宗**，并把「改→验」接回 IDE。

核心功能：
1. 结论卡：一句话根因 + 三级根因路径 + 责任领域 + 证据强度（定性 / 定位 / 修复三轴）
2. 主线程时间线：用户操作、任务执行、3S/6S 检测点、队列堆积画在同一时间轴
3. 证据检查清单：8 项检查每项一行状态（✓ 通过 / ✗ 排除 / — 缺数据），展开看解读与原始日志
4. 源码定位：`文件:行号` 可跳转，故障版本与工作区版本差异显式提示
5. 修复建议：按精度分级（精确补丁 / 通用方向），可复制、可应用、可验证
6. 精度升级：源码不可达时说明损失了什么，给出「允许读取源码并重新定位」入口

## 使用场景〔承接 U·P〕

1. **本地复现，源码可达（V2）**：开发者小林在模拟器上点了两次「保存笔记」，应用卡死。DevEco Code 生成报告，他打开标签页——首屏就看到「hasAttachment() 误判 + 主线程同步忙等 8×500ms」和 3 处文件行号；点 `FreezeNoteDetailPage.ets:48` 右侧分屏出代码，点「应用补丁」，再点「复现验证」，时间线上 6S 标记消失。
2. **只有 faultlog，源码不可达（V1）**：QA 从测试机拉回 faultlog 交给外包同学分析，未授权读工程源码。报告给出「saveNoteSync 同步流水线」的业务函数级定位，并**明确标注**「修复建议为通用方向，未经源码核实」；同学看到「建议 2 可能已存在」的提示，选择「授权读取源码重新定位」，而不是直接照抄模板。
3. **专家复核**：稳定性工程师老周收到转发，直接看证据清单：整机 ✓、时间差 ✓、队列 ✗ 阻塞、堆栈=繁忙、专项排除 7 项全 ✗，三级根因标「默认匹配（无采样栈）」——他据此判断三级根因需补采样栈，一分钟给出复核意见。
4. **分派**：TL 看结论卡的「责任领域：应用」与一句话结论，复制分享链接派给页面 owner。

## 核心操作流程

1. **读判决**（必须先）：结论卡 → 证据强度 → 责任领域
2. **看因果**（可选，推荐）：时间线，理解「为什么是 6S 而不是 3S」
3. **定位**（依赖 1）：点文件行号 → 分屏看代码；若源码不可达 → 升级入口
4. **修复**（依赖 3）：审 diff → 复制或应用
5. **验证**（依赖 4）：复现同场景 → 前后对比 → 提交
6. **复核**（任意时刻，专家路径）：证据清单逐项展开 → 原始日志

顺序约束：4 依赖 3 的定位精度——**源码不可达时不应提供「应用补丁」，只提供「复制方向」**。

## 数据结构概览（报告数据契约，Demo Mock 用）

```ts
interface FreezeReport {
  meta: { generatedAt: string; faultType: 'THREAD_BLOCK_3S'|'THREAD_BLOCK_6S'|...; pid: number; bundle: string;
          foreground: boolean; page: string; buildCommit?: string; workspaceDirty?: boolean };
  verdict: { summary: string; domain: '应用'|'系统'|'三方库'; rootCausePath: [string, string, string];
             thirdLevelBasis: 'sampled'|'default'; threadState: 'busy'|'blocked' };
  strength: { qualitative: 'high'|'medium'|'low';            // 定性：根因类别
              location: 'line'|'function'|'module'|'none';    // 定位：粒度
              fix: 'patch'|'direction'|'none' };               // 修复：精度
  sourceAccess: 'granted'|'denied'|'unavailable';
  timeline: { t: string; lane: 'input'|'main'|'watchdog'|'queue'; kind: string; label: string; durMs?: number }[];
  checks: { id: string; title: string; status: 'pass'|'excluded'|'hit'|'missing'; oneLine: string; rawLog?: string }[];
  locations: { file: string; line: string; role: string; commit?: string }[];
  fixes: { id: string; title: string; precision: 'patch'|'direction'; diff?: string; caveat?: string }[];
}
```

魔法值 / 枚举映射（UI 层必须转换）：
- `app_freeze` → 「应用冻屏」；`full` → 「日志完整」；`high` → 「高」（且拆成三轴）
- `state=R` → 「运行中（繁忙）」；`state=S` → 「睡眠等待（空闲）」
- `utime=564, clk=100` → 「用户态 CPU 5.64s」；两次差值 → 「3s 内占用 98%」
- `Not mapped` → 「解释器帧，无法回溯（正常现象）」
- 时间统一为 `HH:mm:ss.SSS`，日期只在头部出现一次

#### 特殊技术概念说明（四步法摘要，详见报告 concept 页）

- **THREAD_BLOCK_3S / 6S**：①看门狗对主线程的两级检测 ②先告警留证据、再上报定案 ③主线程连续 3s 无响应抓一次栈，6s 再抓一次并上报 ④UI 要把两个检测点画在时间线上，让人看懂「为什么是两次点击叠加才到 6S」
- **繁忙 vs 阻塞**：①主线程卡住有两种：在干活（R）和在等人（S）②修法完全不同：繁忙→把活挪走；阻塞→找它等的那个人 ③判据：state、CPU 占用、两次栈顶是否不同 ④UI 用一张「判据 → 结论」小表替代 200 字排除散文

### 专利潜力评估
- 差异化组合：**「证据强度三轴分级」×「源码授权前后的精度升级交互」×「冻屏时间线上叠加修复前后复现对比」**
- 行业先例：单项均有（AI 根因、栈跳代码、hang 统计），**组合未见**【推断·待确认（竞品仅查公开文档）】
- 评级：**中**（组合新颖，单项不稀缺）
- 用户交互角度描述：「用户在未授权读取源码时看到的是方向性建议与明确的精度标注；授权后同一份报告就地升级为逐行定位与可应用补丁，并能在同一时间线上对比修复前后是否再次卡死」

## 设计注意事项

- **不能把 V1 的通用建议渲染得和 V2 的精确补丁一样可信**：视觉权重、按钮能力都要不同（通用方向不给「应用补丁」）。
- **报错与危险提示不压缩**：「未经源码核实」「故障版本 ≠ 工作区」这类提示在结论先行里也必须完整显示（【输入】条目 08 原则：报错、安全警告永远完整显示）。
- **原始日志必须可原样复制**：当前把 `← 解读` 写进 `<pre>`，复制出去就污染了日志；解读与原文分开。
- **合法的「无」不是错误**：「无采样栈」「binder 调用 0 条」是有效结论（排除项），不是缺数据，要与「数据缺失」分色。
- **时间线的时间基准**：faultlog 有 3 种时间来源（故障时间、抓栈时间、上报时间），统一到同一时钟并标注来源，否则画出来会错位。
- **深色主题**：IDE 默认深色，报告当前只有浅色；嵌入编辑区必须跟随 IDE 主题。
- **两版共用一个模板**：差异只由 `sourceAccess` 与 `strength` 字段驱动，不做两套页面。
