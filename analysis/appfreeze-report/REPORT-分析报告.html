Pain Points · 痛点分析

六个痛点，按最频 × 最痛排

5.6–6.2屏

P1 答案埋在卷宗末尾

修复建议在页深 70%（V2 y=5022）/ 84%（V1 y=5542）。首屏只有 250 字诊断散文。

痛点核心：报告按 Agent 的推理顺序写，不按读者的决策顺序写。
51–68%

P2 证据链全量平铺

8 节证据默认全展开，10 段原始日志 60–82 行；术语（Jeqz、utime、VIP 队列）不解释。

痛点核心：给专家的卷宗挡在了开发者前面。
8个时间戳

P3 因果只能读日志

两次点击 → 两轮 4.0s → 3S → 6S 的关系，只存在于 21 行 hilog 与两段散文，读者自己做减法。

痛点核心：最该被画出来的东西没被画出来。
HIGH= HIGH

P4 置信度不分证据强度（最痛）

V1 未读源码，定位只到函数，建议 2 已存在且无效；却与 V2 同标 HIGH。

痛点核心：结论对 ≠ 定位准 ≠ 修复准，一个数掩盖了三件事。
0个交互

P5 报告是终点

7 处行号不能点，3 处 diff 不能用；「验证冻屏不再复现后提交即可」没有入口。

痛点核心：任务在代码里继续，报告停在了文字里。
4种时间格式

P6 格式与口径不一

两个 H1；「置信度 high」与「可信度 HIGH」；V1「9 步 × 0.5s = 4.0s」自相矛盾。

痛点核心：小瑕疵直接折损专家对结论的信任。

Glossary · 术语表

给第一次读冻屏报告的设计师和开发

术语人话
AppFreeze应用冻屏：应用界面长时间不响应，被系统判定为故障
THREAD_BLOCK_3S / 6S看门狗对主线程的两级检测：3s 告警并抓栈，6s 再抓栈并上报定案
主线程处理点击、绘制界面的那条线程；它一忙，界面就卡
EventHandler 队列主线程的待办清单；卡住时越积越多（本次 62→115）
MMITask一次触摸 / 按键输入的分发任务
VIP 队列最高优先级待办（输入、vSync），本次积压 105 个
state=R / SR：正在跑（繁忙）；S：在睡觉等别人（阻塞或空闲）
utime · clk=100用户态 CPU 时间，单位 1/100 秒；564→859 即 3s 里用了 2.95s
术语人话
stub.an · 字节码桩ArkTS 解释器执行一条指令的入口；栈顶是它说明在跑应用 ArkTS 代码
Jeqz / Ldobjbyname「为零则跳转」（循环判定）/「按名取属性」（如 Date.now）
Not mapped解释器帧无法回溯到符号，正常现象，不是错误
hilog · A00000应用自己打的日志；域 A00000 表示应用域，V1 靠它定位到业务函数
Binder / FFRT / libuv跨进程通信 / 并发任务框架 / 异步 IO 库——本次都被排除
采样栈卡顿期间多次抓栈统计热点；缺它时三级根因只能「默认匹配」
TaskPoolArkTS 把计算挪到后台线程的机制，冻屏的常见修法
BuildID · 符号解析把 so 里的地址还原成函数与行号的前提；本次栈里没有应用 so 帧
