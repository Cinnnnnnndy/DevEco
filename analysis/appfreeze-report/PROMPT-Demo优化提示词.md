## 设计角色与领域上下文

你是一位做**开发者平台故障诊断页**的 UI 设计师，熟悉华为开发者联盟官网的视觉语言、Android Studio App Quality Insights、Sentry Issue 详情页。

- **产品**：DevEco Code 的 DFX 故障分析报告 · 应用冻屏（AppFreeze）。Agent 读 faultlog + hilog（+ 可选工程源码）后生成本报告。
- **承载形态**：DevEco Code 故障分析的独立报告页，视觉按鸿蒙开发者官网（文档中心形态：顶部导航 + 左侧目录 + 正文），浅色。
- **目标用户**（服务对象标签在 §C 中引用）：
  - 〔应用开发者〕ArkTS 应用层，懂页面与业务代码，**不懂** EventHandler / 字节码桩 / Binder。要的是「改哪行、怎么改、改完好没好」。
  - 〔DFX 专家〕复核 AI 结论，要证据清单与原始日志锚点。
  - 〔QA/TL〕转发分派，要一句话结论与责任领域。
- **核心原则**：**先给判决，再给卷宗**。当前低保真按 Agent 的推理顺序排版（证据在前、结论在后），要改成读者的决策顺序。

## §A 设计系统（可插拔槽位——官网令牌）

**设计系统 = 华为开发者联盟官网令牌**（参照 developer.huawei.com/consumer/cn/develop/、/deveco-studio/、/doc/；令牌与 `deck-blueprint-style` 同一套）。报告做成官网文档中心形态的独立页面：顶部全局导航 64px、左侧目录 248px（`--panel` 底）、正文两栏；不再套 IDE 外壳。

| Token | 值 | 用途 |
|---|---|---|
| `--paper` / `--panel` / `--card` | `#FFFFFF` / `#F1F3F5` / `#F4F6F7` | 页面 / 侧栏 / 卡片——**分层只靠换填充色** |
| `--ink` … `--ink4` | `#141414` `#4D4D4D` `#7A7A7A` `#A3A3A3` | 正文四级灰 |
| `--accent` / `--soft` | `#0A59F7` / `#E6EEFE` | 唯一点缀色：主按钮、链接、选中、信息横幅 |
| `--yes` / `--part` / `--no` | `#237A45` / `#8F5A00` / `#C4322A` | 三个状态色：通过·已验证 / 未核实·缺数据 / 故障·命中；各配一个浅底 |
| `--line` | `#E8E8E8` | 只用于表格分隔与顶栏底线 |

硬规则：
1. 一个点缀色（系统蓝），之外只允许三个状态色；「已排除」用灰。
2. **无边框、无阴影**：要分层就换填充色（paper / card / panel / soft）。
3. 标题一律不加粗（`font-weight:400`），靠字号分层：H1 24px、区块标题 18px、结论 19px。
4. 不用 emoji，图标一律线性 SVG；品牌位用 30px 蓝色渐变瓦片 + 6px 白细格。
5. 按钮是胶囊：主操作 `--accent` 实底白字，次操作 `--soft` 底蓝字，第三级 `--panel` 底。
6. 图表容器（时间线）用蓝图层：20px 单层格（系统蓝 5%）+ 四角 13px 制图角标；普通卡片不加。
7. 字体回落链：`HarmonyOS Sans SC, PingFang SC, Microsoft YaHei, Noto Sans CJK SC`；代码与时间戳用等宽。
8. **单文件交付**：CSS/JS 全部内联，`grep -c 'rel="stylesheet"'` 必须为 0。

> 换设计系统只改本节，§B–§F 的能力规格与视觉无关。原先的 `deveco-intui-kit` 方案适用于把报告嵌进 IDE 编辑区的形态；本轮按官网形态出，「行号 → 编辑区分屏」相应改成「行号 → 右侧代码面板」。

## §C 问题 → 目标状态映射

**B1 首屏无判决**
- 目标：报告头之后第一块是**结论卡**（`--card` 底、无边框、12px 圆角，padding 16px 20px），自上而下：
  1. 一句话结论（19px，400）：「保存笔记时主线程同步忙等 8 × 500ms，两次点击叠加阻塞约 8s」（V1：「保存笔记时主线程同步执行 saveNoteSync 流水线，两次点击叠加阻塞约 8s」）
  2. 三级根因路径：`主线程卡死超时 › 主线程繁忙 › 执行耗时操作`，第三级后挂 `--part` 浅底 pill「默认匹配 · 无采样栈」
  3. 4 条编号要点（见 B2）
  4. 底行：主按钮「查看修复（3）」+「因果链 6 步」+ 右对齐元信息「责任领域 应用 · 页面 FreezeNoteDetailPage · 主线程连续占用 约 8s」
- 首屏（1440×900）必须同时可见：结论卡 + 证据强度 + 时间线。〔应用开发者·首次打开 30 秒〕

**B2 散文堆叠**
- 目标：诊断拆成**编号要点行**，每行一个事实，行尾是定位链接（等宽 12.5px，`--accent`）：「`hasAttachment()` 把已有封面图当作待保存附件 · FreezeNoteDetailPage.ets:48」；落在时间线上的事实给「看时间线」。
- 排除项改为 **7 个胶囊**：`等锁` `Binder` `阻塞 IO` `FFRT` `libuv` `FullGC` `HeapDump`，每个带 ✕ 线性图标 +「已排除」，hover 显示判据；上面配一张「繁忙 vs 阻塞」四行判据表，命中列用 `--no`。〔DFX 专家·复核〕

**B3 单栏孤岛**
- 目标：正文 ≥1200px 两栏——左 58%：结论卡 → 时间线 → 因果链 → 修复；右 42%：证据强度 → 证据清单 → 排除项与判据 → 线程快照。<1200px 单栏同顺序；<900px 隐藏左侧目录。
- 点任一行号：右侧滑出**代码面板**（宽 min(760px, 56vw)，遮罩压暗正文），顶部是完整路径 + 「故障版本 4ca0c7e」，三文件标签可切；命中行 `--no-soft` 整行底 + 左侧 3px `--no` 色条 + 进场闪一下，关联行用 `--part-soft`；右上浮胶囊「对应根因 ① · hasAttachment 误判」；底栏写行号的含义。`Esc` 关闭。〔应用开发者·定位〕

**B4 因果只在日志里**
- 目标：**主线程时间线**（内联 SVG，宽随容器），放在蓝图层图表容器里；横轴 11:15:02 → 11:15:11，四条泳道：
  - 点击：两个 `--accent` 圆点（02.631、03.418），第 2 个拉一条虚线到它真正被分发的 06.639，标「排队 3.2s」
  - 主线程：两轮各 8 段（每段对应一步 hilog，约 500ms），`#F3E3C6` 底；第 2 轮超过 3s 的段用 `--no-soft`；6S 上报之后仍在执行的部分用 `--no` 虚线框
  - 看门狗：竖线 `3S 告警 07.142 · 抓栈 Jeqz`（`--part`）、`6S 上报 10.313 · 抓栈 Ldobjbyname`（`--no`）
  - 队列：折线 62 → 115（VIP 52 → 105）
- hover 任一段显示对应 hilog 原文。V1 与 V2 用同一时间线（数据相同）。〔应用开发者·理解为什么是 6S〕

**B5 无状态编码 / 单一置信度**
- 目标：**证据强度三轴**（右栏顶部三块 `--card`）：
  - 定性 · 根因类别：高 ·「state=R，3s 内 CPU 98%，两次栈顶不同」
  - 定位 · 粒度：V2「行级 · 3 个文件、7 处行号」/ V1「函数级 · 来自应用日志」
  - 修复 · 精度：V2「精确补丁 · 3 处，工作区已包含」/ V1「通用方向 · 未经源码核实」
  - 高 / 行级 / 精确用 `--yes`，函数级 / 通用方向用 `--part`；不用红色（红色只给故障本身）。
- 证据清单 9 行（原 8 节 + 采样栈），每行：状态圆标 + 标题 + 一行结论 + 状态胶囊 + 展开箭头。四种状态：命中 `--no`、通过 `--yes`、已排除 灰、缺数据 `--part`。标题右侧摘要：V2「3 命中 · 2 通过 · 3 排除 · 1 缺数据」，V1「2 命中 · 2 通过 · 3 排除 · 2 缺数据」。〔DFX 专家·一分钟复核〕

**B6 证据全展开**
- 目标：证据清单默认折叠，只展开「任务队列」一项。展开后两层：解读要点（堆栈项用「帧号 → 人话」对照表）→「原始日志」再次折叠（等宽、`--paper` 底、自动换行、右上「复制原文」）。〔应用开发者 / DFX 专家〕

**B7 源码不可达无降级**
- 目标（V1 状态）：报告头下方一条 `--part-soft` 横幅（不可关闭，属于「警告永不压缩」）：「**未读取工程源码：**定位只到业务函数（来自应用日志），修复为通用方向，可能与现有代码重复。」右侧主按钮「允许读取源码并重新定位」。
- V1 修复卡：编号圆标用 `--part`，标「通用方向」胶囊；代码块按普通示例代码显示（不画成 diff）；只有「复制示例代码」，**不提供「应用补丁」**，旁边给链接「读取源码，换成精确补丁」；建议 2 下方一行 `--part` 提示：「页面可能已经有保存中禁用逻辑；主线程被阻塞时它不会重渲染，拦不住第 2 次点击——先完成上一条。」
- 点「允许读取源码并重新定位」→ 结论卡内 3 步进度（读取工程 → 版本比对 · 4ca0c7e → 重新定位）→ 同一页面就地升级为 V2 状态。〔外包/QA 场景·源码不可达〕

**B8 零交互**
- 目标：每个 `文件:行号` 是 `--accent` 链接 → 代码面板（见 B3）。
- V2 修复卡：编号圆标 + 标题 + 行号链接 + diff（增删行 `--yes-soft` / `--no-soft` 底，行号列 + ± 列）+ 为什么这样改一句话。工作区已含该改动时标「已在工作区 · 未提交」，按钮「查看代码」「复制 diff」；未含时主按钮为「应用补丁」。
- 修复区底部「复现验证」横幅（`--soft` 底）：点后按钮变进度（安装构建 → 连点两次保存 → 采集），完成后时间线叠加一条「修复后」泳道（`--yes`），横幅变 `--yes-soft`「已验证不再复现：主线程最长任务 4.0s → 14ms，未再触发 3S / 6S」。V1 状态下该按钮禁用，说明「先读取源码、拿到精确补丁」。〔应用开发者·改完好没好〕

**B9 机器枚举**
- 目标：去掉「分诊结论 / 输入完整度 / 置信度」文本行，改为报告头上的胶囊：`应用冻屏 · THREAD_BLOCK_6S`（`--no` 浅底）`日志完整` `已读取工程源码 / 未读取工程源码`；包名、设备、时间放 H1 下的元信息行（`--ink3`）。全页只用「置信度」一个概念，并按 B5 拆轴。

**B10 时间格式**
- 目标：日期只在元信息行出现一次（`2026-06-05`）；正文时间统一 `HH:mm:ss.SSS`，等宽。

**B11 重复 H1 与结论**
- 目标：只有一个 H1（24px，400）；「根本原因」变成可折叠的「因果链」有序列表（V2 6 步 / V1 5 步）；「根因模块」并入结论卡元信息与行号链接。

**B12 数字与模板矛盾**
- 目标：V1 写「8 步、每步约 500ms，单轮约 4.0s」；修复区副标题随状态变化（V2「精确补丁 · 按行号定位」/ V1「通用方向 · 未经源码核实」）。

**B13 空态**
- 目标：「采样栈」并入证据清单为「缺数据」一行：「未包含采样栈 → 三级根因按规则默认匹配」，展开说明判定规则与开启方式（顶部导航「采集设置」）。〔DFX 专家〕

**B14 版本差异**
- 目标（V2 状态）：报告头下方 `--soft` 横幅：「行号基于故障版本 `4ca0c7e`（06-05 10:31）· 工作区已修改 2 个文件，未提交」+ 次按钮「对比工作区」（代码面板里列出 3 处改动）。

**B15 原文污染**
- 目标：原始日志只放原文；逐帧解读放在日志上方的「帧号 → 人话」对照表。

**B16 主题**
- 目标：本轮按官网形态出浅色页，全部走 §A token；嵌入 IDE 编辑区时再按 IDE 主题做深色。

**B17 可访问性**

## §D 跨视图一致性约束

- V1 / V2 是**同一个模板的两种状态**，只由 `sourceAccess` 与 `strength` 驱动差异，布局不变。
- 与 `22-coldstart-report` 在信息结构上一致：结论先行、根因编号 ①②③、行号可跳代码、命中行染色与浮标；视觉按 §A 官网令牌。
- 红色只表示「故障 / 命中」；「未核实 / 缺数据」用 `--part`；「已排除」用灰。
- 所有代码、时间、线程号、地址用等宽字体。

## §E 视图设计要求

## §F 状态覆盖

| 状态 | 触发 | 视觉表现 |
|---|---|---|
| 空（无故障） | 未选择 faultlog | 「选择一条冻屏记录开始分析」+ 拖放区 +「从设备拉取」+ 两张示例卡（本次两份数据），左侧目录收起报告区块 |
| 分析中 | 点示例卡 | 证据清单 9 行依次点亮后恢复默认展开状态 |
| 源码可达（V2） | `sourceAccess=granted` | 三轴：高 / 行级 / 精确补丁；版本横幅；修复卡带 diff |
| 源码不可达（V1） | `sourceAccess=denied` | 警告横幅 + 升级按钮；三轴：高 / 函数级 / 通用方向；修复卡只能复制；复现验证禁用 |
| 升级中 | 点「允许读取源码」 | 结论卡内 3 步进度，其余区域保持可读，完成后就地变 V2 |
| 缺数据 | 无采样栈 / 源码未读 | 证据行 `--part` + 说明影响；**「binder 调用 0 条」属于已排除，不是缺数据** |
| 验证中 | 点「复现验证」 | 横幅文字按步骤推进，按钮禁用 |
| 验证通过 | 未再触发 3S / 6S | 时间线多一条「修复后」泳道，横幅变绿并给出前后对比数字 |
| 验证失败 | 仍触发 | 新泳道上标出 3S / 6S，提示「补丁未解决」（本轮 Demo 未做） |
