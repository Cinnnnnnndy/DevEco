# AppFreeze 冻屏分析报告 · UI 设计优化简报（Demo 优化提示词）

> 模式：**优化模式**（有现存 UI：两份低保真 HTML 报告 → 一个模板承载两种输入条件的高保真 Demo）
> 输入：`input/v1-源码不可达-210435.html`、`input/v2-源码可达-220705.html`
> 产出：`optimized-demo/index.html`——单文件、可双击打开、**CSS/JS 全部内联、零外链**；一个页面内可切换「源码可达 / 源码不可达」两种状态
> 问题编号 B1–B17 与可视化报告 critique 页同源，数字均为实测值（Chromium 无头，视口 1440×900）

---

## 设计角色与领域上下文

你是一位做 **IDE 内故障诊断工具**的 UI 设计师，熟悉 JetBrains Int UI、Android Studio App Quality Insights、Sentry Issue 详情页。

- **产品**：DevEco Code 的 DFX 故障分析报告 · 应用冻屏（AppFreeze）。Agent 读 faultlog + hilog（+ 可选工程源码）后生成本报告。
- **承载形态**：DevEco Studio 编辑区里的一个标签页（与同仓 `demos/22-coldstart-report` 同构），默认**深色**，可切浅色。
- **目标用户**（服务对象标签在 §C 中引用）：
  - 〔应用开发者〕ArkTS 应用层，懂页面与业务代码，**不懂** EventHandler / 字节码桩 / Binder。要的是「改哪行、怎么改、改完好没好」。
  - 〔DFX 专家〕复核 AI 结论，要证据清单与原始日志锚点。
  - 〔QA/TL〕转发分派，要一句话结论与责任领域。
- **核心原则**：**先给判决，再给卷宗**。当前低保真按 Agent 的推理顺序排版（证据在前、结论在后），要改成读者的决策顺序。

## §A 设计系统（可插拔槽位——A-1 委托模式）

**设计系统 = `deveco-intui-kit`（本仓库）。** 生成前先读：
- `deveco-intui-kit/README.md`、`deveco-intui-kit/docs/index.html`（规范页）
- `deveco-intui-kit/src/tokens.css`（`--ui-*` 语义色、`--fs-*` / `--lh-*` 字阶、`--font-ui` / `--font-code`、`--arc`）
- `deveco-intui-kit/src/components.css`、`demos/_shared/frame.css`（`.dm-pill` `.dm-kv` `.dm-seg` `.dm-group` `.dm-list` `.dm-score` `.btn` 等）
- **参照实现**：`demos/22-coldstart-report/index.html`（报告工具栏、总分环、根因卡、点行号→编辑区左右分屏、代码命中行染色与「对应左侧根因 ①」浮标）

规则：
1. 颜色只用 `--ui-*` 语义变量（`--ui-error` / `--ui-warning` / `--ui-success` / `--ui-accent` / `--ui-fg-info` / `--ui-field-bg` / `--ui-border`…），**不自创任何 hex**；状态底色用 `color-mix(in srgb, var(--ui-xxx) 18%, transparent)`，与 `.dm-pill.err/.warn/.ok` 同法。
2. 字号只用 `--fs-*`，代码与时间戳一律 `--font-code`。
3. IDE 外壳保持英文，报告面板用中文；图标用 kit 的 `#i-*` 雪碧图，**不用 emoji**。
4. 深 / 浅主题跟随 `.ide[data-ide-theme]`，改面板宽度写 `.ide[data-ide-theme]{--xxx:…}`。
5. **单文件交付**：把 `tokens.css`、`components.css`、`frame.css`、`icons.js`、`frame.js` 逐字内联（做法同 `deveco-intui-kit/dist/coldstart-report.html`；内联 JS 时把源码里字面出现的 `</script` 转义），不得出现 `<link rel="stylesheet">`。

> 换设计系统只改本节，§B–§F 的能力规格与视觉无关。

## §C 问题 → 目标状态映射

**B1 首屏无判决**
- 目标：报告顶部是**结论卡**（`--ui-field-bg` 底、1px `--ui-border`、`--arc` 圆角，padding 14px 16px），自上而下：
  1. 一行标题（`--fs-h2`，600）：「保存笔记时主线程同步忙等 8×500ms，两次点击叠加阻塞约 8s」（V1：「保存笔记时主线程同步执行 saveNoteSync 流水线，两次点击叠加阻塞约 8s」）
  2. 三级根因面包屑：`主线程卡死超时 › 主线程繁忙 › 执行耗时操作`，第三级后挂 `.dm-pill.muted`「默认匹配 · 无采样栈」
  3. `.dm-kv` 四行：责任领域「应用」· 故障类型「THREAD_BLOCK_6S」· 页面「FreezeNoteDetailPage」· 发生「11:15:10.313」
  4. 右侧主按钮「查看修复（3）」锚到修复区；次按钮「复制结论」
- 首屏（900px）必须同时可见：结论卡 + 证据强度 + 时间线。〔应用开发者·首次打开 30 秒〕

**B2 散文堆叠**
- 目标：诊断拆成**要点行**，每行一个事实，行首图标 + 行尾定位 chip（`--font-code` 11px，`--ui-link`）：「`hasAttachment()` 把已有封面图当作待保存附件 · FreezeNoteDetailPage.ets:48」。
- 排除项改为 **7 个 chip 网格**：`等锁` `Binder` `阻塞 IO` `FFRT` `libuv` `FullGC` `HeapDump`，每个带 ✕ 图标 +「已排除」，hover 显示判据。〔DFX 专家·复核〕

**B3 单栏孤岛**
- 目标：报告区 ≥1200px 宽时两栏——左 58%：结论卡 → 时间线 → 修复；右 42%：证据强度 → 证据清单 → 线程快照。<1200px 单栏同顺序。
- 点任一行号：编辑区左右分屏（左报告、右代码），命中行按严重度整行染色 + 左侧 3px 色条 + 进场闪一下，代码面板右上浮「对应根因 ① · hasAttachment 误判」——**完全沿用 22 冷启动报告的分屏交互**。〔应用开发者·定位〕

**B4 因果只在日志里**
- 目标：**主线程时间线**（SVG，宽度随容器，高 150px），横轴 11:15:02 → 11:15:11，四条泳道：
  - 输入：两个点击点（02.631、03.418），第 2 个点击画一条虚线到它真正被分发的 06.639，标「排队 3.2s」
  - 主线程：两段任务条 `MMITask #1 02.632–06.639 · 4.0s`、`MMITask #2 06.639–(10.313+) · ≥3.7s`，条内用 8 个细分隔表示 8 步 × 500ms；超过 3s 的部分用 `--ui-error` 18% 底
  - 看门狗：竖线标 `3S 告警 07.142`、`6S 上报 10.313`
  - 队列：一条小折线 62 → 115（VIP 52 → 105）
- hover 任一步显示对应 hilog 原文。V1 与 V2 用同一时间线（数据相同）。〔应用开发者·理解为什么是 6S〕

**B5 无状态编码 / 单一置信度**
- 目标：**证据强度三轴**（结论卡下方一行三块）：
  - 定性（根因类别）：高 · 「state=R，3s 内 CPU 98%，两次栈顶不同」
  - 定位（粒度）：V2「行级 · 3 个文件」/ V1「函数级 · 来自 hilog」
  - 修复（精度）：V2「精确补丁 · 3 处」/ V1「通用方向 · 未经源码核实」
  - 用 `.dm-pill.ok / .warn / .muted` 表达高 / 中 / 低，不用红色（红色只给故障本身）。
- 证据清单 8 行，每行：状态图标 + 标题 + 一行结论 + 展开箭头。状态四色：`命中`（`--ui-error`）、`通过`（`--ui-success`）、`已排除`（`--ui-fg-info`，灰）、`缺数据`（`--ui-warning`）。顶部摘要：「8 项检查 · 1 命中 · 2 通过 · 4 排除 · 1 缺数据」。〔DFX 专家·一分钟复核〕

**B6 证据全展开**
- 目标：证据清单默认全部折叠；「命中」项默认展开 1 项。展开后分两层：解读（要点行）→「原始日志」再次折叠（`--font-code`，`--ui-code-bg`，带行号与「复制原文」）。整页首屏证据区不超过 8 行高。〔应用开发者 / DFX 专家〕

**B7 源码不可达无降级**
- 目标（V1 状态）：结论卡顶部一条 `--ui-warning` 18% 底的提示条（不可关闭，属于「警告永不压缩」）：
  「未读取工程源码：定位到业务函数（来自 hilog），修复为通用方向，可能与现有代码重复。」右侧按钮「允许读取源码并重新定位」。
- V1 修复卡：标 `.dm-pill.warn`「通用方向」，只提供「复制示例代码」，**不提供「应用补丁」**；建议 2 下方加一行灰字「若页面已有保存中禁用逻辑，它在主线程阻塞期间不会生效——先完成建议 1」。
- 点「允许读取源码并重新定位」→ 进度态 3 步（读取工程 → 版本比对 → 重新定位）→ 同一页面就地升级为 V2 状态，证据强度三轴动画过渡。〔外包/QA 场景·源码不可达〕

**B8 零交互**
- 目标：每个 `文件:行号` 是链接（`--ui-link`，hover 下划线）→ 分屏跳转（见 B3）。
- V2 每张修复卡：标题 + 改动文件 chip + diff（kit 的代码块样式，增删行用 `--ui-success` / `--ui-error` 14% 底）+ 按钮组「应用补丁」（主）「复制 diff」「在编辑器中查看」。
- 修复区底部「复现验证」按钮：点后进入验证态（见 §F），完成后在**同一时间线**上叠加一条「修复后」主线程泳道，对比最长任务 4.0s → <16ms，6S 标记消失；结论卡加 `.dm-pill.ok`「已验证不再复现」。〔应用开发者·改完好没好〕

**B9 机器枚举**
- 目标：头部去掉「分诊结论/输入完整度/置信度」文本行，改成报告工具栏上的 pill：`应用冻屏` `日志完整` + 右侧设备与包名（`--font-code`，`--ui-fg-info`）。全页只用「置信度」一个词，并按 B5 拆轴。

**B10 时间格式**
- 目标：日期只在工具栏出现一次（`2026-06-05`）；正文所有时间统一 `HH:mm:ss.SSS`，`--font-code`。

**B11 重复 H1 与结论**
- 目标：只有一个标题；「根本原因」合并进结论卡下的「因果链」6 步有序列表（默认折叠为 1 行「展开因果链（6 步）」）；「根因模块」合并进 `.dm-kv` 的责任领域与定位 chip。

**B12 数字与模板矛盾**

## §D 跨视图一致性约束

- V1 / V2 是**同一个模板的两种状态**，只由 `sourceAccess` 与 `strength` 驱动差异，布局不变。
- 与 `22-coldstart-report` 一致：报告工具栏（左 segmented、右设备信息 + 导出）、根因编号 ①②③、行号跳转分屏、代码命中行染色与浮标、`.dm-*` 组件。
- 红色只表示「故障 / 命中」；「未核实 / 缺数据」用警告色；「已排除」用灰。
- 所有代码、时间、线程号、地址用 `--font-code`。

| 缺数据 | 无采样栈 / 无 binder 区段 | 证据行「缺数据」警告色 + 说明影响；**「binder 调用 0 条」属于已排除，不是缺数据** |
| 补丁已应用 | 点「应用补丁」 | 修复卡变 `.dm-pill.ok`「已应用」+「撤销」；Project 树文件标修改 |
| 验证中 | 点「复现验证」 | 时间线右侧出现「修复后」泳道并实时推进；按钮变进度 |
| 验证通过 | 未再触发 3S/6S | 两条泳道对比，结论卡 `已验证不再复现` |
| 验证失败 | 仍触发 | 新泳道上标红的 3S/6S；提示「补丁未解决，查看新报告」 |
| 空（无故障） | 未选择 faultlog | 空态卡：「选择一条 faultlog 或从 FaultLog 面板拖入」+ 两张示例卡（本次两份数据），点击载入 |
