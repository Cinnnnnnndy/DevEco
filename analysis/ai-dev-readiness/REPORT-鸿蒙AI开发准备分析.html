鸿蒙开发者的 AI 开发准备：四类用户要导入什么，鸿蒙要开放什么

在「开发准备 → 编码实现 → 运行验证 → 发布上架」四段里，开发准备这一段决定 AI 后面写得准不准。本文先列出开发准备要交给 AI 的七类东西，再按互联网头部厂商、中型企业、小企业 / 创业团队、个人开发者四类用户，拆开各自已有什么、要导入什么、要平台给什么；然后展开头部厂商的工具链需要鸿蒙以什么形式提供能力（开发、测试、鸿蒙独有能力、上架四段），盘点鸿蒙生态目前已经开放的 Skill、MCP、CLI；最后列出鸿蒙进入 AI 生态需要对齐的公共规范和需要自己定义的 spec。

结论

  1. 开发准备的本质，是把「写给人看的上下文」改成「AI 读得进去的上下文」。要准备的有七类：项目规则、需求与 spec、设计稿与设计系统、已有代码、知识与文档、工具能力（MCP / Skill / CLI）、环境与账号。前五类是用户自己带来的，后两类主要靠平台给。
  2. 四类用户的差别不在「要不要准备」，而在「谁来准备、准备在哪」。个人开发者几乎什么都不带，要平台把知识和规则直接装好；小企业带一点规则和截图；中型企业带规则、分级 spec 和存量工程；头部厂商带的是一整套自研工具链，他们不进我们的 IDE，要的是能插进自己流水线的接口。
  3. 头部厂商要的形式是「无头、可编排、可审计」：CLI 和 MCP 跑在 CI 里，Skill 按开放标准写、能导进他们自己的 Agent，上架和签名有 API。界面对他们是次要的。
  4. 鸿蒙在开发和测试两段已经开放了不少：官方 Skill 仓库按设计、开发、SDK、测试、工具、发布、多设备、质量分了十类，约 70 个 Skill；DevEco CLI 有文档检索、Skill 安装和 MCP 服务；CodeGenie MCP 带模拟器工具组。缺口集中在两头：准备阶段的规则模板、设计稿接入、迁移映射，以及上架阶段的「创建应用」API。
  5. 鸿蒙进入 AI 生态有两个方向，要分开讲：一是让外部 AI 会写鸿蒙（对齐 AGENTS.md、Agent Skills、MCP、llms.txt 这些公共规范）；二是让鸿蒙应用被 AI 调用（HMAF、意图框架、小艺 Skill / MCP、A2A、A2UI）。DevEco 主要承接第一个方向，第二个方向是开发者要接入的能力。
  6. 鸿蒙需要自己定义的 spec 有五个：带 API 版本标注的 ArkTS 规则包、鸿蒙工程的 AGENTS.md 模板、设计稿到 ArkUI / HDS 组件的映射、Android / iOS 到鸿蒙的迁移映射、机器可读的验收与上架体检清单。它们都放在开发准备这一段，DevEco 可以做成「准备度检查」一步到位。

四类用户：已有什么、要导入什么、要平台给什么

访谈样本里中厂 2 份（WPS、格力）、创业团队 4 份、个人 / 学习者 6 份，没有互联网头部厂商。头部厂商这一列用 HDC 2026 公开的快手、抖音案例和中厂访谈往上推，标为推断。

分层依据是工程体系成熟度，不是行业属性。同样是中大型企业，互联网的 WPS 和非互联网的格力在开发准备上要的东西几乎一样，都是分级 spec、规则和存量工程。真正把需求分开的，是有没有自己的 AI 基建、自研 IDE 和 Agent：有的只要接入原子能力，没有的依赖我们的工具。下面四类和汇报里的三类对应关系是：成熟工程体系的大厂 = 互联网头部；有独立团队、依赖我们工具的中大型企业（互联网和非互联网都有）= 中型企业；经验和资源有限的初创与个人 = 小企业 / 创业 + 个人开发者。小企业和个人拆开写，是因为两者在「导入什么」上差别大：前者带截图和自己的 Agent，后者几乎什么都不带。10-29 评审时领导提到的「幺五客户」该归到哪一层，还要确认。待确认

互联网头部厂商

抖音、快手、腾讯视频、京东这类，有自己的 AI 基建团队、自研 IDE 和 Agent
已经有
自研或企业版 Agent / IDE、内部模型或模型网关、CI/CD 流水线、设备农场、自有设计系统、跨端框架（Taro、KMP 等）推断
要导入
企业规则和 spec 流程、私有组件库与接口文档、存量多端代码、自己的测试用例和埋点规范
要平台给
能接进自己 Agent 和 CI 的原子能力，最看重调试和性能分析；形式是无头 CLI、MCP、标准格式 Skill、SDK 与上架签名 API、可在内网部署的知识包
准备期最大卡点
鸿蒙能力不能脱离 DevEco 界面单独调用，进不了他们的 Agent 和 CI
快手构建 Agent Loop 双循环，AI 代码生成率 80%，测试用例直出采纳率 84%；抖音鸿蒙版 AI 智能测试主功能点覆盖率 100%。官方

中型企业

WPS（互联网）、格力（非互联网）这类，有独立的移动端团队，但仍依赖我们的工具和外部 AI 工具
已经有
采购的商用 Agent（Codex、Trae 企业版）或自研（WPS Code 接 GLM）、定制过的 SDD 流程、几十个子模块的存量工程 访谈
要导入
分级 spec（L0 直接改 / L1 完整流程 / L2 先架构设计）、规则文件、存量工程、BDD 自动化用例
要平台给
官方维护的上架 / 批量发布 Skill、安全与质量 review 规则、多端一致的验证能力
准备期最大卡点
规则和流程要自己搭，搭完还要自己维护；30 多个定制应用的创建和重签名靠脚本
「不想自己维护，应该官方给……最大的问题是创建应用这个环节没有 API。」——WPS 移动端负责人 访谈

小企业 / 创业团队

2 到 10 人，产品、设计、开发经常是同一批人
已经有
Claude Code / Codex + 一套开源 Skill（Superpowers）、接国产模型省钱、设计靠 AI 出图或截图 访谈
要导入
截图和风格锚点、HTML 原型、简单的规则（多数用自然语言说，不写成文档）
要平台给
能被他们的 Agent 直接调用的鸿蒙能力（编译、截图、日志、真机），以及知识库
准备期最大卡点
设计稿给不进去；外部 Agent 碰不到模拟器和真机，要自己找第三方 MCP
「截图、编译、调试、各种数据都扔给他，会超出你想象的好用……开放能力就行。」——理性幻想 访谈

个人开发者 / 学习者

学生、副业、跨界做应用的人，很多是第一次写鸿蒙
已经有
一个想法、一个模型账号（常常是便宜的国产模型）、一台电脑，几乎没有规则和 spec 访谈
要导入
一句话需求、几张参考图；导入越少越好
要平台给
开箱即装好的规则、知识和 Skill，一步步的路径，证书和上架的引导
准备期最大卡点
不知道要准备什么；文档版本多，从哪开始不知道；token 贵
「你们现在给的太多太全……我从哪开始看不知道。」——疯狂来电（培训讲师转述学生）访谈

准备物互联网头部 推断中型企业小企业 / 创业个人开发者
1 项目规则 带自己的规则；要鸿蒙规则包能合并进企业规则 自己写，要官方模板减少维护 口头说为主；要默认规则 不会写；要平台默认装好
2 需求与 spec 自有需求系统通过 MCP 接入 分级 spec + 人工审核门槛 自然语言 + plan，不写 spec 一句话需求，要 AI 拆步骤
3 设计稿 自有设计系统和 token，要映射到 ArkUI Figma 打通还在 demo 阶段 截图、风格锚点最常用 参考图；没有 Figma 高级版
4 已有代码 多端存量 + 跨端框架 几十个子模块的存量工程 Flutter / 安卓项目移植 多为新项目
5 知识与文档 要可离线、可内网部署的知识包 官方知识 + 私有组件文档 要 md / MCP，不要网页 要准、要标版本、要有路径
6 工具能力 无头 CLI + MCP 进 CI 上架、批量发布 Skill 编译、截图、真机给外部 Agent 要内置好，不用配置
7 环境与账号 企业证书、权限、审计；批量创建应用 30 多个应用的重签名和上传 证书和公私钥搞不清 证书、AGC 每一步都要引导
  • 越往头部走，用户带来的越多，要平台给的越「底层」：头部要接口，个人要成品。同一份鸿蒙规则包，对个人是默认装好，对头部是可导出、可合并。
  • 设计稿和环境账号是四类人共同的痛点，而且都不靠模型变强能解决，是平台要补的。
  • spec 两极分化：中型企业要分级 spec，创业团队和个人不写 spec。DevEco 不应该强推一套 spec 流程，而是按任务大小分流，并允许企业导入自己的 spec 模板。

互联网头部厂商展开：他们的工具链要鸿蒙以什么形式提供能力

10-29 评审中提到，互联网客户更关注接口、SDK 和全链路服务的接入；大厂要的是接入原子能力、接入 CI，以及调试和性能分析。头部厂商的特点是不换工具链：他们已经有自己的 Agent、模型网关、流水线和设备农场，鸿蒙对他们来说是「多一个目标平台」。所以要回答的问题不是「怎么让他们用 DevEco」，而是「鸿蒙的每一项能力用什么形式交给他们的工具链」。

能力的七种交付形式

形式 1
知识
AI 可读的文档：Markdown、llms.txt、文档检索 MCP、可离线的知识包
形式 2
规则
ArkTS / ArkUI 的规则包，能合并进 AGENTS.md 或企业规则
形式 3
Skill
按 Agent Skills 标准写的 SKILL.md，能导入任何 Agent
形式 4
CLI
无头命令行：构建、签名、装机、截图、日志，能跑在 CI 里
形式 5
MCP
把 CLI 的能力暴露给 Agent，带权限分级和调用记录
形式 6
云端 API
AGC 的创建应用、上传、元数据、审核状态，云测试和设备农场
形式 7
评测与语料
鸿蒙代码评测集、可训练的开源样例，给企业自研模型用

前三种形式回答「AI 知道什么」，第四、五种回答「AI 能做什么」，第六种回答「AI 能把东西交出去」，第七种回答「企业自己的模型能不能学会鸿蒙」。黑马讲师的原话是「国外模型鸿蒙语料不够，训练 GitHub，鸿蒙代码不在 GitHub」。访谈

上架交得出 批量创建应用；签名与重签名；上传测试包和正式包；元数据和截图；上架前预审；审核状态回传 云端 API · CLI · Skill 部分hmos-connect-api-cli-skill（通过 connect-api-cli 操作 AGC）、app-metadata-audit-skill（上架元数据预审）官方 创建应用没有 API（WPS 用 Playwright 绕）访谈；审核反馈不是机器可读的，Agent 没法自己修

头部厂商最在意的四个非功能要求

  • 能脱离界面运行：所有能力要能在没有 DevEco 界面的 Linux 构建机上跑。DevEco CLI 当前要求本机装好 DevEco Studio 6.1.0+，支持 macOS 和 Windows 社区，Linux 构建机能否使用 待确认。
  • 版本可钉住：CodeGenie MCP 的 npm 版本线里，stable 1.1.11 是精简线，没有模拟器工具组，latest 0.2.6 才有 社区。版本线不一致会让企业流水线随时坏掉，要有明确的版本与能力对照。
  • 权限与审计：签名、上传、装正式包这类敏感操作，要能按 Agent 分别授权、留调用记录（项目 23 号「开放 MCP 与 Skill」demo 已经做了按 Agent 授权的审批卡）。
  • 标准格式：Skill 用 Agent Skills 标准、工具用 MCP、规则能合并进 AGENTS.md。头部厂商自研 Agent 不会为鸿蒙单独适配私有格式。

缺口：准备阶段和上架阶段最薄

  1. 没有鸿蒙工程的规则模板。开发者都在自己写「必须 MVVM V2、不能用 router、用 HDS 组件」这类规则，社区各写一套。官方应该出一份带 API 版本标注的规则包，并能一键写进 AGENTS.md / CLAUDE.md / Cursor rules。
  2. 设计稿进不来。只有一个「按设计规范生成页面」的 Skill，没有设计稿或截图到 HDS 组件、设计 token 到 ArkUI 资源的映射。四类用户都有这个需求。
  3. Android 原生到鸿蒙的迁移没有官方 Skill。跨端框架（Taro、uni-app、ArkUI-X）有，但「安卓转鸿蒙」是个人和中厂最常见的起点。
  4. 上架的第一步没有 API。创建应用要手动，审核反馈不是机器可读的，Agent 走不完「从零到上架」。
  5. 版本与能力不对齐。Skill 仓库约 72 个、CLI 内置 44 个、MCP 两条版本线工具数不同，企业很难判断该用哪个。需要一张能力 × 版本 × 交付形式的对照表。
  6. 网页文档对 Agent 不友好。知识已经进了 CLI 和 DevEco Code，但官网文档仍是 AJAX 加载，外部 Agent 直接读网址读不到；对照 Ant Design 已经提供 llms.txt 和逐组件 Markdown 社区。

鸿蒙进入 AI 生态需要哪些 spec

分两类：一类是要对齐的公共规范，鸿蒙不用自己发明，按标准提供就能被所有 Agent 用上；另一类是要自己定义的鸿蒙 spec，公共规范只规定了「装东西的盒子」，盒子里装什么得鸿蒙自己定。

两个方向不要混讲

方向回答的问题主要规范DevEco 的角色
让外部 AI 会写鸿蒙任何 Agent 在任何入口都能写对、验得了、交得出鸿蒙应用MCP、AGENTS.md、Agent Skills、llms.txt、5 个鸿蒙 spec主场：知识、规则、工具的提供方
让鸿蒙应用进 AI应用的能力能被小艺和其他 Agent 发现、调用、呈现HMAF、意图框架、MCP、A2A、A2UI辅助：提供接入用的 Skill、调试和测试工具

对 DevEco 的建议从体验角度

  1. 做一步「准备度检查」：打开或新建工程时，检查七类准备物哪些齐了、哪些缺了（有没有规则、有没有 AGENTS.md、模型是否可用、证书是否配好、设备是否在线、AGC 应用是否已创建），缺的一项项补，补完才开始交给 AI。对个人是路径，对企业是体检。
  2. 导入按用户类型分档：个人默认装好规则和 Skill；团队导入截图、Figma、HTML 原型；企业导入自己的规则、spec 模板、私有知识库，并能分发给全组。
  3. 所有内置能力都能导出：Skill、规则、MCP 一条命令导出给 Claude Code、Codex、Cursor、Trae 和企业自研 Agent，和 Xcode 27、Android Studio 的做法对齐。
  4. 先补两头：准备阶段补规则模板、设计稿映射、安卓迁移；上架阶段推动创建应用 API 和机器可读的审核结果。中间的开发和测试已经比较全，重点是统一版本和交付形式。
  5. 给头部厂商一份「能力 × 形式 × 版本」对照表：每项能力写清有没有 CLI、有没有 MCP、有没有 Skill、能否在 Linux 无头运行、对应哪个版本，作为进 38+ 家头部公司的对接材料。
