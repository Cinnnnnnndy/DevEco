# 招募筛选与配额执行说明

版本：2026-11-05（全局审校）。仅供研究与招募团队使用，不作为受访者问卷正文。配套文件：`recruitment-questionnaire.md` / `.html`。

## 样本配额

建议招募 30–40 位独立受访者，沿用前期画像方向：头部互联网及同类大型研发团队、中厂、小团队与个人开发者。以下为工作量区间，不是生态分布。按本批条件确认具体目标，再据实际完成数计算比例。

| 画像主类 | 建议区间 | 核验重点 |
|---|---:|---|
| P1 头部互联网及同类大型研发团队 | 12–16 人 | 多团队协作、组织级平台与工具链支撑；包含工程体系相近的内部团队，覆盖 3–4 家外部重点企业 |
| P2 中厂 | 8–10 人 | 稳定研发组织和分工，以具体业务交付为主，工程支撑围绕项目配置 |
| P3 小团队与个人开发者 | 10–14 人 | 少量成员或个人承担多个环节；组内小团队与独立开发 / 学习者分别争取至少 4 人 |
| 合计 | 30–40 人 | 三组下限合计 30，上限合计 40；来源与业务标签不另加人数 |

每人只有一个画像主类。先看本轮项目是否依托组织级平台与多团队体系（P1），再区分稳定分工的中厂（P2）和自主承担多环节的小团队 / 个人（P3）。大型企业的小项目组不只按人数归 P3；不根据品牌名、AI 水平或是否采用某种工具直接归类。问卷自述与核验不一致时保留原答卷，记录调整依据。

华为内部 / 外部是来源标签：内部实际使用 DevEco 者建议 6–10 人，包含在三组总数内，按工程体系归组，优先覆盖至少 3 个业务团队。“生态伙伴”不再单列，框架、三方库、平台或开发服务记录为业务标签；学生 / 学习者为身份标签。统一称鸿蒙生态开发者。

角色交叉覆盖：一线开发约 55%、测试 / 质量 / 发布约 17%、工具链 / AI 平台 / 效能约 17%、技术负责人约 11%；按实际总人数换算，主角色按投入时间最多的职责确定。其他协作角色进入专题补充，批准纳入时记录调整。

AI 高频、低频和近月未用各争取约三分之一；未用再分从未使用与曾用后停用。鸿蒙经验 ≤3 个月约 28%、>3–12 个月约 33%、>12 个月约 39%。这些是交叉覆盖参考，不把全部组合设为硬性人数。

准备、编码、验证、签名 / 发布各争取 ≥6 人；暂停 / 放弃项目 3–4 人；Android ≥8 人、iOS ≥6 人、非手机终端 ≥6 人，可重叠。内部来源一线开发争取 ≥4 人、测试 / 发布 ≥1 人。先补画像缺口，再兼顾角色、AI 和场景差异。

## 问卷设计取舍

参考其他项目“用户是谁 → 实际怎么用 → 能否参与”的筛选思路与自然直接的措辞，围绕鸿蒙项目重写为 12 道核心题，另设 S0 知情同意及 C1 联系授权。预计 5–8 分钟，需经试填校准。没有沿用云服务器资源数量、控制台形态、活动日期、奖项或评审机制。

报名阶段识别人群和经历，预约阶段核实配额标签，正式访谈追问需求与原因。问卷不替代深访，也不直接产出需求排名或满意度结论；不把参与奖励设计成对观点质量的评奖。奖励、时间及渠道确认后另行说明。

## 入选与补充规则

- 主样本须同意筛选、有可核实的本人任务经历，并愿意接受访谈安排。外部优先近 6 个月参与者；内部需近 3 个月实际使用 DevEco。题目间不一致时先澄清，不直接认定无效。
- Q04 尚未亲自参与：结束本轮开发者招募，不展示其余题目及联系方式。Q06 近 3 个月无任务：继续填写，预约时确认最后实践时间；3–6 个月者仍可纳入外部主样本，超过 6 个月者进入历史 / 停用经历补充池，必要时纳入并记录理由。
- Q05 外部未用 DevEco，但通过其他工具参与鸿蒙工程或平台接入：可纳入对应专题；内部不满足近期使用条件者进入补充池。
- Q06 一句话只有概括态度而无任务信息：预约前简短核实，不要求截图、代码或保密证明。仍无本人经历者不进入主样本。
- AI 未用、无负面反馈、未上架、拒绝录音录屏均不构成排除理由。不能以痛点多少或熟悉 Spec / MCP 等术语筛人。
- Q12 先了解安排者：仅进入沟通池；确认愿意后预约。暂不参与者结束，不展示联系信息题。
- C1 不同意留下联系方式：结束报名，不进入预约名单，不从其他渠道补抓个人信息。
- 纯专家意见另记，不充当实际用户证据。内部与外部分别分析，并标注内部支持条件。

## 筛选顺序与结果判定

逐人按“参与授权 → 本人经历 → 时间范围 → 分类核验 → 配额排期”处理。问卷答案只用于初筛，预约核验后由研究员确认；不计算笼统的“优质用户分”。

| 顺序 | 判断条件 | 处理 |
|---|---|---|
| 1. 是否授权及愿意参与 | S0 同意、Q12 愿意、C1 同意联系 | 三项明确后才能进入可预约名单；希望先了解者先沟通 |
| 2. 是否有本人实际任务 | Q04 与 Q06 能说明任务、本人操作及结果 | 练习、测试、工具链交付均有效；含糊或矛盾先核验，不能直接判无效 |
| 3. 是否符合近期条件 | 外部近 6 个月有任务；内部近 3 个月实际用 DevEco | 超出范围但有真实经历者进入专题补充池，保留停用或中断价值 |
| 4. 是否能明确分类 | 画像主类、主角色、AI 频率、经验有依据 | 未知记录“待确认”并标记待核验，不凭公司名称、人数或术语熟悉度猜测 |
| 5. 本批是否需要 | 客户配额与关键角色有缺口，且组织来源不过度集中 | 符合条件且有缺口者进入本批；满额者进入配额候补，不记为不合格 |

每人只设一个当前筛选状态；预约、到访及完成情况另设执行状态，避免把“符合招募条件”当成“已完成访谈”。

| 筛选状态 | 使用条件 | 后续动作 / 原因码 |
|---|---|---|
| 待核验 | 缺关键事实、分类有歧义或希望先了解安排 | V01 经历待确认；V02 分类待确认；V03 意愿待确认；核验后再转状态 |
| 本批入选 | 基本条件已确认，符合本批配额或场景缺口 | A01 客户缺口；A02 角色缺口；A03 场景对照；进入预约 |
| 配额候补 | 条件符合，但本批满额或组织来源过于集中 | W01 配额已满；W02 同组织集中；W03 时间不合适；补位时重新确认 |
| 专题补充 | 有真实经历，但近期条件或现有角色主配额不匹配 | P01 历史 / 停用经历；P02 设计等协作角色；P03 专题例外；负责人确认是否纳入及调整配额 |
| 本轮不纳入 | 核实无本人相关经历，或当前不愿参与 / 不授权联系 | X01 无实际经历；X02 暂不参与；X03 无联系授权；不因 AI 未用或拒绝录制使用此状态 |
| 已撤回 | 受访者明确撤回参与或资料使用许可 | X04 撤回；停止联系，并按已告知约定处理资料，不再作为候补 |

拒绝 S0 者不建立含答卷或联系信息的个人台账；只可保留不识别个人的流程统计。部分信息仍无法核实者保留“待核验”，不将未知等同于虚假。仅经核实没有实际经历才使用 X01。专家交流单独建表，不混入实际用户人数。

## 分类字典：一个主类，多个交叉标签

| 字段 | 允许分类 | 来源及判定规则 |
|---|---|---|
| 画像主类（单选） | P1 头部互联网及同类大型研发团队；P2 中厂；P3 小团队与个人开发者 | Q01＋Q03、Q06 及预约核验，以项目依托的组织体系和协作方式归组；每人仅一类，未知记待确认 |
| 来源（单选） | 华为内部；外部；待确认 | Q01b。独立于画像；华为员工分享个人项目时记为外部个人项目，不能只看任职身份 |
| P3 组内形态（单选） | 小团队；独立开发；个人学习 / 练习；待确认 | Q01c，P1 / P2 记不适用；用于检查合并组内覆盖 |
| 业务（多选） | 框架 / 三方库；工具或平台；开发 / 测试服务；应用 / 元服务；其他 | Q01d，生态合作身份可补记，不另计主配额 |
| 主角色（单选） | R01 一线开发；R02 测试 / 质量 / 发布；R03 工具链 / AI 平台 / 效能；R04 技术负责人；R05 其他协作角色 | Q02，按最近项目投入时间最多的职责；兼任作为副角色多选，不重复占主角色配额。R05 默认专题补充 |
| AI 使用（单选） | A01 高频；A02 低频；A03 曾用后近月未用；A04 从未使用；AU 待确认 | Q08，最近 4 周每周 ≥3 天为高频，用过但平均 <3 天为低频。A03＋A04 合并统计近月未用配额，原始细分保留 |
| AI 使用场景（多选） | 鸿蒙；其他平台；待确认；不适用 | Q08 补充：两者都有则记录两个标签；从未使用为不适用；未回答为待确认，不能推定用于鸿蒙 |
| 鸿蒙实践经验（单选） | E01 ≤3 个月；E02 >3–12 个月；E03 >12 个月；EU 待确认 | Q04a，以首次亲自参与至今计，不直接当作技能水平；暂停时长预约补记 |
| 项目阶段（单选） | 学习练习；准备；开发；测试 / 发布准备；已发布 / 已交付维护；暂停 / 放弃；其他 | Q04b，按本次讨论的一个项目记录；工具链与库允许按交付状态填写 |
| 本人流程经历（多选） | 准备；编码 / 迁移；构建调试；测试验证；签名发布；工具接入；生态交付；练习 | Q06＋预约核验。Q06 仅问高频前三项，没选不等于从未做过 |
| 接入经验（单选） | 亲自接入；评估 / 试接；团队有而本人未参与；无；未知 | Q11。只有前两项可作为接入执行经历，不能用团队经历替代本人经历 |
| 平台 / 设备 / 工程方式（多选） | 按 Q07 与预约记录实际平台、设备、原生 / 跨平台 / 迁移等 | 仅记录本人做过的场景；未回答与无经验分别标记 |
| 支持条件及授权 | 公开资源 / 同事 / 内部工具 / 产品团队等；录音、录屏、复访分别记同意 / 拒绝 / 待确认 | 预约核验，访谈前再确认录制；三种授权相互独立，不影响主分类 |

同一人有多个项目身份时，先确定本轮访谈要讨论的项目再分类；必要的其他经历保留为副标签。改类需记录旧值、新值、依据、确认人和日期，不覆盖原始答卷。

## 邀请优先级与配额核对

优先邀请能补足画像主配额的人，再比较该组内关键角色、AI 使用差异、经验及流程场景缺口。同等适配者按可参与时段和报名顺序安排；不按表达流畅程度、负面反馈数量或 AI 熟练度排名。

同一外部企业原则上 ≤2 人；头部厂商配对访谈可 ≤3 人，并尽量覆盖 3–4 家。内部来自至少 3 个业务团队，一线开发 ≥4 人、测试 / 发布 ≥1 人。若与关键配额冲突，由负责人记录取舍而非静默改类。

画像主类合计应等于去重后的独立参与者人数；主角色、AI 频率和经验各自合计应等于同一人数（含待确认），跨维度不能相加。流程、设备和副角色多选标签的合计允许超过总人数。

区间不直接参与减法：研究负责人先在区间内确认本轮目标，各组目标合计控制在 30–40 人，再计算缺口。正式完成数仅统计已批准纳入主样本且“已完成首访”的独立编号，复访另计场次。排期剩余名额＝本轮确认目标－已完成首访－已确认待访，至少为 0；未确认邀约与候补不占名额。仍未完成的目标人数＝本轮确认目标－已完成首访。超额或特殊人群另行标注调整原因。

## 台账使用

下载配套的 recruitment-tracker-template.md，复制“单人记录卡”管理每位授权候选人，并每周更新配额汇总。模板不含真实受访者或联系方式，填写后应保存在团队受控位置。公开 Pages 仅保留空白模板和研究规则。

## 跳题与问卷平台配置

| 条件 | 后续路径 |
|---|---|
| S0 不同意 | 结束，不保存未同意答卷 |
| Q01 任意选项 | 展示 Q01b 来源；仅 P3 展示 Q01c 组内形态，所有人可选答 Q01d 业务 |
| Q04 尚未参与 | 隐藏项目状态，结束，不展示联系题 |
| Q05 从未使用 | 隐藏产品子题，继续 Q06 |
| Q06 近 3 个月无任务 | 继续，真实任务填更早经历，标记预约补充核验 |
| Q08 高频 / 低频 / 曾用后停用 | Q09 → Q10 |
| Q08 从未使用 | 跳过 Q09，隐藏 Q10 的 AI 材料补充题 |
| Q11 亲自接入或试接 | 展示选填的一例；其他选择不展示 |
| Q12 暂不参与 | 结束，不收集联系信息 |
| Q12 愿意 / 先了解 | 展示 C1 |
| C1 同意 | 展示称呼、一种联系渠道及选填时段；不同意则结束 |

已在问卷中明确列出 01b 来源、01c 小团队 / 个人细分、01d 业务标签、06b 真实任务、08b AI 平台、09b 工具名称、10b 材料、11b 接入例子及 C1b 联系信息；子题不另算核心题数。其他组合题在平台上拆成独立子题，如 Q04a 实践年限、Q04b 项目状态；Q05a 最近使用、Q05b 产品；Q06a 高频任务、Q06b 一句话经历。条件隐藏题不能设为全局必填。“没有 / 不清楚 / 记不清”等按题意配置互斥；Q06 和 Q09 最多选 3 项，其余多选不限项。“其他”可补充说明。

问卷页面的“配置说明”、配额及筛选规则仅供搭建使用，正式发放时不向受访者展示；不显示“符合 / 不符合预期答案”等文案。若试填超时，可将 Q10 AI 材料选答及 Q11 接入例子移到预约阶段。

## 预约时补充核验（按人群选问，不要求每人全答）

| 核验主题 | 简短提问 | 用途 |
|---|---|---|
| 画像与组织核验 | 本项目依托哪些组织级工程支撑？涉及多少团队、如何分工？工具由组织统一建设还是项目自行选择？ | 对照 P1 / P2 / P3，内部项目也用同一口径；框架、库或服务另记业务标签 |
| 实际参与与频率 | 最近一次任务何时发生？近 3 个月大致每周做几天？DevEco 用什么版本？ | 核验近期参与；与 AI 使用频率分别记录 |
| 技术与终端 | 原生 ArkTS、跨平台还是迁移项目？涉及哪些设备？ | 补齐开发方式及非手机终端标签 |
| 角色与流程 | 除主要职责，是否直接负责测试发布或工具链？实际做过哪一步？ | 副角色与全流程覆盖，不只依据高频前三项 |
| 内部支持 | 平时主要通过公开文档、同事还是产品技术团队获得支持？ | 标注内部 / 外部支持差异，不要求联系人 |
| AI 未用 / 停用 | 是近期没任务、已有方式足够、受条件限制，还是其他原因？ | 保留不同原因，不将未用视为能力不足 |
| 参与安排 | 哪些时段方便？是否只口述，或愿意展示脱敏材料？录音 / 录屏是否可另行确认？ | 拒绝展示或录制不影响入选 |
| 后续邀请 | 是否愿意在本次结束后另行接收复访或原型体验邀请？ | 单独记录许可，拒绝不影响本次访谈 |

Spec 的保存与更新、AI 任务跟进与接管、代码审查和二次编辑、测试验收、能力输入输出和调用形式等保留在正式访谈，先从具体经历展开，不用术语测试筛选用户。

## 执行与资料管理

发放前补齐并向受访者展示研究团队、联系渠道、信息用途与访问范围、保留期限、撤回方式；不发布带空白占位的正式采集表。当前 HTML 是审阅稿，无提交接口，不存储答案。活动时间与礼品如未确认，不作具体承诺；不要求匿名观点公开共享。

仅收集一种联系渠道，联系方式与研究答案分开保存，以参与者编号关联；公开报告仅展示汇总或脱敏内容。复访仅联系单独授权者，每次参与均重新确认。不得将真实答卷或联系方式提交至公开 Git 仓库。

台账字段：参与者编号、渠道、主分组、组织代称、主 / 副角色、最近任务及 DevEco 使用、经验、AI 频率与停用标签、流程 / 平台 / 终端、支持条件、筛选 / 预约 / 完成状态、复访许可、调整理由。个人联系方式单独管理。

先安排 3–5 人试填，覆盖内部用户、外部企业和未用 AI 者。验证拒绝同意、尚未参与、停用 AI、未用 DevEco、隐藏必填、拒绝联系方式及手机展示；记录实际耗时和理解偏差后再发放。

每周核对已完成访谈的配额，预约与候补另列；先补缺失画像类型和角色，再兼顾 AI、经验及其他标签。同一外部企业原则上 ≤2 人，头部厂商配对访谈可 ≤3 人；失约不计为完成样本。

## 三类画像与交叉标签的路径检查

| 类型 | 核验与处理 |
|---|---|
| P1 头部互联网及同类大型研发团队 | Q01 自述＋预约核验组织级平台、多团队协作与工程支撑；内部团队可归入，保留来源对照 |
| P2 中厂 | 核验稳定分工和项目交付方式，不只看公司规模，不按是否重度使用 AI 分类 |
| P3 小团队与个人 | Q01c 区分协作小团队、独立开发和个人学习；两侧都需覆盖，不要求商业化或上架 |
| 内部来源 | Q01b 标记；近 3 个月实际用 DevEco，跨业务团队覆盖，不额外计入总人数 |
| 框架 / 三方库 / 服务人员 | Q01d 记业务标签；按其依托的组织体系归 P1 / P2 / P3，不另设生态伙伴组 |
| AI 未用 / 停用 | 从未使用跳过 Q09，继续通用准备材料；不因未用 AI 排除 |

Q01b 对所有人展示并必答；Q01c 仅选小团队 / 个人时展示且必答，Q01d 所有人可选答；Q08b 仅曾用 AI 者展示且选填。P3 组内形态仍待确认时由预约补问。试填需交叉覆盖三个画像、内部来源、个人初学者及 AI 未用者。

## 全局版本与执行边界

研究计划维护目标、配额、方法和排期；本规则维护分类与筛选口径；招募问卷维护题目与跳题；空白台账承接执行。当前均为研究启动前的设计稿，没有真实答卷。正式启动时间、采集平台、联系与资料管理信息确认后，再组织试填和正式招募。

招募问卷与后续体验测量问卷分别编制、分别统计。招募问卷试填不等于完成访谈；2–3 场访谈试访仅在符合正式标准时计入首访。30–40 人是独立受访者的弹性工作量，三类人数区间分别为 12–16、8–10、10–14 人；日记、观察、测试优先从其中邀请，复访不重复增加人数。

凡调整筛选阈值、主配额、标签或题目，须同步检查上述四份材料并记录版本；招募与定向补招持续到 4 月，之后的常态研究另设周期统计。
