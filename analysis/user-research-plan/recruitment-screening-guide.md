# 招募筛选与配额执行说明

版本：2026-11-05（全局审校）。仅供研究与招募团队使用，不作为受访者问卷正文。配套文件：`recruitment-questionnaire.md` / `.html`。

## 招募适用范围与两条路径

配套招募问卷仅面向外部开发者，不包含内部身份题。外部答卷在台账中由研究员统一标记为“外部”，无需受访者填写来源。内部用户通过业务团队定向邀约，研究员分别确认研究参与及联系授权，核验本人任务、近 3 个月 DevEco 使用、画像与角色，再录入同一台账；不要求填写外部问卷。

以下配额和分类规则适用于整个研究，仍包含内部 6–10 人；不是外部问卷需要额外招满的名额。两条路径合计控制在 30–40 人，内部与外部来源由招募渠道及核验记录维护，不从公司名称自动推断。

## 样本配额

建议招募 30–40 位独立受访者，沿用前期画像方向：头部互联网及同类大型研发团队、中厂、小团队与个人开发者。以下为工作量区间，不是生态分布。按本批条件确认具体目标，再据实际完成数计算比例。

| 画像主类 | 建议区间 | 核验重点 |
|---|---:|---|
| P1 头部互联网及同类大型研发团队 | 12–16 人 | 多团队协作、组织级平台与工具链支撑；包含工程体系相近的内部团队，覆盖 3–4 家外部重点企业 |
| P2 中厂 | 8–10 人 | 稳定研发组织和分工，以具体业务交付为主，工程支撑围绕项目配置 |
| P3 小团队与个人开发者 | 10–14 人 | 少量成员或个人承担多个环节；组内小团队与独立开发 / 学习者分别争取至少 4 人 |
| 合计 | 30–40 人 | 三组下限合计 30，上限合计 40；来源与业务标签不另加人数 |

每人只有一个画像主类。先看本轮项目是否依托组织级平台与多团队体系（P1），再区分稳定分工的中厂（P2）和自主承担多环节的小团队 / 个人（P3）。大型企业的小项目组不只按人数归 P3；不根据品牌名、AI 水平或是否采用某种工具直接归类。问卷事实与核验不一致时保留原答卷，记录调整依据。

华为内部 / 外部是来源标签：内部实际使用 DevEco 者建议 6–10 人，包含在三组总数内，按工程体系归组，优先覆盖至少 3 个业务团队。“生态伙伴”不再单列，框架、三方库、平台或开发服务记录为业务标签；学生 / 学习者为身份标签。统一称鸿蒙生态开发者。

角色交叉覆盖：一线开发约 55%、测试 / 质量 / 发布约 17%、工具链 / AI 平台 / 效能约 17%、技术负责人约 11%；按实际总人数换算，主角色按投入时间最多的职责确定。其他协作角色进入专题补充，批准纳入时记录调整。

AI 高频、低频和近月未用各争取约三分之一；未用再分从未使用与曾用后停用。鸿蒙经验 ≤3 个月约 28%、>3–12 个月约 33%、>12 个月约 39%。这些是交叉覆盖参考，不把全部组合设为硬性人数。

准备、编码、验证、签名 / 发布各争取 ≥6 人；暂停 / 放弃项目 3–4 人；Android ≥8 人、iOS ≥6 人、非手机终端 ≥6 人，可重叠。内部来源一线开发争取 ≥4 人、测试 / 发布 ≥1 人。先补画像缺口，再兼顾角色、AI 和场景差异。

## 问卷设计取舍

参考其他项目“用户是谁 → 实际怎么用 → 能否参与”的筛选思路与自然直接的措辞，围绕鸿蒙项目重写为 17 道核心题，开场说明研究用途与自愿参与，末尾设置 C1 联系授权。预计 6–9 分钟，需经试填校准。没有沿用云服务器资源数量、控制台形态、活动日期、奖项或评审机制。

报名阶段识别人群和经历，预约阶段核实配额标签，正式访谈追问需求与原因。问卷不替代深访，也不直接产出需求排名或满意度结论；不把参与奖励设计成对观点质量的评奖。奖励、时间及渠道确认后另行说明。

## 入选与补充规则

- 主样本须同意筛选、有可核实的本人任务经历，并愿意接受访谈安排。外部优先近 6 个月参与者；内部需近 3 个月实际使用 DevEco。题目间不一致时先澄清，不直接认定无效。
- Q03 选择 0 个项目：结束本轮有项目经历者招募，不展示后续题目及联系方式。Q07 仅记录年限和阶段，不再重复筛除；记不清时预约核验。Q09 近 3 个月无任务：继续填写，预约时确认最后实践时间；3–6 个月者仍可纳入外部主样本，超过 6 个月者进入历史 / 停用经历补充池，必要时纳入并记录理由。
- Q08 外部未用 DevEco，但通过其他工具参与鸿蒙工程或平台接入：可纳入对应专题；内部不满足近期使用条件者进入补充池。
- Q09 一句话只有概括态度而无任务信息：预约前简短核实，不要求截图、代码或保密证明。仍无本人经历者不进入主样本。
- AI 未用、无负面反馈、未上架、拒绝录音录屏均不构成排除理由。不能以痛点多少或熟悉 Spec / MCP 等术语筛人。
- Q17 想先了解具体安排者：仅进入沟通池；确认愿意后预约。暂不参与者结束，不展示联系信息题。
- C1 不同意留下联系方式：结束报名，不进入预约名单，不从其他渠道补抓个人信息。
- 纯专家意见另记，不充当实际用户证据。内部与外部分别分析，并标注内部支持条件。

## 筛选顺序与结果判定

逐人按“参与授权 → 本人经历 → 时间范围 → 分类核验 → 配额排期”处理。问卷答案只用于初筛，预约核验后由研究员确认；不计算笼统的“优质用户分”。

| 顺序 | 判断条件 | 处理 |
|---|---|---|
| 1. 是否授权及愿意参与 | 外部：已展示研究用途并收到自愿提交的答卷，Q17 愿意、C1 同意联系；内部：定向邀约中分别确认同等授权 | 参与意愿和联系授权明确后才能进入可预约名单；希望先了解者先沟通 |
| 2. 是否有本人实际任务 | Q07 与 Q09 能说明任务、本人操作及结果 | 练习、测试、工具链交付均有效；含糊或矛盾先核验，不能直接判无效 |
| 3. 是否符合近期条件 | 外部近 6 个月有任务；内部近 3 个月实际用 DevEco | 超出范围但有真实经历者进入专题补充池，保留停用或中断价值 |
| 4. 是否能明确分类 | 画像主类、主角色、AI 频率、经验有依据 | 未知记录“待确认”并标记待核验，不凭公司名称、人数或术语熟悉度猜测 |
| 5. 本批是否需要 | 客户配额与关键角色有缺口，且组织来源不过度集中 | 符合条件且有缺口者进入本批；满额者进入配额候补，不记为不合格 |

每人只设一个当前筛选状态；预约、到访及完成情况另设执行状态，避免把“符合招募条件”当成“已完成访谈”。

| 筛选状态 | 使用条件 | 后续动作 / 原因码 |
|---|---|---|
| 待核验 | 缺关键事实、分类有歧义或希望先了解安排 | V01 经历待确认；V02 分类待确认；V03 意愿待确认；核验后再转状态 |
| 本批入选 | 基本条件已确认，符合本批配额或场景缺口 | A01 客户缺口；A02 角色缺口；A03 场景对照；进入预约 |
| 配额候补 | 条件符合，但本批满额或组织来源过于集中 | W01 配额已满；W02 同组织集中；W03 时间不合适；补位时重新确认 |
| 专题补充 | 有真实经历，但近期条件或现有角色主配额不匹配 | P01 历史 / 停用经历；P02 设计等协作角色；P03 专题例外；负责人确认是否纳入及调整配额 |
| 本轮不纳入 | 核实无本人相关经历，或当前不愿参与 / 不授权联系 | X01 无实际经历；X02 暂不参与；X03 无联系授权；不因 AI 未用或拒绝录制使用此状态 |
| 已撤回 | 受访者明确撤回参与或资料使用许可 | X04 撤回；停止联系，并按已告知约定处理资料，不再作为候补 |

外部问卷开头不设置同意题。平台在用户主动提交前不保存未完成答卷；未提交者不建立候选台账。内部定向邀约仍单独确认参与授权。部分信息仍无法核实者保留“待核验”，不将未知等同于虚假。仅经核实没有实际经历才使用 X01。专家交流单独建表，不混入实际用户人数。

## 分类字典：一个主类，多个交叉标签

| 字段 | 允许分类 | 来源及判定规则 |
|---|---|---|
| 画像主类（单选） | P1 头部互联网及同类大型研发团队；P2 中厂；P3 小团队与个人开发者 | 外部按 Q01–Q06 的行业、岗位、项目数量、组织研发人数、项目团队人数、协作事实，结合 Q09 任务与预约核验；内部按定向邀约核验记录，以项目依托的组织体系和协作方式归组；每人仅一类，未知记待确认 |
| 来源（单选） | 华为内部；外部；待确认 | 研究员根据招募渠道与核验记录填写，外部问卷统一记外部；内部定向邀约单独核验。来源独立于画像，不是问卷题目 |
| P3 组内形态（单选） | 小团队；独立开发；个人学习 / 练习；待确认 | Q05 项目人数＋Q07 项目状态及预约核验；独立开发 / 个人练习分别标记，企业项目按组织支撑核验，P1 / P2 记不适用 |

| 最常用 AI 工具（单选） | 按问卷工具名称、近月未用、不确定、其他原文 | Q12 仅近期使用者回答；跳题者记“未展示”，另据 Q11 标记近月未用，不伪造工具答案。最近 4 周使用天数最多的一款，并列按最近一次使用 |
| DevEco Code 经历（单选） | 近月实际使用、曾用后近月未用、仅安装试用、听过未用、未听过、不确定 | Q13；与整体 AI 频率及最常用工具分别记录，不互相推定 |

| AI 使用（单选） | A01 高频；A02 低频；A03 曾用后近月未用；A04 从未使用；AU 待确认 | Q11，最近 4 周平均每周 ≥3 天为高频，用过但平均 <3 天为低频。A03＋A04 合并统计近月未用配额，原始细分保留 |
| AI 使用场景（多选） | 鸿蒙；其他平台；待确认；不适用 | Q11 补充：两者都有则记录两个标签；从未使用为不适用；未回答为待确认，不能推定用于鸿蒙 |
| 鸿蒙实践经验（单选） | E01 ≤3 个月；E02 >3–12 个月；E03 >12 个月；EU 待确认 | Q07a，以首次亲自参与至今计，不直接当作技能水平；暂停时长预约补记 |
| 项目阶段（单选） | 学习练习；准备；开发；测试 / 发布准备；已发布 / 已交付维护；暂停 / 放弃；其他 | Q07b，按本次讨论的一个项目记录；工具链与库允许按交付状态填写 |
| 本人流程经历（多选） | 准备；编码 / 迁移；构建调试；测试验证；签名发布；工具接入；生态交付；练习 | Q09＋预约核验。Q09 仅问高频前三项，没选不等于从未做过 |
| 接入经验（单选） | 亲自接入；评估 / 试接；团队有而本人未参与；无；未知 | Q16。只有前两项可作为接入执行经历，不能用团队经历替代本人经历 |
| 平台 / 设备 / 工程方式（多选） | 按 Q10 与预约记录实际平台、设备、原生 / 跨平台 / 迁移等 | 仅记录本人做过的场景；未回答与无经验分别标记 |
| 支持条件及授权 | 公开资源 / 同事 / 内部工具 / 产品团队等；录音、录屏、复访分别记同意 / 拒绝 / 待确认 | 预约核验，访谈前再确认录制；三种授权相互独立，不影响主分类 |

同一人有多个项目身份时，先确定本轮访谈要讨论的项目再分类；必要的其他经历保留为副标签。改类需记录旧值、新值、依据、确认人和日期，不覆盖原始答卷。

## 从事实题判断画像

画像由研究员判定，受访者无需选择“头部 / 中厂 / 小团队”。先记录 Q03 项目数量、Q01 行业、Q04 组织研发总人数、Q05 当前鸿蒙项目人数和 Q06 实际协作，再结合 Q09 任务与预约确认组织背景。

| 候选画像 | 组合线索 | 核验边界 |
|---|---|---|
| P1 头部互联网及同类大型研发团队 | 较大研发组织、多团队交付、组织级工程平台或专门支撑；互联网行业是线索之一 | 结合客户名单及组织背景确认；单凭“互联网”、人数多或有统一仓库不能判为头部；大型企业的小项目不能只按项目人数降为 P3 |
| P2 中厂 | 企业 / 机构项目，有稳定人员分工和工程流程，支撑以具体业务项目为主 | 综合组织规模、项目规模与协作方式；不能把未达到某人数阈值者自动归入，也不能只按非互联网行业归类 |
| P3 小团队与个人 | 独立开发 / 个人练习，或小规模成员自行承担多环节、选择工具 | 小团队可把 1–10 人作为核验线索，但需排除依托大组织体系的小项目组；组内保留小团队与个人 / 学习者标签 |

组织研发人数与项目人数分别记录；区间用于描述事实，不作为唯一归类门槛。任一关键答案“不清楚”或相互矛盾时记待核验，补问后再分组；不按公司规模推断具体需求。

## 邀请优先级与配额核对

优先邀请能补足画像主配额的人，再比较该组内关键角色、AI 使用差异、经验及流程场景缺口。同等适配者按可参与时段和报名顺序安排；不按表达流畅程度、负面反馈数量或 AI 熟练度排名。

同一外部企业原则上 ≤2 人；头部厂商配对访谈可 ≤3 人，并尽量覆盖 3–4 家。内部来自至少 3 个业务团队，一线开发 ≥4 人、测试 / 发布 ≥1 人。若与关键配额冲突，由负责人记录取舍而非静默改类。

画像主类合计应等于去重后的独立参与者人数；主角色、AI 频率和经验各自合计应等于同一人数（含待确认），跨维度不能相加。流程、设备和副角色多选标签的合计允许超过总人数。

区间不直接参与减法：研究负责人先在区间内确认本轮目标，各组目标合计控制在 30–40 人，再计算缺口。正式完成数仅统计已批准纳入主样本且“已完成首访”的独立编号，复访另计场次。排期剩余名额＝本轮确认目标－已完成首访－已确认待访，至少为 0；未确认邀约与候补不占名额。仍未完成的目标人数＝本轮确认目标－已完成首访。超额或特殊人群另行标注调整原因。

## 台账使用

下载配套的 recruitment-tracker-template.md，复制“单人记录卡”管理每位授权候选人，并每周更新配额汇总。模板不含真实受访者或联系方式，填写后应保存在团队受控位置。公开 Pages 仅保留空白模板和研究规则。

## 执行与资料管理

发放前补齐并向受访者展示研究团队、联系渠道、信息用途与访问范围、保留期限、撤回方式；不发布带空白占位的正式采集表。当前 HTML 是审阅稿，无提交接口，不存储答案。活动时间与礼品如未确认，不作具体承诺；不要求匿名观点公开共享。

仅收集一种联系渠道，联系方式与研究答案分开保存，以参与者编号关联；公开报告仅展示汇总或脱敏内容。复访仅联系单独授权者，每次参与均重新确认。不得将真实答卷或联系方式提交至公开 Git 仓库。

台账字段：参与者编号、渠道、主分组、组织代称、主 / 副角色、最近任务及 DevEco 使用、经验、AI 频率与停用标签、流程 / 平台 / 终端、支持条件、筛选 / 预约 / 完成状态、复访许可、调整理由。个人联系方式单独管理。

先安排 3–5 位外部开发者试填，覆盖三个画像及未用 AI 者。验证未提交退出、尚未参与、停用 AI、未用 DevEco、隐藏必填、拒绝联系方式及手机展示；记录实际耗时和理解偏差后再发放。

每周核对已完成访谈的配额，预约与候补另列；先补缺失画像类型和角色，再兼顾 AI、经验及其他标签。同一外部企业原则上 ≤2 人，头部厂商配对访谈可 ≤3 人；失约不计为完成样本。

## 全局版本与执行边界

研究计划维护目标、配额、方法和排期；本规则维护分类与筛选口径；招募问卷维护题目与跳题；空白台账承接执行。当前均为研究启动前的设计稿，没有真实答卷。正式启动时间、采集平台、联系与资料管理信息确认后，再组织试填和正式招募。

招募问卷与后续体验测量问卷分别编制、分别统计。招募问卷试填不等于完成访谈；2–3 场访谈试访仅在符合正式标准时计入首访。30–40 人是独立受访者的弹性工作量，三类人数区间分别为 12–16、8–10、10–14 人；日记、观察、测试优先从其中邀请，复访不重复增加人数。

凡调整筛选阈值、主配额、标签或题目，须同步检查上述四份材料并记录版本；招募与定向补招持续到 4 月，之后的常态研究另设周期统计。

## DevEco Code 后续招募重点

在三类画像中交叉检查 DevEco Code 近期使用、曾用后近月未用、仅试用及未使用者的覆盖，不只招募当前活跃用户。Q12 最常用工具可识别其他工具用户；Q13 单独记录是否有 DevEco Code 经历，避免把“最常用其他工具”误判成“没用过 DevEco Code”。Q12 仅向近 4 周用过 AI 者展示，Q13 向所有有项目经历者展示；两题均不是淘汰条件，具体场次按当前可招募人数与后续研究任务安排，暂无依据时不强设产品配额。

预约或正式访谈追问：DevEco Code 使用在哪类项目和任务、为何选择或停止、是否使用 AI 能力、怎样检查结果和继续修改；未使用者了解现有工具选择与采用条件。Q11、Q12、Q13 看似冲突时先核实时间和具体功能，不直接作废答卷。所有工具选项只作为使用经历记录，其他填答保留原文再统一标签。
