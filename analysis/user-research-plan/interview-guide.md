# 鸿蒙开发者访谈与任务评测提纲

版本：2026-11-06 · 配套研究计划与外部招募问卷

从一个真实鸿蒙项目展开，了解DevEco Studio、DevEco Code和其他工具怎样帮助开发者完成工程准备、实现、验证与交付。AI问题随具体步骤追问，每场只选本人做过的环节。

## 一、材料依据与本轮重点

| 已有输入 | 本次要核实什么 |
|---|---|
| 六月原声：生成的代码未必编译通过，用户仍需真机验收 | 最近一次失败是否与ArkTS语法、API版本、依赖、工程配置或业务实现有关？怎样发现、修改和复验？ |
| 六月原声：反复编译影响查看UI；打包后还要处理签名和发布 | 预览、模拟器和真机分别承担什么？哪里重复操作、等待或跨平台交接？ |
| 六月原声：规则需要重复交代，也有人觉得持续维护Spec麻烦 | 哪些鸿蒙知识和工程约束必须提供？如何复用，维护成本有多大？ |
| 1028规划与10月29日会议：分客户旅程、能力开放、代码质量 | 按本人流程区分开发、测试、鸿蒙专项和发布能力，核实企业接入形式及二次修改成本。 |
| 1104整合稿：已有资产进入AI开发、持续执行、头部工具链接入 | 在真实鸿蒙任务中验证这三个场景是否存在、谁需要、哪里仍缺支持。 |

每轮先明确产品要做的决定、重点用户、H1–H6中的2–3个问题、可用版本和成功标准（Top-down）。历史原声只作为线索，先听近期经历，再复核旧问题。

## 二、开场与项目核对（15分钟）

前5分钟说明研究用途和约定时长，分别确认录音、录屏许可；用户可跳过问题或停止，不展示保密代码、账号和业务资料。

- 请介绍最近一个您亲自参与的鸿蒙项目：应用、元服务、库／框架还是工具链？要解决什么业务问题，目前做到哪一步？
- 面向手机、平板、穿戴或其他哪些设备？您本人负责什么，开发、测试与发布怎样分工？
- 是原生ArkTS／ArkUI开发、安卓／iOS迁移，还是跨平台适配？已有代码和团队经验如何影响做法？
- 本次使用的Studio、Code、SDK／API和设备系统版本大致是什么？不清楚可会后核验。
- Studio、Code、其他AI工具、自有平台分别在哪一步使用？哪款是主力，什么时候需要切换？

问卷已有信息只核对变化。内部用户另记获得的内部支持。所有版本和能力按参与者实际环境核实。

## 三、沿一条鸿蒙任务回溯（30分钟）

主问：请选择最近一次亲自完成的鸿蒙功能开发、适配、调试或测试任务，从接到目标到确认结束，按实际顺序讲一遍。请先讲怎么做，再讲哪里顺畅或受阻。

| 环节 | 主问与选择性追问 | 记录重点 |
|---|---|---|
| 工程准备与迁移 | 如何创建或接入工程？SDK、依赖、权限、已有业务代码和设计怎样准备？若从安卓／iOS迁移，哪些资产复用，哪些需要重做？如何查到适用版本的鸿蒙文档和示例？ | 起点、准备责任、缺项、查找与配置成本；H1／H2 |
| ArkTS／ArkUI实现 | 最近修改了什么页面、状态逻辑或API调用？哪些自己写，哪些交给AI？怎样把设计、工程上下文、团队规则和目标API版本交代清楚？收到结果后亲自改了什么？ | 代码与设计来源、版本依据、规则传递、二次编辑；H2／H4／H6 |
| 构建与调试 | 第一次构建和运行结果怎样？若报错，在哪里看到，如何判断是语法、依赖、配置、API还是实现问题？用过哪些日志、断点或其他诊断方式？怎样把错误交回Code或其他工具继续修？ | 实际错误、诊断证据、工具切换、修复与重跑；H4／H5 |
| 预览、模拟器与真机 | 这次先在哪里看效果？为什么？哪些问题到真机才发现？如何确认UI交互、业务逻辑、权限和目标设备表现？若涉及多形态／跨设备，怎样选择设备并复验？ | 预览与运行的分工、设备连接、差异、等待和验证覆盖；H5 |
| 性能与质量 | 本次是否做过性能或代码检查？如何发现冗余、规则偏离、异常逻辑或后续维护问题？用过Studio哪些相关模块？没有做时，按什么条件决定可以交付？ | 检查标准、Profiler等实际模块、未验证项、返工；H4／H5 |
| 签名、打包与交付 | 如何从可运行工程到签名、打包、提交审核或交付测试？哪些在Studio／Code完成，哪些转到其他平台？证书、账号、材料和审批由谁处理？失败后怎样定位和继续？ | 工具与组织交接、发布条件、失败恢复；H1／H5／H6 |

测试人员从本人测试任务展开；工具链人员走能力交付流程；学习者可回溯实际练习。未上架、未做性能或未用某模块时跳过，不要求走完全部阶段。

每个关键事件先问Do（做了什么），再问Think（当时怎样判断）和Feel（当时什么感受）。用5W2H补足何事、为何、谁、何时、何处、怎样做和花费；耗时分清实际记录与回忆估算。

## 四、按经历深挖（20分钟，选1–2项）

### DevEco Code怎样进入鸿蒙工作流

- 最近一次用Code完成什么鸿蒙任务？为什么选它，完成到哪一步？还需要Studio或其他工具处理什么？
- 在Code和Studio之间切换时，需要重新打开工程、传错误、找文件或重复配置吗？请讲一次实际过程。
- 如何确认AI采用了正确的ArkTS／ArkUI、API和项目规范？有没有生成结果不适用于当前工程的例子？也请讲一个顺利完成的例子。
- 如果同时跑多个任务，如何区分分支、文件改动、构建结果和设备运行？若中断或离开后回来，先检查什么，怎样继续？
- 仅试用或停用者：最后一次做到哪一步、之后改用什么？区分任务结束、条件限制和产品原因。未用Code者先讲现有方法，不要求评价Code。

### Studio模块与鸿蒙验证

- 问卷中最常用的模块，在刚才任务中具体怎样用？可按实际情况展示Previewer、构建、模拟器、真机、日志／调试、性能或签名步骤。
- 最近一次反复改UI或排错，在哪里等待、重复编译或丢失上下文？哪些步骤可以省略，哪些必须保留？
- 如何判断“编译通过”“设备上跑通”和“满足交付要求”分别成立？还有哪些没有验证？
- 如果做过安卓／iOS相近任务，同等设备与熟悉条件下哪里不同？只比较亲自做过的任务。

### 头部团队与平台接入

- 请画最近一次鸿蒙修改经过自有Agent、CI、构建、测试和设备服务的流程，标出您亲自负责的部分。
- 哪些开发／测试能力已有，哪些必须由鸿蒙平台提供？涉及ArkTS／ArkUI、API、设备形态或分布式场景时，有哪些专门约束？
- 调用方传什么、返回什么？状态、日志、失败和未验证项怎样回到原流程？权限、版本和维护由谁负责？
- 实际用的是CLI、API／SDK、插件或服务中的哪种？为什么？若需要其他形式，要改变哪段流程？MCP、Skill只在用户有相关经验时补问。
- 准备、构建验证、签名发布中，最值得先开放哪一项？请用最近的接入成本或阻塞说明。

### 鸿蒙知识、工程规则与生态Spec

- 开始前实际交给AI哪些设计、存量工程、接口、鸿蒙文档、依赖和测试条件？来自哪里、谁维护？
- 团队规范与鸿蒙平台要求发生冲突或版本变化时，怎样发现并更新？哪些规则需每次重讲？
- 哪类任务值得写清规格、调用约定和验收标准？有没有不用完整Spec也能顺利完成的任务？维护代价如何？
- 先锋用户补问：新方式在鸿蒙项目中解决了什么原方法解决不了的问题？试过后放弃了什么？意见影响力用户补问一次他人采用后的具体反馈。

## 五、Code评分与收尾（10分钟）

近4周用Code做过实际鸿蒙任务者，在回溯后评价以下四项：该任务的整体体验、准备与导入、执行判断与控制、结果检查与继续修改。

选项统一为1很不满意、2不太满意、3一般、4比较满意、5很满意，另有“不适用／记不清”。每项追问哪件事让他选这个分数。停用者的历史评分单列；仅试用或未用者不评价完整流程。

收尾问：如果先解决一个鸿蒙开发问题，您选什么，为什么？目前哪些地方顺畅、值得保留？确认礼品约定及是否愿意另收后续邀请。

## 六、形成性任务测试：从真实鸿蒙场景抽题

每轮选1–2个场景，先做5–8人。使用可公开或脱敏的鸿蒙测试工程；在预测试中核对版本、依赖、设备和已知问题，明确成功、协助与退出标准。

| 任务卡 | 给用户的目标示例 | 研究员检查什么 |
|---|---|---|
| T1 工程准备与首次跑通 | 接手一个鸿蒙工程及明确的小功能需求，按平时方式准备并完成首次可运行修改。 | 依赖、SDK／API及工程规则是否明确；能否找到材料、完成构建并在指定环境运行。 |
| T2 ArkUI修改与反馈 | 根据设计参考调整指定页面和一项交互，在约定设备检查效果，再继续修改。 | 设计表达、Code与Studio切换、预览／运行分工、交互与逻辑是否满足要求。 |
| T3 错误定位与修复 | 一个鸿蒙工程在构建或设备运行中出现已核定的问题，请定位、修复并证明通过。 | 能否找到错误依据、区分原因、交回AI或手动修复，并在同一场景复验。 |
| T4 鸿蒙能力接入 | 在隔离测试环境，将一项鸿蒙构建或设备验证能力接入现有脚本／流水线，查看结果并处理一次失败。 | 调用、权限、状态、日志、结果回传与恢复；只邀请实际相关岗位。 |
| T5 验证与发布准备 | 对已完成的鸿蒙功能判断是否可以交付，完成约定设备检查和签名／打包准备。 | 是否识别未验证项、找到发布条件并完成交接。使用测试证书与账号，终点止于约定准备，不向生产商店提交。 |

任务来自前轮实际问题，不要求产品具备未发布能力；企业和个人、初次与熟练用户按任务分别安排。R3记录是否见过旧方案，R4固定版本和任务后再评价表现。

记录独立完成、协助后完成或失败／退出，以及关键错误、人工介入、耗时与设备结果。环境等待和主持帮助单列；任务后可用1非常困难至7非常容易的难易评分并追问原因。它与5点满意度分别统计。

10–12人是阶段综合评估的工作量估计。若要量化推断或比较版本效果，需重新设计样本与指标，不能直接用形成性场次证明效率提升。

## 七、观察与日志的补充方式

情境观察直接看用户如何处理真实鸿蒙工程、Studio模块、Code及设备，不指定操作路径；口述回忆与实际观察分别标记。

跨日问题可邀请4–6人记录7–14天：任务与工程／版本、设备、用了什么工具、人工介入、结果及当时判断。每个关键事件3–5分钟，结束后回访核验；没有事件可以记无。

小组讨论仅在需要对齐企业接入或规范边界时使用，同类角色4–6人，先个人记录再讨论，不用共识代替实际任务证据。

## 八、分析、行动与执行容量

把每场整理成鸿蒙事件卡：参与者编号、任务、工程与版本、设备、行为、判断／感受、结果、影响和原始位置；标明本人经历或转述、自发或追问。按旅程归纳主题（Bottom-up），比较不同画像、岗位与使用阶段，再回看H1–H6。

旧问题记录仍存在、缓解、已解决、转变或证据不足；未再提及不能判解决。每项建议关联具体鸿蒙任务、证据、负责人、BP／版本／展会节点及复测条件。

两位交互各30%，合计3人日／周，其中核心研究约2.25人日、招募与竞品约0.5人日、机动约0.25人日。执行周约2场，分析周减少场次；启动准备2–3周，首批探索及形成性测试各约6–9周，综合评估约9–12周。产品修改与等待版本另排。每轮完成准备、执行、分析和产品评审后决定下一步。
