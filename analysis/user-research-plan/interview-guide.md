# 鸿蒙开发者访谈与任务评测提纲

版本：2026-11-06 · 研究设计稿 · 与研究计划、20题外部招募问卷及筛选规则配套。

以已上线的初期 DevEco Code 与 DevEco Studio 为对象，理解实际采用、任务流程与后续机会；候选方案在探索之后按条件测试。本提纲是一套按经历选用的模块，不要求每位用户回答全部问题。

## 一、每轮开始前：Top-down 对齐决策

| 研究准备 | 本轮需要明确的内容 |
|---|---|
| 产品决策 | 本轮是识别机会、改进现有流程、验证候选方案，还是评价阶段表现？结果需在哪个 BP／版本／展会节点前交付？ |
| 对象与范围 | P1–P3画像、本人角色、Code／Studio使用状态、先锋／熟练／影响力标签、内外部来源；本轮不覆盖什么？ |
| 研究问题 | 从 H1–H6、RQ1–RQ11 中选2–3个核心问题，其余作为补充，不能每场全面铺开 |
| 已有证据 | 六月原声与十月材料能说明什么、哪些日期和版本已核实、哪些仍是推测？本轮需要什么反例？ |
| 任务与版本 | 观察实际任务或使用统一测试工程；明确产品、模型、插件、设备与权限条件，冻结本批任务口径 |
| 成功标准 | 哪些行为和结果可判完成？哪些错误或未验证项需记录？主持人何时提供帮助或停止任务？ |
| 预测试 | 研究团队演练环境，2–3场试访／任务预测试校准措辞、时长与难度；重大修改后重新试跑 |

Top-down 用于研究设计和事后对照，不向用户朗读研究假设、规划结论或期待答案。既有材料中的引导式问句不直接沿用。

## 二、场次与分支选择

| 参与者状态 | 采用模块 | 不强求的内容 |
|---|---|---|
| Code近期实际使用 | 项目背景、真实旅程、AI事件、Code采用与评分 | 不要求展示全部功能，也不假定使用Code等于使用其AI能力 |
| Code停用／仅试用 | 最后一次使用、转向其他方式的具体事件、采用条件 | 停用回忆单列；仅试用不评价完整开发交付流程 |
| 未用Code但有鸿蒙任务 | 当前工具组合、Studio模块、采用障碍；有AI经验再问AI任务 | 不要求给Code满意度打分或预测购买意愿 |
| 从未用AI | 现有开发方法、资料与协作、为何未用、实际限制 | 跳过AI执行与AI验收经历；不把不用AI理解为能力不足 |
| 平台／工具链角色 | 交付或接入旅程、调用方、工程接口、失败处理和组织协作 | 不强行要求应用上架或UI开发经历 |
| 测试／质量／发布角色 | 测试任务、标准、设备、证据、修复复验与交付 | 编码只追问本人做过部分 |
| 小团队／个人／学习者 | 本人实际项目或练习工程、多环节承担与可用资源 | 不要求商用、团队分工、正式规范或已上架 |
| 先锋／熟练／意见影响力 | 主旅程之后按标签追问新工作方式、熟练操作或影响实例 | 标签不替代行为核验；第二手评价单独标记 |

同一人可以命中多个分支。内部开发者使用相同旅程，另记其获得的内部支持及可用版本，不与外部条件直接合并比较。

## 三、单场半结构化访谈（75分钟示例）

### 0. 开场与授权 · 5分钟

感谢参与。本次想了解您真实的开发经历，帮助我们确定后续改进方向。我们关注工具与流程，您可以跳过任何问题，也可以随时停止。只需分享允许交流的内容，不需要提供代码、账号或非公开业务信息。

分别确认记录、录音、录屏许可；不同意录制可用文字笔记。说明本次用途、资料访问与撤回方式，确认约定时长。后续邀请另行确认。

### 1. 项目、角色与工具选择 · 10分钟

- 请介绍最近一个您亲自参与的鸿蒙项目，当时要交付什么？您负责哪些部分？
- 谁还参与？哪些步骤自己做，哪些依赖同事、平台或其他组织？
- 最近一次用了哪些工具？在什么环节切换？Code和Studio分别承担什么？
- 这次为什么选择这些工具？有没有试过后改回去或停用的例子？请从具体一次选择讲起。
- 如果是复访，最近的项目、工具版本与六月相比有哪些变化？先听新的完整经历，再回看旧问题。

预约已确认的行业、人数和年限只核对变化，不重复整份问卷。

### 2. 沿真实用户旅程回溯 · 30分钟

开场主问：请选最近一次有代表性的任务，从“为什么开始”到“怎样确认结束”，按实际发生的顺序讲一遍。顺利和不顺利都可以；如果方便，可以展示脱敏的工作记录。

| 旅程环节 | Do：实际做了什么 | Think：当时如何理解和判断 | Feel：当时的感受 | 记录证据与对应假设 |
|---|---|---|---|---|
| 开发准备 | 开始时已有何种需求、设计、工程、规则、环境？谁准备？怎样导入或交给工具？缺了什么后做了什么？ | 当时怎样判断可以开始？哪些信息必须确认，哪些边做边补？ | 当时对能否开始、完成任务有什么感受？是什么让感受变化？ | 准备清单、责任人、缺项、重复交代及成本；H1／H2 |
| 编码与AI执行 | 按实际步骤如何写、改或让AI处理？过程看了什么？何时切工具、接管、中断或恢复？ | 当时认为工具在做什么？凭什么继续、叫停或调整范围？ | 哪个时刻比较放心或不确定？请用自己的话描述原因。 | 输入、计划、状态、修改范围、介入与恢复；H3／H6 |
| 测试与验证 | 怎样确认结果正确？执行了哪些构建、测试、设备或代码检查？发现问题后怎样修改和复验？ | “完成”由谁、按什么标准判断？还有哪些没有验证？ | 看到结果时的感受是什么？有没有做完仍不能确认的情况？ | 运行证据、规范与冗余、返工、不可视逻辑、未验证项；H4／H5 |
| 交付、发布与维护 | 怎样打包、签名、交付或提交审核？哪里需要其他人／系统？后续修改如何继续？ | 怎样判断可以交付？如果失败，如何知道下一步？ | 哪一步带来压力或顺畅感？是什么造成的？ | 工具切换、权限、材料、平台依赖、发布失败与恢复；H1／H5／H6 |

Do、Think、Feel是记录框架，不是必须逐格念出的问卷。先问行为，再问当时判断与感受；不把停顿、表情直接解释为情绪。测试与工具链任务可以在本人交付处结束，无需延伸到应用商店。

### 3. 关键事件与角色专题 · 20分钟

每场选择一个关键事件，再从以下专题选择1–2项。先问发生过什么，再问为什么，不假设某个问题必然存在。

| 专题 | 可直接使用的开放追问 | 需要区分 |
|---|---|---|
| AI准备与Spec · H2 | 最近一次让工具遵循要求时，要求放在哪里、怎样更新？哪项需要反复说明？有没有不写完整规范也顺利完成的任务？ | 需求、团队规则、平台要求；谁维护、何时失效；术语不熟悉可用实际文件说明 |
| 持续任务与接管 · H3 | 最近一次让任务持续运行时，您何时离开、回来后先看什么？哪里需要确认？有没有完全不需要离开的任务？ | 真正发生的无人值守与设想；失败、恢复、并行冲突；非核心时段是否实际存在 |
| 质量与二次编辑 · H4 | 最近一次“生成完成”后还做了哪些修改？为什么？如何发现冗余、规则偏离或不可见逻辑问题？怎么确认没有引入新问题？ | 结果正确、可运行、规范、可维护不同层面；检查花费与质量风险 |
| 头部与平台接入 · H1／H5 | 画一下最近一次任务如何穿过你们的Agent、工程平台与鸿蒙工具。由谁调用，带入什么，返回什么？哪里要人工接续？失败怎样定位？ | 通用与鸿蒙特有能力，开发与测试能力；本人参与与团队转述；现成产品和开放能力的实际取舍 |
| 能力提供形式 · H1 | 上次接入采用了什么形式，为什么？如果改成另一种形式，哪段现有流程要改变、谁承担维护？ | 先讲实际操作，再必要时追问CLI、API、SDK、插件、服务或MCP；不能只收集偏好投票 |
| Studio模块与Code组合 · H5／H6 | 请演示或回忆最近一次在二者之间切换的任务。为什么切换？带走了哪些上下文？什么需要重做？ | 高频模块与仅用过模块；工程基础能力与AI能力；产品版本和网络／设备条件 |
| 跨平台 · H5 | 在另一个您做过的平台，相近任务怎样完成？哪个条件不同？ | 尽量匹配任务、熟悉程度与环境；不把平台名或单次体验直接归因于设计 |
| 先锋与影响力 | 最近尝试的新方式解决了什么旧办法不能解决的问题？有没有试过后放弃？最近一次他人采用建议后，发生了什么？ | 新奇偏好与实际收益；个人经历、他人反馈与研究者解释分别记录 |

### 4. 条件性体验评分 · 5分钟

仅向最近4周用DevEco Code做过实际任务的用户展示。锚定刚刚回溯的任务和版本，先独立选分，再追问依据；不在访谈开始时评分，以免引导后续叙述。

统一选项：1 很不满意；2 不太满意；3 一般；4 比较满意；5 很满意；未使用／不适用；记不清。

- 对这次用DevEco Code完成任务的整体体验，您有多满意？
- 对开始任务前准备、导入和确认所需内容的体验，您有多满意？
- 对执行过程中了解进展、判断是否需要介入及控制修改的体验，您有多满意？
- 对检查结果、发现问题并继续修改的体验，您有多满意？

每项追问：哪件具体事情让您选这个分数？如果改善一件事，您会选什么？允许答“没有需要改善的地方”。没有体验过的环节选不适用，不记零分。

停用者可回顾最后一次实际任务并单独标为历史评分，不与近期分数合并；仅试用者只描述试用经历。评分用于追问和本轮描述，报告标明每项实际回答人数、版本和使用阶段，不计算总体满意度或未经设计的NSS指标。

### 5. 优先事项与收尾 · 5分钟

- 回到刚才的实际工作，如果先改善一件事，您会选什么？影响哪个任务，为什么优先？
- 有哪些目前做得顺畅、希望保留的地方？还有什么我们漏问了？
- 如后续有与本次经历相关的研究，是否愿意另行收到邀请？不影响本次参与。

确认礼品约定、联系渠道及撤回方式。不要向参与者承诺功能一定上线或某个版本一定交付。

## 四、5W2H关键事件追问卡

| 维度 | 中性问法 |
|---|---|
| What | 当时要完成什么？实际结果是什么？ |
| Why | 为什么当时决定这样做？当时还有哪些选择？ |
| Who | 哪些人或工具参与，您亲自负责哪一步？ |
| When | 大约什么时候、什么版本？哪个步骤前后发生？ |
| Where | 在什么设备、工具入口、工程或协作环境中？ |
| How | 先做什么、再做什么？用了哪些资料？怎样检查和恢复？ |
| How much | 大约花了多少时间、重复几次、影响谁？这是记录还是回忆估算？ |

只追问缺失且与研究问题有关的信息。避免“是不是很难用”“是不是希望自动完成”“这个方案会不会提高效率”等预设判断。

## 五、形成性任务测试模块（R2／R3）

每轮选1–2个目标场景，先安排5–8位相近目标用户。任务从访谈中抽取，预测试后固定起点和成功标准；完成一轮后先修订，再进入下一轮。同一场可含简短背景访谈，但不把完成统一任务误称为自然情境观察。

| 候选任务 | 给参与者的任务表达（按真实场景改写） | 研究员观察／预定完成条件 |
|---|---|---|
| T1 开始首个任务 | 给定一份允许分享的工程与修改目标，请按您平时的方法做好准备并开始完成它。 | 是否识别必要资料和环境；能否形成可执行任务并得到约定的可运行结果；记录遗漏、帮助与重做 |
| T2 执行判断与接续 | 在任务处理过程中，需求出现一项变更。请按您认为合适的方式处理，并确认可以继续。 | 是否理解当前状态、变更影响与修改范围；能否暂停／调整／恢复；具体能力以受测版本支持为准 |
| T3 验收与继续修改 | 这里有一次任务的交付结果，请判断是否满足给定要求；如仍有问题，请继续处理到可交付。 | 能否识别预先核定的问题、未验证项与证据缺口；是否完成相应检查和复验；不能只听AI自报成功 |
| T4 既有工具链接入 | 请在允许的测试环境，把一项鸿蒙构建或验证能力接入现有工作流，并查看执行结果。 | 是否完成调用、得到可解释结果、定位失败并接回原流程；仅邀请实际相关岗位 |
| T5 Studio与Code衔接 | 请用您熟悉的组合工具完成一次修改、运行与检查，并回到后续修改。 | 切换、信息传递、重复配置、模块可发现性及任务结果；不规定用户必须采用某种入口 |

每张任务卡记录：任务编号、关联H／RQ、用户画像与熟练度、起点工程、版本与环境、给用户的说明、成功标准、已知问题／正确答案、停止与协助规则、预估时长、观察字段、预测试修订。

记录独立完成／协助后完成／失败或退出；客观计时从理解任务后开始操作，到达到标准或退出为止。环境等待、故障及主持干预单独记；思考出声对耗时的影响须说明，不将形成性场次直接作为生产效率基准。

每项任务结束后可问“刚才这项任务完成起来有多困难或容易？”使用7点难易选项（1非常困难、7非常容易），再追问原因。此题与访谈中的5点满意度不同，不能混算为同一指标。

R4综合评估先固定目标、任务、版本、评分和协助口径，再按10–12人的暂估工作量安排；如要比较版本效果或推断总体，先确定抽样、误差、差异及组间／组内设计，重新估算样本。参与过旧方案者单独标记，警惕练习效应。

## 六、观察、日志与小组的补充模块

情境观察：请用户按平时方式做一项真实任务，记录工具切换、寻找资料、等待、手工补救及协作；不擅自操作其环境，不将观察到的沉默或表情当作感受。无法展示时可口述或使用脱敏材料，并标记证据类型。

事件日志：仅在需要跨日证据时邀请4–6人，记录7–14天；字段为日期、任务与版本、预期、实际行为、人工介入、结果及当时想法／感受，每条约3–5分钟。没有事件可以记录“无”；不要求每天编一条。结束后通过回访核验，区分记录与补记。

小组讨论：完成个人访谈后按需组织同类角色4–6人讨论机会或接入边界；先个人书写再轮流表达，避免上下级混组。讨论记录按个人编号整理，群体共识不能代替行为证据。

## 七、Bottom-up整理、历史对照与产品行动

| 步骤 | 处理与产物 |
|---|---|
| 事件卡 | 来源编号、日期、任务、版本、Do、Think、Feel、结果、影响、原始位置；标记自发／追问／方案刺激和本人／转述 |
| 编码与聚类 | 从原话和行为归纳标签，形成主题；复核关键证据及反例，不只按既有规划标题装材料 |
| 分层旅程 | 比较P1–P3、岗位、产品使用阶段、熟练标签和来源，解释任务条件，避免把人群差异直接归因于规模 |
| 历史复核 | 六月证据与本期事件逐条对照：仍存在、缓解、已解决、转变、证据不足；没有再提及不等于解决 |
| 假设判断 | H1–H6逐项标支持、部分支持、反证或证据不足；新主题补入研究问题台账 |
| 行动建议 | 明确近期修复、BP候选、客户专题、引导优化、继续验证或暂缓；记录负责人、节点、依赖与复测标准 |

每批结束检查新增主题与缺失人群，不仅看是否达到人数。旧资料不能与新访谈直接合并算频率；小样本任务完成数和评分须标分母与条件。研究报告区分用户原话、观察事实、解释和规划建议。

行动记录模板：问题／假设编号 → 适用用户与任务 → 证据及反例 → 影响 → 候选行动 → BP／版本／展会节点（待确认可标待确认）→ 负责人 → 依赖 → 验证任务 → 状态及决策理由。

## 八、每轮执行与资料交付

评测前完成需求对齐、场景与任务设计、环境和记录准备、内部预测试，并并行招募预约；评测中逐场执行和当天复盘；评测后完成编码分析、报告、产品行动评审与下一轮安排。礼品按参与约定发放，可在完成参与后启动，不以观点好坏或正负评价为条件。

公开材料仅保留计划、提纲和空白规则。真实答卷、录音、联系方式和礼品登记保存在团队受控位置；每人统一编号，重复研究只增加场次。研究终止或不愿后续参与者停止邀约。
