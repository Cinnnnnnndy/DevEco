# 鸿蒙开发者分阶段访谈提纲

2026-11-19 · 研究员执行版

以最近一次本人做过的鸿蒙任务为例，了解鸿蒙开发与通用开发的差异、要给 AI 输入什么，以及用什么 Spec 或规范保证产出符合需求。

常规访谈约 75 分钟。资深开发者深访可根据案例深度延长，单场最长 90 分钟，预约时确认时长。

| 环节 | 常规访谈 | 资深开发者深访上限 |
|---|---:|---:|
| 开场与背景核对 | 10 分钟 | 10 分钟 |
| 开发准备 | 8 分钟 | 10 分钟 |
| 编码与 AI 协作 | 14 分钟 | 18 分钟 |
| 构建与调试 | 7 分钟 | 9 分钟 |
| 测试与验收 | 10 分钟 | 12 分钟 |
| 签名与交付 | 4 分钟 | 5 分钟 |
| 差异深挖 | 4 分钟 | 5 分钟 |
| Code 评分（适用者） | 3 分钟 | 3 分钟 |
| 其他专题与产品方向 | 10 分钟 | 13 分钟 |
| 收尾 | 5 分钟 | 5 分钟 |
| **合计** | **75 分钟** | **90 分钟** |

预约时选定时长。深访优先追问 AI 输入、Spec、产出检查和跨平台对照。不评分时，3 分钟并入其他专题。

超时按这个顺序删减：同一文件协作 → AI 无人看管时的持续执行 → 无界面产出的检查 → 产品方向。始终留足最后 5 分钟收尾。

## 主持方式与选问路径

先读取招募台账中的“访谈带入卡”，再让受访者自由讲 Q05–Q07 对应的最近一次本人鸿蒙任务。不要重新逐题询问问卷，也不要从非鸿蒙经历开始讲任务。先问当时的判断和感受，最后按需展示概念。等受访者讲完，再用功能清单帮助回忆。至少选一个关键事件问清当时发生了什么、本人怎样处理、结果怎样。

问题分三层。未加标签的是必问。「差异先问」「鸿蒙清单提示」「AI 协作时再问」「AI 产出时再问」按条件问，条件符合时也是必问。「深访优先」在常规访谈中通常跳过，「按需」在时间充裕或案例相关时再问。

主干必问最近任务、实际流程、关键卡点、验收依据和首要改善。根据本人职责跳过未参与的阶段。下表帮助主持人选择分支，兼任者按本次任务选最贴合的一行。其他受访者沿通用主干提问。

| 问卷带入信号 | 访谈处理 |
|---|---|
| Q05–Q07 的本人鸿蒙项目、时间和工作环节 | 作为整场访谈主线；开场先核对任务仍准确，再沿其实际参与环节提问。 |
| Q08 有其他平台同类任务 | 各阶段先对所有人开放问「差异先问」，有此经历者再点名对照平台追问；没有此经历不问假设题。 |
| Q09–Q10 Studio 使用与模块 | 仅追问受访者实际使用过的 Studio 环节。 |
| Q11 Code 状态、Q12–Q13 AI 状态与工具 | 用过 AI／Code 才进入具体案例、评分或对比；未用者了解现有做法，不要求评价未体验产品。 |

| 受访者 | 开场确认 | 优先追问 |
|---|---|---|
| 高频使用 AI 的资深开发者 | 带入近期 AI 使用频率和项目经历，确认本人用 AI 完成过哪项鸿蒙任务。 | 优先追 AI 输入、Spec、工具切换和验收。有同文件编辑再问写入与冲突，有双工具同类任务再做竞品对照。 |
| 这次任务未用 AI 的开发者 | 确认实际采用的 IDE、终端、文档和协作工具。从未用过 Code 或其他 AI 工具时，记下是个人选择还是团队规定。 | 沿手工流程追环境准备、查资料、构建和验证。未采用原因放到「工具采用与停用」专题。 |
| 试用后放弃或已停用 Code／AI 的开发者 | 确认最后一次使用的时间、入口（独立 Code、Studio 内置 AI 或其他工具）和版本，以及停用前用它做的那项鸿蒙任务。 | 开发旅程沿停用前最后一次任务还原卡点，再简要了解现在的替代做法。专题固定选「工具采用与停用」，只问停用原因和重新试用的条件。历史评价单列，不与近期使用者合并。 |
| 学生／学习者 | 选本人实际做过的一个练习工程，核对当时用过的教程或帮助。 | 重点问从准备环境到首次运行、怎样理解和处理报错、怎样确认做对。交付段可问练习成果如何验收或分享。 |
| 工具链／平台人员 | 选本人参与接入或维护的一条鸿蒙流水线。 | 沿提交到产物问构建、测试、签名和交接。找出仍需人工介入的步骤、现有绕过方式和接入条件。专题优先选「头部厂商工具链接入」。 |
| 华为内部 DevEco 用户 | 不填外部问卷，开场逐题问背景核对题（见下节）。确认使用的是内部版本还是公开版本，以及配套的内部工具与平台。 | 追内部规范、工程模板和内部平台怎样交给 AI。每个问题都区分是产品本身的问题还是内部环境特有的问题，外部开发者没有的条件单独记录。 |

## 开场与背景核对

常规约 10 分钟，分三步：说明与授权约 2 分钟，背景核对约 4 分钟，选定本次任务约 4 分钟。

**第一步　说明与授权**　说明研究用途，并分别确认记录、录音和录屏许可。

**第二步　背景核对**　外部受访者开场前带入问卷第 1–13 题，用第 14 题的参与意愿协助预约，标出缺项和变化。核对时只问缺项、前后矛盾或可能已变化的题，用「问卷里您选的是……，现在还是这样吗？」带出，不整套重问。内部受访者不填外部问卷，邀约时请业务团队提供所在团队、工程体系和岗位，开场逐题问完。

「鸿蒙经历」中的开始原因和学习途径问卷里没有，内外部受访者都要完整问。两类受访者的回答都按对应题号记入台账，与问卷答案不一致时以访谈核实为准，并标注「访谈更正」。

| 背景 | 核对问题 | 对应问卷题与记录 |
|---|---|---|
| 团队与岗位 | 您现在在哪个团队、负责什么岗位？<br>团队里大概多少人做研发，这个项目有多少人？ | Q01–Q04。内部受访者补问所在业务团队和使用的工程体系 |
| 鸿蒙经历 | 您参与过几个鸿蒙项目？什么时候开始做鸿蒙的？<br>做鸿蒙是公司或项目要求，还是您自己选的？<br>主要靠什么学会鸿蒙开发，例如官方文档、课程、同事带、示例工程，还是问 AI？ | Q05–Q06 核对项目数和最近任务时间。记下鸿蒙年限、开始原因和学习途径，分析时用来解释差异从何而来 |
| 其他平台经历 | 做鸿蒙之前，您主要做哪个平台的开发？<br>类似的事情，您在安卓、iOS、Web 或其他平台上亲手做过吗？做的是什么？ | Q08。记下原平台和一项具体的同类任务，供各阶段的差异追问使用 |
| 工具使用 | 最近 4 周用 DevEco Studio 多吗，主要用哪些功能？<br>用过 DevEco Code 吗？用的是独立的 Code，还是 Studio 里的 AI 功能？<br>最近 4 周用 AI 辅助开发大概每周几天，最常用哪款工具？ | Q09–Q13。Studio 内置 AI 与独立 Code 分开记。只是试过或已不用 Code 时，记下最后使用时间，转入停用者路径。AI 使用情况决定是否做 Code 评分和工具对比 |

**第三步　选定本次任务**　核对时已讲清的内容不再重复问。

| 任务 | 开场问题 | 记录 |
|---|---|---|
| 任务与分工 | 请选最近一次亲自参与的鸿蒙任务，当时要完成什么，您负责哪一段？外部看近 6 个月，内部看近 3 个月，正在做的首个项目也算。<br>这项任务需要和哪些人或岗位配合？ | 以 Q07 的主要工作为起点。记下任务、本人职责和协作岗位 |
| 开发方式与设备 | 这次是原生开发、已有应用迁移，还是跨平台适配？主要面向哪些设备，例如手机、平板、手表、电脑、智慧屏或车机？<br>有没有用到鸿蒙特有的能力，例如跨设备协同，或调用相机、定位、通知等系统能力？ | 记下开发方式、目标设备、主要技术栈和相关鸿蒙能力 |

## 一、沿用户的开发旅程提问

请用户按实际顺序讲同一项任务，跳过本人没有参与的阶段。每个阶段按表中顺序问：

1. 先问未加标签的核心问题，让受访者把这一段讲完。
2. 再用「差异先问」开放问有没有不一样的地方。有其他平台同类经历的人，再点名对照平台追问。
3. 受访者没提到时，最后才用「鸿蒙清单提示」提示。

记录差异是「自发」还是「提示后」提到的，避免只验证我们预想到的差异。AI 相关追问按案例选。未用 AI 的案例，沿实际工具和手工步骤了解材料来源、协作规则和检查方法，并核实当时的工具条件与团队使用规定。

> **研究员用语提示**：不要求受访者理解 SDK、API、依赖等术语。可换成“项目要支持的系统版本”“要接入的功能”“项目里已经在用的库或组件”等日常说法；需要时再用括号举例确认。

| 开发阶段 | 核心问题与按需拓展 | 记录重点 |
|---|---|---|
| 开发准备 | 动手之前，您手里已经有什么，还准备了什么才开始？<br>这些材料分别是谁准备的，怎样交给您或 AI 的？例如放在工程里、发链接、复制粘贴，还是口头说明。用了 AI 的话，又手动给它补了什么？<br>差异先问　这些准备跟您以前做开发时比，有没有不一样的地方？有其他平台经历时再问：在安卓、iOS 或 Web 项目里要准备哪些？哪些是鸿蒙多出来的，哪些在鸿蒙上更难拿到？<br>鸿蒙清单提示　开始前有没有要先确定的内容，例如要支持的设备、系统或 SDK 版本、权限、签名配置？需要的三方库有没有现成的鸿蒙版本？哪一项最容易缺，缺了怎么办？<br>按需　哪些内容每次都要重新跟 AI 或同事解释一遍？ | 需求、设计、代码、鸿蒙文档、SDK／API 版本、依赖、签名配置、设备和权限。记录材料来源、准备人、交接方式与缺项影响，反复解释的内容和可从工程或平台补齐的内容，以及缺少鸿蒙版本的库或组件和替代做法 |
| 编码与 AI 协作 | 从拿到任务到做出第一次改动，您当时怎么做的？<br>这次您怎么确定改动范围、要遵守的工程规则，以及做到什么算完成？<br>改动偏离要求，或者您中途改了要求时，您是怎么发现的，又怎么让 AI 或自己改回来？<br>AI 协作时再问　AI 给的鸿蒙代码有没有用错 API、用了旧版本写法，或者写成了安卓、前端的写法？您是怎么发现的？<br>差异先问　写这部分代码，跟您以前做开发时比有没有不一样？有其他平台经历时再问：同类功能在那边写起来有什么不同？在那边用 AI，表现和在鸿蒙上一样吗？<br>鸿蒙清单提示　写界面、调用系统能力或适配设备时，有没有要查鸿蒙文档、示例或 API 说明的地方？卡住时去哪里找答案，找到了吗？找到的教程或示例和您用的版本对得上吗？<br>深访优先　这次有没有让 AI 在您没盯着的时候继续做，例如去开会、处理别的事或下班？回来后您怎么知道它做到哪一步、改了什么、有没有卡住？<br>深访优先　回忆一次 AI 和您先后改同一个文件的经历。AI 的修改怎样写入？您手动改完后再请 AI 接着做，怎么确认您改的内容还在？ | 记录工具分工、切换原因、需求和规则如何传递、修改范围、人工确认与恢复，以及 AI 写错鸿蒙 API、版本或沿用其他平台写法的实例。记录查资料的去处与结果。无人看管时记下离开时长、回来后的核对方式和恢复办法。同文件协作时记下改动来源、确认方式、版本同步和冲突提示 |
| 构建与调试 | 拿到初版代码后，您怎样构建并跑起来？<br>出现错误时，您怎样找到原因并修好？<br>差异先问　排查这类问题，跟您以前做开发时比有没有不一样？有其他平台经历时再问：在那边遇到类似报错时您怎么排查？在鸿蒙上哪一步更费时间？<br>鸿蒙清单提示　报错有没有和 SDK／依赖版本、构建配置、设备连接或权限有关？您先看哪里，例如构建输出、日志或设备提示？拿报错去搜，能搜到答案吗？ | 首次构建结果、报错依据、重试次数、等待与返工。记录 SDK、依赖、构建配置、设备连接和权限等鸿蒙工程条件，以及报错能否搜到答案。区分现场记录和回忆估计 |
| 测试与验收 | 您这次做了哪些检查，怎么判断结果符合需求和规范？<br>发现问题后，谁来改、改了几轮，最后怎样再次验证？<br>AI 产出时再问　检查 AI 写的代码时，有没有发现多余、重复或不符合团队规范的地方？是自己看出来的，还是靠代码检查工具或构建告警？<br>差异先问　这些检查跟您以前做开发时比，有没有不一样？有其他平台经历时再问：在那边做同样的验证需要哪些设备或环境？鸿蒙多了或少了什么？<br>鸿蒙清单提示　预览、模拟器和真机分别检查了什么？要支持手机、平板、手表或其他设备时，有没有需要分别验证的地方？<br>按需　如果产出没有界面，例如接口逻辑、脚本或配置，您怎样检查它是否正确？ | 代码质量与规范、业务逻辑、单元测试／自动化／真机手动验证等实际证据。记录冗余与规范问题的类型、发现方式和工具，二次修改的轮次和执行人。记录预览、模拟器、真机和多设备验证的分工，以及未验证项和复验条件 |
| 签名与交付 | 验证完成后，您怎样把结果交给同事、交付系统或发布平台？哪些步骤需要人工处理或切换工具？<br>差异先问　这一步跟您以前做开发时比，有没有不一样？有其他平台经历时再问：和安卓、iOS 的打包、签名、上架相比，鸿蒙哪一步不同，影响有多大？<br>鸿蒙清单提示　打包、签名或发布准备时，有没有卡在证书、权限、应用包配置或审核材料上？最后交给谁、怎么确认可以继续？ | 签名、打包、审核、结果回传和实际交付终点。记录证书、权限、应用包配置和发布准备中的人工步骤 |

## 二、差异深挖（任务讲完后，必问）

紧接开发旅程问，趁受访者对刚讲的细节还有印象。从各阶段提到的差异中选影响最大的一处：

- 刚才您提到了几处不一样，哪一处对这次任务影响最大？具体多花了什么，时间、返工还是找人？
- 您觉得这处差异主要因为什么：鸿蒙本身就要求这样做，资料和三方库还不够多，工具不好用，还是团队自己的条件？
- 哪些做法可以从其他平台直接沿用？

没有其他平台经历，或各阶段都没提到差异时，改问「您觉得鸿蒙开发最不像其他开发的地方是什么？依据是哪次经历？」，按态度证据记录。

## Code 评分（适用者）

近 4 周实际用 Code 做过鸿蒙任务的用户，在差异深挖之后评分。先请受访者连续给出这次任务的整体、准备、过程控制和结果检查四项分数，采用 1–5 分并提供“不适用／记不清”。再只追问最高分和最低分两项的理由，各用刚讲过的一个具体事件说明。停用者的历史评价单列。不适用者跳过本节，时间并入其他专题。

## 三、其他专题与产品方向

常规访谈按受访者路径选一项专题，再选一项产品问题；深访可各选两项。停用、放弃和从未使用 Code／AI 的受访者，专题固定选「工具采用与停用」。同一案例能回答多个问题时合并问。

| 专题 | 问题 | 适用对象 |
|---|---|---|
| 头部厂商工具链接入 | 沿现有 Agent、CI 或测试平台，开发、测试、鸿蒙专项验证和发布还缺哪些能力？<br>哪些能力希望开箱即用，哪些需要接到自己的流程里？具体通过 CLI、API／SDK、插件还是服务提供更合适？ | 工具链、平台和相关一线岗位 |
| Spec 与规范复用 | 刚才提到的工程规则和完成标准现在写在哪里？哪些能跨项目复用，哪些要为鸿蒙补充？<br>规则变更后由谁更新，协作的人或 AI 怎样拿到最新版？ | 用过任务规范、团队规则或验收约定者 |
| 工具采用与停用 | 您最开始是怎么用上，或者决定不用 Code／这款 AI 工具的？是自己决定还是团队要求？<br>后来为什么不用了？出现什么变化会让您再试一次？ | 试用后放弃、已停用或从未使用 Code／AI 者。停用前的任务已在开发旅程中讲过，这里不再重复。从未使用者只问第一问和「什么变化会让您试一次」。记录决定人、时间、版本和入口，区分本人经历与听说 |

### 按实际经历选问产品方向

| 关注点 | 访谈问题 | 适用经历与记录 |
|---|---|---|
| IDE 与轻量工作方式 | 这次有哪些步骤实际只用到了简易编辑器、终端或对话工具？反过来，哪些步骤离不开 IDE，用的是它的哪项能力？<br>展示轻量方案后，问受访者会用它尝试哪一步，以及完成那一步需要什么能力。 | 记录实际做过的步骤、用到的 IDE 能力、替代做法与切换条件。学习者以当前练习为例，平台岗位重点谈命令行或接口接入。 |
| DevEco Code 与其他工具的对比 | 您用 DevEco Code 和另一款 AI 工具分别做过什么相近任务？<br>在同一个环节，两款工具的做法和结果各是什么？ | 亲自用过两款工具做相近任务者。按案例选 1–2 项记录，例如代码质量、鸿蒙 API、工程上下文、得到可用结果的耗时、IDE 集成或修复验证。只有单边经历时记录现用做法。 |
| 独立 Agent 的交互方式 | 回到刚才的任务，您希望在哪一步得到独立 Agent 的帮助？<br>这一步您希望同时看到或操作什么？ | 先让受访者描述，再按需展示独立对话、内联、侧栏、分屏和终端入口。可选最适合这一步的一两种，也可提出自己的方式。 |

若受访者没有同文件协作经历，可在产品方向时间用一张统一示意图了解其希望怎样查看和确认 AI 改动。记录其选择及理由，作为后续原型验证的输入。

## 四、收尾

- 如果只能先改善一个环节，您选哪一步？
- 怎样判断这个问题已经解决？

记录优先环节、实际影响和验收条件。需要后续验证时，另行确认参与意愿及可用的脱敏材料和设备。

每个环节先问实际行为，再记录判断、感受与结果。用具体事件核实时间、操作、证据和成本，访谈后按三项研究目标归纳。

## 附：鸿蒙与通用旅程差异的整理方法

访谈后，把每条提到差异的事件按下面两个维度打标签，再按开发阶段汇总。

| 差异类型 | 含义 | 例子 |
|---|---|---|
| 通用 | 各平台都一样，不是鸿蒙特点 | 需求理解、代码评审、业务逻辑测试 |
| 鸿蒙放大 | 步骤相同，但在鸿蒙上更难、更慢或更常出错 | 查文档、找三方库、搜报错答案、AI 写错 API |
| 鸿蒙特有 | 其他平台没有，鸿蒙多出来的步骤 | 一次开发多端部署的适配、元服务、鸿蒙签名配置 |

| 差异原因 | 含义 | 对应的产品行动 |
|---|---|---|
| 平台机制 | 鸿蒙的设计本来就要求这样 | 用引导、模板、自动检查降低成本 |
| 生态成熟度 | 资料、三方库、社区答案、AI 训练数据还不够，会随时间改善 | 补知识库、示例和 AI 上下文；判断要不要等生态成熟 |
| 工具 | DevEco Studio 或 Code 的能力或体验问题 | 进入产品改进 |
| 团队条件 | 团队规范、工程基础或内部平台造成 | 形成专项支持，不作为普遍结论 |

每条记录同时注明对照平台、对照任务、自发还是提示后提到。没有其他平台经历的受访者，只作为鸿蒙一侧的证据。

汇总成一张旅程对照图：每个阶段写通用做法、鸿蒙差异、差异类型、原因和证据人数。通用一侧可以用已有竞品分析和通用开发者研究补充，不必全靠访谈。

## 附：第2–4轮任务评测：从真实鸿蒙场景抽题

每轮选1–2个场景，先做5–8人。使用可公开或脱敏的鸿蒙测试工程；在预测试中核对版本、依赖、设备和已知问题，明确成功、协助与退出标准。

| 任务卡 | 给用户的目标示例 | 研究员检查什么 |
|---|---|---|
| T1 工程准备与首次跑通 | 接手一个鸿蒙工程及明确的小功能需求，按平时方式准备并完成首次可运行修改。 | 依赖、SDK／API及工程规则是否明确；能否找到材料、完成构建并在指定环境运行。 |
| T2 ArkUI修改与反馈 | 根据设计参考调整指定页面和一项交互，在约定设备检查效果，再继续修改。 | 设计表达、Code与Studio切换、预览／运行分工、交互与逻辑是否满足要求。 |
| T3 错误定位与修复 | 一个鸿蒙工程在构建或设备运行中出现已核定的问题，请定位、修复并证明通过。 | 能否找到错误依据、区分原因、交回AI或手动修复，并在同一场景复验。 |
| T4 鸿蒙能力接入 | 在隔离测试环境，将一项鸿蒙构建或设备验证能力接入现有脚本／流水线，查看结果并处理一次失败。 | 调用、权限、状态、日志、结果回传与恢复；只邀请实际相关岗位。 |
| T5 验证与发布准备 | 对已完成的鸿蒙功能判断是否可以交付，完成约定设备检查和签名／打包准备。 | 是否识别未验证项、找到发布条件并完成交接。使用测试证书与账号，终点止于约定准备，不向生产商店提交。 |

任务来自前轮实际问题，不要求产品具备未发布能力；企业和个人、初次与熟练用户按任务分别安排。R3记录是否见过旧方案，R4固定版本和任务后再评价表现。

记录独立完成、协助后完成或失败／退出，以及关键错误、人工介入、耗时与设备结果。环境等待和主持帮助单列；任务后可用1非常困难至7非常容易的难易评分并追问原因。它与5点满意度分别统计。

10–12人是阶段综合评估的工作量估计。若要量化推断或比较版本效果，需重新设计样本与指标，不能直接用形成性场次证明效率提升。

## 附：情境观察

情境观察直接看用户如何处理真实鸿蒙工程、Studio 模块、Code 及设备。分别记录用户回忆和现场看到的操作。

**选谁**　第 1 轮从受访者中选 4–6 人。优先选能展示真实或脱敏工程的人，高频 AI 用户、工具链／平台人员和学习者各争取至少 1 人。

**怎么安排**　并入访谈时，由受访者现场演示能展示的阶段，约 20–25 分钟，替换开发旅程中对应阶段的口头回溯；其余阶段照常口头问，补充专题缩为 1 项。另约时安排约 60 分钟远程共享屏幕或现场观察。预约时确认可展示的工程、设备和录屏许可；不要求现场完成真实提交或发布。

**主持原则**　先看后问，少打断。受访者停顿、切换工具、撤销或返工时记下时间点，演示结束后对照时间点追问当时在想什么。不替受访者操作，也不提示功能位置。

| 观察点 | 看什么 |
|---|---|
| 工程与环境 | 打开工程后先做什么；怎样确认 SDK 版本、依赖和设备状态 |
| 给 AI 的输入 | 实际粘贴、引用或附加了什么；规则文件和需求材料放在哪里、怎样拿到 |
| 工具切换 | 在 Studio、Code、终端、浏览器文档和其他工具之间的切换点与原因 |
| 构建、运行与设备 | 构建和运行的方式；看哪些日志或提示；预览、模拟器和真机怎样分工 |
| 检查与修改 | 怎样查看 AI 的改动；接受、拒绝、回退或手动修改的依据 |

记录时给现场操作加时间戳，标注「现场观察」，与受访者口述分开。

## 附：记录与执行容量

每场按参与者编号整理阶段事件，保留原始位置、本人经历或转述、自发或追问等标记。旧问题按仍存在、缓解、已解决、转变或证据不足复核；未再提及不等于解决。

两位交互各30%，执行周约2场；具体人数、周期及四轮工作安排以研究计划时间线为准。方案修改和版本等待另排，下一轮是否启动由阶段评审决定。
