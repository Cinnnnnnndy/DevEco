鸿蒙开发者用户研究计划

围绕不同规模团队的鸿蒙开发场景与 AI 使用方式，规划第一期半年访谈，并建立持续收集用户需求的机制。

立项阶段拟深访 50 人第一期：2026.11—2027.04样本、排期与预算待立项确认
计划概览一、背景与目的二、初期访谈目标三、研究问题四、样本规划五、方法与提纲六、招募安排七、实施时间线八、预期产出九、常态机制立项待确认

计划概览

  1. 研究对象：参与鸿蒙应用开发的企业团队、初创团队、个人开发者及生态伙伴，兼顾不同工程体系和 AI 使用程度。
  2. 研究重点：拟面向互联网头部厂商、非互联网中大型企业、初创团队及个人开发者，梳理不同工程体系下从开发准备、编码实现、测试验证到签名上架的真实流程，并比较鸿蒙与安卓、iOS 的开发体验差异；重点了解头部厂商现有工具链在开发、测试与交付环节需要哪些通用及鸿蒙特有能力，以及这些能力适合以接口、SDK、CLI、插件或服务等何种形式接入；进一步探索各类客户进入 AI 开发前需要准备和导入的需求、设计、代码、知识与工程规则，以及任务、工具调用和验收等生态 Spec 的要求，同时了解 AI 协作中的需求交代、过程控制、代码冗余与规范检查、二次编辑和结果验收问题。
  3. 实施方式：拟以 50 人半结构化访谈为主，结合真实任务回溯；现场观察、日记研究、问卷与原型测试按阶段需要补充。
  4. 决策用途：为 DevEco 体验优化、27X 需求优先级、不同客户的工具支持方式提供用户依据。
  5. 计划节点：拟于 12 月提交首轮访谈快报、2027 年 2 月提交中期报告、4 月提交第一期研究报告，后续转入常态访谈。

一、背景与目的

面向鸿蒙生态发展与 AI 驱动的开发方式转变，拟对互联网头部厂商、非互联网中大型企业、初创团队及个人开发者开展分层访谈，比较鸿蒙与安卓、iOS 的开发体验，梳理不同工程体系下开发、测试、验证及上架的真实流程，重点探索头部厂商所需的通用与鸿蒙特有能力及其接入形式、各类客户进入 AI 开发所需准备和导入的内容与生态 Spec 要求，以及 AI 任务控制、代码质量和二次编辑问题，为 DevEco 体验优化、能力开放与后续产品规划明确重点场景和需求优先级。

业务背景

生态发展带来多样化开发需求

结合前期体验规划材料，需要进一步了解不同类型开发者的应用目标、工程条件和工具选择，明确 DevEco 可以支持的关键场景。

体验背景

AI 正在改变开发任务的分工

前期规划关注从人工指挥到 AI 承接任务的变化，本次拟了解开发者如何交代需求、跟进执行、检查代码与验收结果，以及哪些环节仍需人工处理。

立项必要性

产品方向需要真实场景支撑

拟扩大团队类型与使用阶段的覆盖，补充企业工具链和非重度 AI 用户的视角，形成可追溯的需求依据，支持后续规划取舍。

背景参考：DevEco 体验规划与创新 Keynote 配套主线及逐页文稿、2026-10-29 规划探讨与用研交流记录，以及补充的领导建议。既有规划中的「托付得放心 / 验得了 / 接得进」作为后续分析参照；访谈先从用户自身任务与经历展开。

G8 梳理 AI 开发准备与规范不同客户进入开发任务前需要准备和导入什么，哪些可复用、哪些需平台补齐；需求、工程、工具调用和验收 Spec 如何衔接。明确分客户的准备清单、支持条件与待定义的规范。

三、拟探索的研究问题通过真实任务了解差异及其成因

编号核心问题访谈追问方向对应目标
RQ1 用户与项目谁在开发鸿蒙应用，为什么做，项目希望达到什么目标？角色、团队分工、开发经验、业务目标、项目阶段与工程规范。G1
RQ2 开发全流程最近一次项目从准备到交付是怎样完成的，哪里顺畅、哪里受阻？环境、文档、编码、构建、调试、设备验证、签名与上架；频次、耗时、影响和替代办法。G2
RQ3 AI 的使用边界哪些任务会交给 AI，哪些不会，原因是什么？采用与放弃的实例、需求输入、长任务跟进、人工介入、权限与改动恢复。G3
RQ4 代码与结果验收如何判断 AI 产出的代码和应用可以交付？代码冗余、规范检查、审查与二次编辑；编译、测试、真机与多设备验证、后续维护；谁负责验收及返工。G2、G3
RQ5 平台体验差异相近任务在鸿蒙、安卓、iOS 或 Web 上有哪些异同？知识获取、迁移成本、依赖库、工具链和发布；结合具体任务区分平台、经验与项目差异。G4
RQ6 团队与接入方式不同工程体系如何组织开发，现有工具之间如何衔接？对比互联网企业、传统行业与个人的工程条件；IDE、自研 / 第三方 Agent、接口、插件和 CI 的配合；现成产品与能力接入的选择依据。G1、G5
RQ7 需求优先级如果只能改善一个环节，开发者最希望先解决什么？影响范围、发生频率、解决成本、紧迫性；开放回答后再讨论候选方向，允许提出规划外需求。G2、G5
RQ8 后续研究条件哪些任务适合进一步观察、测量或方案测试？复访意愿、数据可得性、脱敏材料、设备条件与可配合的时间。G6
RQ9 头部厂商能力需求互联网头部厂商的现有工具链在哪些环节需要鸿蒙支持，能力应怎样提供？按流程区分通用开发、测试、鸿蒙特有及发布能力；了解调用方、输入输出、接入限制与候选提供形式。G5、G7
RQ10 AI 开发准备不同客户启动一次 AI 开发任务前，需要准备和导入什么？需求 / 验收、设计、现有代码、接口、团队规则、知识、依赖环境、工具及授权条件；谁准备、放在哪里、如何更新。G1、G8
RQ11 生态 Spec 与协作现有规范如何传递给 AI 和工具，哪些规范能够复用，哪些仍有缺口？任务 Spec、工程规则、工具能力描述、调用契约、验证与验收、版本兼容；区分客户约束、生态规范和鸿蒙补充要求。G7、G8

比较鸿蒙与其他平台时，仅向有相应经验的受访者追问；记录工具版本、项目复杂度和使用经验；自述的平台差异作为经验线索，需结合可比任务进一步核实。需求差异拟同时从行业、团队规模与工程成熟度分析。

专题 A · 互联网头部厂商的工具链与能力提供形式

拟邀请企业研发工具链 / AI 平台负责人及一线开发、测试人员，结合最近一次交付画出现有流程，再逐项核实能力缺口与接入条件。

流程环节拟核实的能力范围候选形式 · 访谈后判断重点追问
开发准备与编码环境与工程初始化、文档 / API 知识、依赖、代码生成与调试；区分通用开发能力和鸿蒙工程约束。CLI、SDK / API、IDE 插件、知识服务、工程模板。现有 IDE / Agent 如何获取上下文？哪一步需要鸿蒙支持，哪些已有内部能力？
构建与测试构建、静态检查、单元 / UI 测试、设备调度、性能分析及测试报告；了解现有 CI 衔接。无界面命令、测试 / 设备服务、CI 插件、结果接口。谁触发、如何判定成功、失败后怎样回到开发任务？需要什么诊断数据？
鸿蒙特有场景ArkTS / ArkUI、鸿蒙 API 与权限、多形态适配、跨设备协同 / 分布式等在真实项目中的使用与验证。平台工具接口、场景测试能力、设备服务、知识与规则包。项目实际用了哪些能力？现有通用工具覆盖到哪一步？缺口是否与鸿蒙相关？
发布与持续交付打包、签名、应用检查、上架和后续迭代；区分企业审批与平台发布流程。发布接口、CLI、流水线任务或现成操作界面。哪些步骤能自动化、哪些需人工审批？当前如何交接和定位失败？
贯穿全流程的 AI 调用Agent 如何发现并调用能力、接收状态和结果；任务权限、执行边界、失败恢复与审计。直接接口、MCP 工具封装、Skill 工作流说明或其他适配方式。企业实际支持哪些形式？执行位置、版本、权限与维护责任有哪些限制？

CLI、SDK / API、插件和服务用于讨论能力如何交付；MCP 用于讨论 Agent 如何调用工具，Skill 用于讨论任务步骤与知识如何组织，Spec 用于讨论约束与契约如何表达。它们可能组合使用，均为追问选项，不代表已确定的方案或已有能力。

专题 B · 不同客户进入 AI 开发前的准备与导入

客户类型拟了解的现有基础拟核实的准备 / 导入内容拟探索的平台支持
互联网头部厂商自研 / 第三方 IDE 与 Agent、内部知识、研发规范、CI 和测试平台。代码仓库、接口契约、团队规则、任务与验收 Spec、工具声明、设备及环境配置如何进入现有体系。哪些能力以接口接入，哪些内容需适配现有规范，哪些应由企业自行维护？
非互联网中大型企业自研与外包分工、现有开发平台、行业规范和部署要求。业务流程、现有工程、需求与设计、行业约束、团队规范、测试环境及交付标准由谁准备。现成产品、插件、模板、部署指导或能力服务，哪些适合实际工作流？
初创 / 小团队已有产品、跨平台经验、人员配置、第三方服务和工具选择。产品需求、设计稿、已有代码 / 依赖、接口、测试数据与发布条件如何整理并交给 AI。哪些准备可通过示例、模板、导入与检查流程减少重复工作？
个人 / 学习者开发经验、项目起点、可用设备、资料来源与常用 AI 工具。从想法、设计稿或现有项目出发时，需要补充什么需求、环境、账号条件与验收要求。何时需要分步引导、可用示例、缺项提示或现成工具？

上述客户类型用于分层比较；实际访谈仍按工程成熟度、角色和项目阶段记录差异，避免直接以公司规模推定需求。

专题 C · AI 生态的规则、Spec 与能力协作

拟核实的规范内容

  • 任务与验收：需求边界、设计、接口、完成条件如何表达和更新。
  • 工程规则：目录、依赖、代码规范、测试及权限约束如何被 AI 获取与遵守。
  • 能力调用：工具如何声明输入输出、状态、错误、版本与执行范围。
  • 验证与交接：测试结果、证据、未解决问题如何回到任务并支持人工验收。

拟探索的规范边界

  • 客户已经使用哪些规范，哪些需要保留或转换？
  • 现有 AI 工具和生态规范可复用到哪一步？
  • 哪些补充项来自鸿蒙工程、API、设备与发布约束？
  • 由谁定义、维护和校验，如何兼容版本及不同 Agent？

分层招募范围拟访人数重点覆盖
头部企业有鸿蒙项目的头部企业，覆盖互联网与重点行业客户。14争取覆盖至少 8 家，每家最多 2 人；重点覆盖互联网头部厂商，同时兼顾行业客户；包含工具链 / AI 平台负责人和一线开发 / 测试。
中型企业研发团队约 50–500 人，有鸿蒙专项或相关交付经验。12兼顾互联网与传统行业、自研与外包协作方式。
初创 / 小团队研发团队约 2–49 人，正在开发或已交付鸿蒙应用。10覆盖应用与元服务、开发中与已上架项目。
个人 / 学习者独立开发者、学生及转入鸿蒙的开发者。10学生拟不超过 3 人；包含从安卓、iOS、Web 转入者。
生态伙伴跨平台框架、三方库、开发服务及培训相关人员。4兼顾不同类型伙伴，了解其服务对象与协作场景。
合计优先按企业层级归类，再按团队规模分层，避免重复计数。50同一受访者参与多种方法时，深访人数只计一次。

横向覆盖要求

开发条件与经验

  • 覆盖原生 ArkTS、跨平台框架及迁移开发经验。
  • 争取至少 20 人具有安卓或 iOS 开发经验，用于平台对比。
  • 覆盖手机与平板、2in1、穿戴、车机等设备项目。
  • 覆盖已上架、开发中、暂停或放弃的项目阶段。

工具使用与团队角色

  • 覆盖重度、轻度与基本不用 AI 的开发者，基本不用者拟至少 8 人。
  • 覆盖 DevEco Studio、DevEco Code 与第三方 / 自研 Agent 使用者。
  • 兼顾一线开发、技术负责人、测试及设计协作角色。
  • 记录工程体系成熟度与地域，避免集中于单一社区或活跃人群。

本研究以目的性分层招募理解场景与差异，50 人是第一期执行目标，不能代表全部鸿蒙开发者的需求比例。横向条件可交叉重叠，不与 50 人相加。前期访谈资料可作提纲参考；若追加复访，单独记录，新增样本目标仍为 50 人。

对照任务测试拟 6 位双栈开发者。进一步探索 RQ5 中的平台差异。深访后选定可比任务，控制工具版本、任务难度与熟悉程度。
问卷与数据分析拟回收有效问卷 ≥500 份；后续视条件复测。了解问题分布，探索满意度、任务耗时等测量口径。基于首轮访谈形成题目；明确渠道、分层与数据权限后执行，单独统计问卷样本。
概念 / 原型测试拟 12 人，包含于 50 人。了解候选方案的理解程度与任务表现，支持 RQ7。在探索访谈后开展；依用户问题选方案，记录不适用场景和新需求。
客户共创拟 2 场，每场 4–6 家企业。进一步讨论 RQ6、RQ7、RQ9–RQ11 的能力边界、支持形式与规范。依据阶段研究确定议题，视客户意愿和排期组织；参会规模单独记录。

初期可直接使用的开放问题

  1. 请介绍一下你最近参与的鸿蒙项目，你主要负责哪些工作？
  2. 回想最近一次开发任务，从开始到交付，你按什么顺序做了哪些事？
  3. 这次任务中，哪些地方比较顺畅，哪些地方需要反复处理？能举一个具体例子吗？
  4. 你在哪些步骤用了 AI？哪些步骤没有用？当时怎么判断和选择的？
  5. 你怎样确认代码或应用符合要求？发现问题后通常怎样处理？
  6. 如果你做过其他平台，相近任务的做法有哪些相同和不同？
  7. 你们现有工具如何配合？如果可以优先改善一件事，你会选什么，为什么？
  8. 回想最近一次 AI 开发任务，开始前准备了哪些东西？哪些由你提供，哪些由工具或同事提供？遗漏后发生了什么？
  9. 最近一次把鸿蒙能力接入现有工具或流水线是怎么做的？谁负责接入，输入和返回结果是什么，哪些地方仍要人工处理？
  10. 最近一次让 AI 遵守需求、代码或测试规范时，你把规范放在哪里？它怎样获取，执行偏差又是怎样发现和处理的？

先记录用户自发提及的问题，再按遗漏主题追问；候选规划与 demo 放在探索之后。记录正向体验、反例与无需求情况，并回到具体事件核实。每次介绍方案前先结束现状访谈并单独标记，区分自发需求与方案刺激后的反馈。

专题按受访者角色和实际经验选问，不要求单场覆盖所有问题；企业工具链 / AI 平台专访可安排 90 分钟，必要时分两次交流。

关键事件追问与主持要求

围绕一次真实经历追问

  • 情境：这件事发生在什么时候？当时要完成什么任务？
  • 行为：你先做了什么，接着做了什么？用了哪些工具或资料？
  • 判断：你当时看到了什么，为什么决定继续、换工具或找人帮忙？
  • 影响：最终怎样处理？影响了谁、花了多少时间？估算与实际记录分别标记。
  • 对照：有没有同类任务比较顺畅的例子？当时有哪些不同？

统一访谈执行口径

  • 主持人保持中性，不介绍预期答案，不替用户概括痛点。
  • 避免“是不是很难用”“你会不会用某功能”等诱导或意愿式提问。
  • 先问实际行为，再问原因与感受；无法回忆时如实记录。
  • 记录员标记时间点与待追问事项，旁听者在约定环节补问。
  • 首批访谈后复盘问题覆盖和追问质量；修改提纲时保留版本。

六、招募与筛选安排

拟采用的招募渠道

  • 企业客户：与生态 BD、行业拓展和客户对接团队确认名单，邀请相关负责人及一线人员。
  • 初创与个人：通过开发者社区、活动、用户群及产品内入口招募，具体渠道待确认。
  • 生态伙伴：联系框架适配、三方库、服务商与培训机构。
  • 招募服务：与用研团队按月确认配额、筛选条件、报价和交付节奏。

筛选问卷拟收集的信息

  • 公司行业、团队规模、角色与工程协作方式。
  • 鸿蒙经验、项目类型、设备形态与发布状态。
  • 其他平台经验、常用工具及近期 AI 使用频率。
  • 近期真实开发任务和可分享的例子。
  • 可参与时间、录音录屏与后续研究意愿；录屏意愿不作为深访的必要筛选条件。

分析方式与研究完成标准

  1. 整理事件证据：按“用户类型—任务情境—实际行为—遇到的问题—影响—现有办法”整理记录，关联脱敏受访者编号与原始证据。
  2. 归纳主题并比较差异：先从材料归纳主题，再对照已有规划；比较团队类型、工程成熟度与 AI 使用程度，保留反例和分歧。
  3. 判断证据充分程度：标记单例、多位受访者重复出现及观察 / 数据支持情况；受访者提及人数与事件次数分开记录，不推算总体比例。
  4. 形成决策建议：综合问题影响、发生条件、紧迫性与现有解决成本，与产品、设计共同讨论；证据不足的议题进入后续研究。
  5. 检查研究覆盖：核心问题均有可追溯记录；关键分层的缺口与差异有说明。连续数场没有新增重要主题时，结合分层覆盖评估主题是否充分，并优先补招尚不清楚的场景。

访谈的完成标准是支持决策的证据质量和覆盖程度。候选方案未获认同、用户没有相关需求等情况同样纳入交付。

每场访谈后

  • 记录反例、分歧与新出现的主题。

阶段报告

  • 列明实际样本与方法覆盖。
  • 区分已观察现象、解释和待验证问题。
  • 说明可支持的决策与后续研究需求。

  • 结合版本节奏安排新增场景探索、复访和方案测试。
