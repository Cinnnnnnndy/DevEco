鸿蒙开发者用户研究计划：鸿蒙开发和通用开发、苹果开发差在哪，以及半年访谈 50 人的安排

两部分。第一部分是初步分析：鸿蒙生态开发和传统通用开发（Web、安卓、跨平台）、苹果开发的区别，以及据此我们给不同客户的交互件该是什么。第二部分是用户研究计划：研究目标、分层样本、方法、招募与筛选、从 2026-11 招募开始到 2027-04 的时间线。依据项目已有材料：10 月 12 份访谈聚类（v4）、27X 三条策略与 31 个规划点、10-29 目标与指标审视、10-28 领导视角审视。

一页结论

  1. 鸿蒙开发最大的不同，是「新平台」和「AI 写代码」同时到来。写安卓、Web、iOS，AI 靠海量语料就能写对；写鸿蒙，AI 语料少、API 还在变，只能靠工具兜底：鸿蒙知识要准、编译要能自动修错、要在多设备上验得了、要能一路走到上架。这正是访谈里 DevEco 赢 Codex 的原因（「会直接构建修复」，像素匠）访谈。
  2. 苹果是最接近的参照，差别在开放度和成熟度。两者都是「一家平台、一套官方工具链」。苹果在 Xcode 26.3 把编译、预览、文档通过 MCP 开放给 Claude Agent、Codex 等外部 Agent 官方；鸿蒙的编译调试、签名上架还没对外部 Agent 开放，WPS 只能用 Playwright 脚本自动化上架网页 访谈。
  3. 因此给客户的交互件按三类伙伴分：头部大厂要「能力包」（编译、真机、体检、签名上架以 CLI / MCP / Skill 开放，接进他们自己的 Agent 和流水线）；中型企业要「接入件」（规范模板、插件、云真机）；初创和个人要「一站式路径」（DevEco Code 从想法到上架）。每次客户交流带去同一套「交流件」：能力地图、可试用 demo、PoC 任务包、反馈回执。
  4. 研究计划：第一期 2026-11-02 到 2027-04-30，26 周，深访 50 人（头部大厂 14、中型 12、初创 10、个人 10、生态伙伴 4），补上 10 月样本缺大厂的洞。配合 500 份以上问卷建 NSS 与体验指标基线、8 人日记研究、3 家大厂现场观察、12 人 27X 原型测试、2 场头部客户共创会。
  5. 两个早出结果的节点：12-11 交第一份快报（含 ≥4 位大厂受访者），赶上 11–12 月 BP；2027-02-26 交中期报告，给 27X 第一个版本定需求和指标目标值。
  6. 按 10-29 下午讨论，用研做成常态：和谭杰（或林丽）立项，走用研招募按月下单，同时在群里自招、申请经费；第一期 50 人后不停，5 月起每月 4–6 人持续到 2027-06 HDC 及以后，先跑满一年。注意：「每两个月 5 人」8 个月只有 20 人，要到 50 人得每月约 6 人。大厂和重点客户（如汪健）以面对面交流为主，材料用简化版。

一、鸿蒙开发、通用开发、苹果开发的区别初步分析，第 4 节的研究要逐条验证

「通用开发」这里指 Web、安卓和跨平台框架（Flutter、React Native 等）。表里蓝底一列是鸿蒙特有、并且直接影响 AI 开发体验的地方。

维度鸿蒙生态开发传统通用开发苹果开发
语言与界面框架ArkTS + ArkUI 声明式，Stage 模型；API 版本更新快（访谈里黑马讲鸿蒙 4/5/6 三个版本、文档改版四次）访谈TS/JS、Kotlin/Java，框架多但成熟稳定Swift + SwiftUI/UIKit，十多年连续演进，迁移路径清楚
AI 对平台的熟悉度公开代码少，通用模型常按 TS 或安卓的写法写 ArkTS，会编不存在的 API；「超过五六个文件第一次编译肯定不通过」（左右相册）访谈语料最多，模型最熟，写得最对语料多，模型熟；官方在 Xcode 里直接接入大模型 官方
工具链与开放度DevEco Studio 是唯一完整工具链（编译、签名、模拟器、Profiler）；DevEco Code CLI 已落地、GUI 落地中；编译调试、签名上架还没开放给外部 AgentIDE 和 Agent 随便选，命令行和 CI 全可用Xcode 也是唯一，但 xcodebuild 命令行完整；Xcode 26.3 通过 MCP 把能力开放给外部 Agent 官方
运行与验证要在手机、平板、2in1、穿戴、车机上验；模拟器能力有限，真机不好借；预览不能点；「展到我手机上……才是最终验收」（格力）访谈Web 刷新即见；安卓模拟器成熟Simulator、Previews 成熟，设备型号少
多设备与分布式一次开发多端部署、跨设备流转、分布式能力是鸿蒙的卖点，也是鸿蒙独有的验证负担以响应式布局为主，很少跨设备协同有接力等连续互通能力，开发者侧负担较轻 推断
打包、签名、上架HAP/HAR/HSP，证书 + Profile + 权限申请，AppGallery Connect 多步网页操作；「创建应用这个环节是没有 API 的」（WPS）访谈Web 直接部署；安卓多市场，各自规则证书和描述文件同样复杂，但 App Store Connect API 和自动化工具链成熟 推断
三方库与跨平台三方库少、更新慢，拖累 Flutter 等跨平台项目的其他端（理性幻想）访谈；跨平台框架需要鸿蒙适配层npm、Maven 生态极大SPM、CocoaPods 成熟
文档与知识版本多、层级深、搜不到（7/12）访谈；社区问答少，AI 搜索也会指到第三方社区问答海量官方文档 + WWDC 视频 + 社区成熟
开发者构成与动机很多人从安卓、iOS、前端转来，或因激励政策入场；担心「挣不到钱」（黑马）访谈；注册开发者 1100 万+ 官方职业主流，岗位多付费用户多，独立开发者有稳定收入

三个判断

判断 1 · 对应「验得了」

AI 写别的平台靠语料，写鸿蒙靠工具

鸿蒙的知识准不准、编译能不能自动修错、多设备上能不能马上看到，决定了 AI 写鸿蒙的成功率。这块编译器、模拟器和真机都在我们手里，是能领先的地方。

判断 2 · 对应「接得进」

大厂的入口是自己的 Agent，不是我们的 IDE

头部客户已经在用 Claude Code、Codex 或自研 Agent 和自己的流水线。苹果的做法是把 Xcode 能力开放出去。鸿蒙要让这些外部 Agent 也能编译、上真机、签名上架。

判断 3 · 对应「托付得放心」+ 外循环

鸿蒙多出来的是「外循环」

通用开发写完基本就能交付；鸿蒙写完还要过多设备、签名、上架三关，而 AI 只加快了写代码这一段。体验差距主要在「做出来、上架」这一段。

这三条是 10 月 12 份访谈和公开资料的初步判断，大厂样本为 0，其中判断 2 最需要研究验证。

要靠研究验证的假设

编号假设怎么验证对应策略
H1写鸿蒙时，AI 生成代码的首次编译通过率明显低于写安卓或 iOS深访追问 + 同一任务对照测试（安卓/iOS 双栈开发者做同一需求）验得了

H3多设备验证是鸿蒙独有的时间黑洞，团队越大越明显日记研究记录每次验证用时 + 问卷验得了
H4签名上架是个人和初创开发者流失最多的一步深访 + 问卷 + 上架流程埋点（产品线提供）接得进
H5从安卓、iOS 转来的开发者，最大的成本是「重新学一遍」而不是写代码本身，AI 能显著缩短这段转入者配额 + 深访托付得放心

H8代码大量由 AI 生成后，代码冗余、规范检查、二次编辑在真实工作里是突出问题，并且会随持续迭代变重，不能只靠「看应用结果」验收 10-29 评审深访追问 + 日记研究记录返工；看 AI 生成代码的 review 和重构次数验得了

二、我们给客户的交互件按「交付给客户的东西」和「交流时带去的东西」两层理解，口径待确认

27X 的产品策略已经按三类伙伴分（头部大厂、中型企业、初创和个人，初创和个人走「一站式交付」）。交互件跟着这三类分：

互联网头部大厂 · 推动「进 38+ 家头部」

能力包：把鸿蒙能力接进他们的 Agent 和流水线

  • 鸿蒙能力开放：编译调试、真机与多设备、应用体检、签名上架，以 CLI（无界面运行）、MCP Server、Skill 提供
  • 鸿蒙知识接入：AI 可读的文档和 API 知识库，能叠加企业自己的规范
  • 企业接入方案：模型可自选或私有部署、权限与审计、CI 模板
  • 对接机制：专属接口人、联合 PoC、需求直通、季度共创会
中型企业 · 推动 NSS、70 万

接入件：在现有工具里把鸿蒙做好

  • 能插进他们正在用的 IDE 和 Agent 的鸿蒙插件和 Skill
  • 团队规范模板（规则、任务分级 L0/L1/L2，参考 WPS 做法）
  • 云真机和多设备验证，不用自己买齐设备
  • 安卓应用转 ArkUI 的迁移工具
初创团队和个人 · 推动 70 万、NSS

一站式路径：一个人几天几块钱上架

  • DevEco Code GUI/CLI 从想法到上架一条路走完
  • 能用图和设计稿交代需求、模板和示例工程
  • 上架前体检、签名自动处理
  • 新手路径：一步一步来，会的不展开

每次客户交流带去的「交流件」

交流件是什么现有基础在研究里怎么用
能力地图一页纸：三条策略、31 个规划点、哪些已落地、哪些在 27X规划全景页、对照表访谈开场 5 分钟，再让受访者标「最想要的三个」
可试用 demo可以点的界面稿和真实工具启动页 29 条创新点 demo、Device Box、DevEco Code CLI概念测试和原型测试的材料
PoC 任务包五条基准任务 + 客户自己的一条任务，记录用时、首次编译通过率、人工介入次数趋势分析里的五条基准任务、10-29 指标定义大厂和中型企业的联合验证；同时得到指标基线
反馈回执访谈后两周内回给客户：我们听到了什么、会做什么、什么时候能试无，新建维持客户关系，方便复访和共创

三、研究目标与研究问题

研究目标

  • 补样本：补上头部大厂（10 月为 0）和生态伙伴，覆盖三类伙伴
  • 验证三条策略：「托付得放心 / 验得了 / 接得进」在不同规模客户中是否成立、谁最痛
  • 讲清鸿蒙独特性：验证第一部分的 H1–H6，回答「为什么必须是 DevEco」
  • 定交互件：大厂要的能力包长什么样、以什么形式接
  • 建基线：给 10-29 的 12 项指标和 NSS 测基线，给 27X 定目标值

研究问题

  • RQ1 不同规模团队的鸿蒙开发全流程（开发准备→编码实现→运行验证→发布上架）各卡在哪、卡多久？
  • RQ2 AI 写鸿蒙和写其他平台，体验差在哪？用户怎么补？
  • RQ3 大厂的 AI 工具链是什么？鸿蒙能力要以什么形式接进去？
  • RQ4 多设备验证和签名上架的真实成本是多少？
  • RQ5 什么让开发者「放心交给 AI」？团队规模如何改变答案？
  • RQ6 31 个规划点里，各类用户最想要哪三个？27X TOP3 是否被认同？
  • RQ7 同一件事在鸿蒙、iOS、安卓上做，开发者的体验差在哪？（10-29 评审追问「那 iOS 跟安卓呢」）
  • RQ8 互联网大厂、非互联网中大型企业（含重点行业客户）、普通开发者的旅程各有什么不同？现在的旅程图是三类的概括，要分别画
  • RQ9 AI 生成的代码质量（冗余、规范、二次编辑）在真实工作里有多突出？
