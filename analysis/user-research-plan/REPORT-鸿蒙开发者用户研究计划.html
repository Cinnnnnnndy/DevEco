计划概览

  • 要解决什么：弄清鸿蒙开发者与通用开发者有哪些差异，做鸿蒙任务时要给 AI 输入什么，以及如何用 Spec 和规范让 AI 产出符合需求。
  • 怎么做：先访谈和观察真实项目，再分轮测试现有产品与改进方案，同时跟踪相关竞品。
  • 找谁：覆盖三类研发组织，累计预计30–40位独立参与者，首批先做5–8人。
  • 谁来做：两位交互设计师各投入30%，合计约3人日／周，按轮次推进。

本页为研究计划。问卷、筛选规则和完整提纲见配套材料；具体时间随客户预约和产品版本调整。

一、背景与目的

背景　随着鸿蒙生态发展，AI 正在参与需求理解、编码、测试等开发工作。不同规模团队已有的工程、规范和工具链各不相同，鸿蒙开发又有平台和设备要求。需要从真实任务了解这些条件如何影响开发者与 AI 协作，以及他们如何判断产出符合需求。

目的　面向鸿蒙生态发展与 AI 驱动开发方式的转变，通过对不同规模团队开发者的访谈，识别鸿蒙开发者与通用开发者的差异、鸿蒙开发时需要提供给 AI 的输入，以及让 AI 产出符合需求的 Spec 和协作规范，为 DevEco 后续产品规划提供依据。

二、研究目标与问题

从开发者亲自做过的任务出发，按头部团队、中厂、小团队与个人比较，并记录已有资产、工程成熟度和工具链条件。

研究目标重点了解的问题研究产出
了解鸿蒙开发者与通用开发者的差异

比较同一开发者在鸿蒙和安卓、iOS、Web 等平台上做过的相近任务。从准备、编码、构建调试、测试到发布，哪些做法可以沿用，哪些受鸿蒙语言、API、设备形态或签名规则影响？

对头部厂商，沿已有工具链核实开发、测试、鸿蒙专项验证和发布各需要什么支持，以及能力适合通过 CLI、API／SDK、插件还是服务提供。

形成通用与鸿蒙特有需求对照，以及分团队的工具支持和接入能力清单。
弄清鸿蒙开发时要给 AI 输入什么

从真实任务还原实际给 AI 的输入，包括需求与验收要求、设计、现有工程与代码、鸿蒙文档及 SDK／API 版本、依赖与设备环境、工具权限和测试用例。

不同团队各有什么现成材料，由谁准备，怎样交给 AI？哪些需要反复解释，哪些可以从工程或平台补齐？

形成按团队和场景划分的输入清单，明确导入、复用和缺项提示需要支持什么。
了解用什么 Spec 或规范让 AI 产出符合需求

任务要求、团队工程规则、鸿蒙平台约束、工具调用约定和验收标准怎样写、传递和更新？哪些可沿用通用规范，哪些需要鸿蒙补充？

怎样判断 AI 按要求执行，何时介入或恢复？生成后如何检查冗余、规范和业务逻辑，如何二次修改、构建、测试、真机验收与复验？

形成规范与协作方式清单，明确规则责任、人工确认节点和可用来验收的证据。

每项任务同时记录 Studio、Code 与其他工具怎样分工，用户为什么采用、试用后放弃或停用。结合问题频率、影响和当前处理成本，提出应先解决的需求。后续选择样板场景时，核实可用的脱敏材料、设备和验收标准。

三、竞品与趋势分析

沿1028材料的四个方向，复用启动页已有报告，按当前鸿蒙研究任务补充对照。竞品做法用于提出方案和假设，再结合用户证据判断是否适合DevEco。

专题对照任务与观察点已有材料／用户问题
C1 准备与目标表达把需求、设计和存量工程交给AI：如何识别依赖、版本与规则，完成首次可验证修改。AI开发准备；开发准备与规范
C2 任务协作并行修改、叫停和恢复：任务归属、改动范围、状态及历史是否清楚。Agent生命周期、会话呈现；任务控制与工具协作
C3 质量与验收检查一次交付：代码、测试与运行证据如何关联，怎样发现未验证项并继续修复。成果验收；质量检查与改善顺序
C4 平台能力与开放从修改代码走到构建、调试、设备验证和发布：哪些可由外部Agent或CI调用，结果怎样返回。Xcode专题；平台差异与能力接入
C5 多入口与轻量工具换入口接续任务：上下文、确认和结果是否保留，是否减少启动和切换成本。AI工具趋势、触屏与笔；用户场景与工具协作

观察范围：Codex、Claude Code、Cursor、VS Code／Copilot，以及Xcode、Android Studio等平台工具。每次只选2–3款能完成相近任务的产品；其他工具按问题补充。

工作节奏：启动时核对旧报告，随后每月整理简短变化记录；深入分析随研究轮次开展。每条记录保留日期、版本、环境、来源和任务证据，区分官方说明、实际观察与研究判断。鸿蒙特有的API、设备及发布条件单独说明。

四、找哪些开发者

累计预计30–40人，先访谈5–8人，再按缺口补充。覆盖以下三类，不要求每个人都做深访；同一人参加多轮只计一人。

用户类型建议人数／比例主要特点
头部互联网及同类大型研发团队12–16人／约40%多团队协作，有组织级研发平台或专门工具链。
中厂8–10人／约25%有稳定分工，工程支持主要围绕业务项目。
小团队与个人开发者10–14人／约35%少量成员或个人负责多个环节，自行组合工具；小团队与独立开发／学习者都需覆盖。

华为内部使用DevEco的开发者建议6–10人，包含在上述人数内，按实际工程体系分组。问卷分别记录行业、岗位、组织研发人数和项目人数，预约时结合分工、工具选择和工程支持确认归组。

三类团队用于安排名额。岗位、项目数与最近任务时间、Studio／Code 经历、AI 使用频率和跨平台同类任务用于匹配本轮场景。优先补缺失案例，兼顾初用、熟练、停用和从未使用者。先锋与意见领袖根据具体行为核验，可与其他标签重叠。

人数和比例用于安排研究覆盖，不代表生态分布；熟练度、经验、设备与平台的详细补招标准见筛选规则。

五、研究方法与提纲

以定性访谈和真实操作观察为主，先归纳问题，再用任务测试验证改进。各方法的轮次与具体任务见实施安排。

方法何时使用
第1轮：访谈＋关键事件回溯从最近一个鸿蒙项目开始，沿工程准备、实现、验证和交付追问具体经历。
第1轮：情境观察从受访者中选4–6人，观察其实际使用Studio、Code和设备的过程，可并入访谈或另约。
第2轮现有产品／第3轮改进方案
形成性任务测试		针对当前产品或可操作原型，观察能否完成指定鸿蒙任务，发现问题后改进再测。
第4轮：综合评估固定版本、任务和成功标准后总结表现；若要统计比较版本效果，另行估算样本。

按用户开发旅程访谈

开场从问卷带入项目、分工和工具使用，补齐设备与技术栈。沿同一次鸿蒙任务，从准备、编码协作、构建调试问到验收和交付。用过 AI 的案例重点了解输入、规则传递和产出检查，未用 AI 的案例了解实际工具与做法。任务讲完后，按经历补问跨平台差异、头部工具链接入和规范复用。

常规访谈约 75 分钟，资深开发者深访按需延长，单场最长 90 分钟，预约时确认。深访时间优先用于有实际案例的 AI 输入、Spec 与跨平台对照，详见访谈提纲。

先问做了什么，再问当时判断与感受，用 5W2H 补足事实，访谈后按三项研究目标归纳证据。

产品讨论补充六项关注点。编码阶段回顾 Agent 与 IDE 的分工和切换，以及 AI 与人工编辑同一工程时的确认、同步和冲突。访谈末尾按经历选问 IDE 必备能力、轻量工具、DevEco Code 与其他工具对比、独立 Agent 的交互方式。用产品补问表记录各方案适用的鸿蒙任务和条件。

评分作为追问线索

近4周实际用过Code的用户，在回溯鸿蒙任务后，分别评价整体体验、准备、过程控制、检查与修改，使用1–5分并提供“不适用／记不清”。停用者的历史评价单列。任务测试记录独立或协助完成、失败、耗时及错误；小样本分数只描述本轮体验。

形成性测试用于发现和改进问题；总结性评价用于总结表现，区别取决于目的。5–8人和10–12人是本项目执行估计，不是通用人数标准。方法参考

七、方法与实施时间线

共四轮：访谈与观察 → 现有产品测试 → 改进方案测试 → 阶段综合评估。每轮先准备、再执行、最后分析与评审；一轮结束后再决定补访或进入下一轮。

由两位交互各投入30%，合计约3人日／周：核心研究2.25人日、招募与竞品0.5人日、机动0.25人日。执行周约2场；整理和分析已计入各轮，不另排满新场次。

八、分析、产出与产品行动

如何整理材料

每场整理“鸿蒙任务—实际行为—当时判断与感受—结果—影响—现有办法”，关联原始记录。按旅程归类，再比较画像、角色、版本和使用阶段。跨平台差异用同类任务对照，AI 输入记录材料及来源，Spec 与验收记录规则和实际检查证据。保留顺畅案例与反例，逐项判断假设得到支持、部分支持、反证或证据不足。

每轮交什么

产出内容与用途
鸿蒙与通用开发差异按团队和相近任务比较开发流程与平台要求，记录头部客户的能力缺口和接入形式。
鸿蒙 AI 开发输入清单按场景列出已有材料、需要补齐的内容、准备责任和导入方式。
Spec 与验收要求整理可复用规范和鸿蒙补充规则，记录维护责任、人工确认节点、代码检查和运行验收证据。
竞品与方案验证记录将实际任务中的工具表现与概念反馈分开记录。用相关用户的任务验证能力差异、编辑交接与界面方案，再整理进入产品规划的依据。
阶段报告与行动表记录实际参与者、任务、版本、证据、优先建议、负责人、目标节点和下一步验证。
