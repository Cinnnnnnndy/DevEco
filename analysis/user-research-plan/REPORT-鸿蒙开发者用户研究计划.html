计划概览

  • 要解决什么：了解鸿蒙开发者从工程准备到应用交付的真实困难，确定 DevEco Studio、DevEco Code 及开放能力下一步先做什么。
  • 怎么做：先访谈和观察真实项目，再分轮测试现有产品与改进方案，同时跟踪相关竞品。
  • 找谁：覆盖三类研发组织，累计预计30–40位独立参与者，首批先做5–8人。
  • 谁来做：两位交互设计师各投入30%，合计约3人日／周，按轮次推进。

本页为研究计划。问卷、筛选规则和完整提纲见配套材料；具体时间随客户预约和产品版本调整。

一、背景与目的

面向鸿蒙生态发展和 AI 开发方式的变化，通过开发者访谈、任务测试与竞品分析，找出鸿蒙开发全流程中的工具和能力缺口，为 DevEco 体验改进与2027年产品规划提供依据。

本次围绕已上线的 DevEco Studio 和 DevEco Code，重点看工程创建与迁移、ArkTS／ArkUI开发、构建调试、设备验证和签名发布。AI如何参与这些工作、用户在哪一步切回人工或其他工具，也放到具体任务中了解。

二、研究目标与问题

弄清楚鸿蒙开发中哪些问题最影响交付、不同用户需要什么支持，并确定下一版优先改什么。以下判断来自旧访谈与规划材料，本次用真实任务核实，也保留不同意见。

每场从一个本人做过的鸿蒙任务展开，只追问相关环节；RQ编号供提纲和专题对应使用。

主题／待验证假设访谈要问什么
H1 工程体系与接入不同团队怎样把鸿蒙构建、调试、测试和发布接入现有流程？哪些用现成工具，哪些需CLI、API／SDK、插件或服务？（RQ1／6／9）
H2 AI开发准备SDK／API、工程依赖、设计和团队规则由谁准备，怎样交给AI？哪些缺项导致失败或返工，哪些规范能复用？（RQ10／11）
H3 AI任务控制修改鸿蒙工程时怎样确认计划、看进展、控制改动和恢复任务？什么时候需要接管，什么时候不必盯着？（RQ3）
H4 质量与二次修改代码生成后还要做哪些检查和修改？怎样判断能编译、符合业务和规范、后续可维护？（RQ4）
H5 鸿蒙验证与交付预览、模拟器、真机、多设备和签名发布怎样衔接，哪里受阻？与亲自做过的安卓／iOS相近任务有什么不同？（RQ2／5）
H6 Code采用与改善顺序Code、Studio与其他工具怎样分工？为什么采用或停用？先改哪一步，后续适合怎样验证？（RQ7／8）

三、竞品与趋势分析

沿1028材料的四个方向，复用启动页已有报告，按当前鸿蒙研究任务补充对照。竞品做法用于提出方案和假设，再结合用户证据判断是否适合DevEco。

专题对照任务与观察点已有材料／用户问题
C1 准备与目标表达把需求、设计和存量工程交给AI：如何识别依赖、版本与规则，完成首次可验证修改。AI开发准备；RQ10／11
C2 任务协作并行修改、叫停和恢复：任务归属、改动范围、状态及历史是否清楚。Agent生命周期、会话呈现；RQ3／6
C3 质量与验收检查一次交付：代码、测试与运行证据如何关联，怎样发现未验证项并继续修复。成果验收；RQ4／7
C4 平台能力与开放从修改代码走到构建、调试、设备验证和发布：哪些可由外部Agent或CI调用，结果怎样返回。Xcode专题；RQ5／9
C5 多入口与轻量工具换入口接续任务：上下文、确认和结果是否保留，是否减少启动和切换成本。AI工具趋势、触屏与笔；RQ1／6

观察范围：Codex、Claude Code、Cursor、VS Code／Copilot，以及Xcode、Android Studio等平台工具。每次只选2–3款能完成相近任务的产品；其他工具按问题补充。

工作节奏：启动时核对旧报告，随后每月整理简短变化记录；深入分析随研究轮次开展。每条记录保留日期、版本、环境、来源和任务证据，区分官方说明、实际观察与研究判断。鸿蒙特有的API、设备及发布条件单独说明。

四、找哪些开发者

累计预计30–40人，先访谈5–8人，再按缺口补充。覆盖以下三类，不要求每个人都做深访；同一人参加多轮只计一人。

用户类型建议人数／比例主要特点
头部互联网及同类大型研发团队12–16人／约40%多团队协作，有组织级研发平台或专门工具链。
中厂8–10人／约25%有稳定分工，工程支持主要围绕业务项目。
小团队与个人开发者10–14人／约35%少量成员或个人负责多个环节，自行组合工具；小团队与独立开发／学习者都需覆盖。

华为内部使用DevEco的开发者建议6–10人，包含在上述人数内，按实际工程体系分组。问卷先了解行业、岗位和两级团队人数，预约时再确认分工与工具支持。

各组兼顾开发、测试发布和工具链岗位，以及AI高频、低频、未用和停用者；既找熟练用户，也保留初用者。先锋与意见领袖按具体经历核验，不另设一套人群分类。

人数和比例用于安排研究覆盖，不代表生态分布；熟练度、经验、设备与平台的详细补招标准见筛选规则。

五、研究方法与提纲

以定性访谈和真实操作观察为主，先归纳问题，再用任务测试验证改进。各方法的轮次与具体任务见实施安排。

方法何时使用
第1轮：访谈＋关键事件回溯从最近一个鸿蒙项目开始，沿工程准备、实现、验证和交付追问具体经历。
第1轮：情境观察从受访者中选4–6人，观察其实际使用Studio、Code和设备的过程，可并入访谈或另约。
第2轮现有产品／第3轮改进方案
形成性任务测试		针对当前产品或可操作原型，观察能否完成指定鸿蒙任务，发现问题后改进再测。
事件日志＋回访（按需）只有跨日执行、中断或验收无法在单场了解时使用；4–6人记录7–14天，每条约3–5分钟。
第4轮：综合评估固定版本、任务和成功标准后总结表现；若要统计比较版本效果，另行估算样本。
小组讨论（按需）个人访谈后，同类角色4–6人讨论规范或协作边界；不替代实际操作证据。

提纲围绕鸿蒙项目展开

75分钟示例：开场5分钟，项目与工具10分钟，鸿蒙任务回溯30分钟，关键问题20分钟，Code评分5分钟，收尾5分钟。每场只深挖本人做过的环节，完整问题见访谈与任务评测提纲。

研究前从产品决策确定重点（Top-down）；访谈中先问做了什么，再问当时判断与感受（Do／Think／Feel），用5W2H补足人物、时间、方式和成本；分析时从事件归纳主题（Bottom-up），再回看假设。

评分作为追问线索

近4周实际用过Code的用户，在回溯鸿蒙任务后，分别评价整体体验、准备、过程控制、检查与修改，使用1–5分并提供“不适用／记不清”。停用者的历史评价单列。任务测试记录独立或协助完成、失败、耗时及错误；小样本分数只描述本轮体验。

形成性测试用于发现和改进问题；总结性评价用于总结表现，区别取决于目的。5–8人和10–12人是本项目执行估计，不是通用人数标准。方法参考

七、方法与实施时间线

共四轮：访谈与观察 → 现有产品测试 → 改进方案测试 → 阶段综合评估。每轮先准备、再执行、最后分析与评审；一轮结束后再决定补访或进入下一轮。

由两位交互各投入30%，合计约3人日／周：核心研究2.25人日、招募与竞品0.5人日、机动0.25人日。执行周约2场；整理和分析已计入各轮，不另排满新场次。

横轴为从启动算起的相对周次。图中第1–3轮各示意8周，第4轮示意11周；实际分别可在6–9周、9–12周调整。产品修改和版本等待另计，进入第3轮前必须先有可测试方案。追加访谈、日志或小组讨论时，替换当期工作或顺延，不能叠加工时。

规范／接入边界

观察可并入第1轮访谈；需要跨日证据才启用虚线日志任务，记录后回访。小组讨论用于接入或规范边界。综合评估的10–12人是执行估计，如需统计比较另行设计样本。礼品按参与约定及时办理，图示为登记与核对时间。

与BP和展会怎样衔接

每轮交付都可进入产品讨论。节点先到时提交已有证据及未验证项；展会优先选择有真实任务依据的场景，预留演练和修订。BP、版本与展会日期确认后再换算实际日期，插入任务时同步调整原排期。

八、分析、产出与产品行动

如何整理材料

每场整理“鸿蒙任务—实际行为—当时判断与感受—结果—影响—现有办法”，关联原始记录。按旅程归类，再比较画像、角色、版本和使用阶段；保留顺畅案例与反例，逐项判断假设得到支持、部分支持、反证或证据不足。

每轮交什么

产出内容与用途
鸿蒙开发旅程与问题清单串起准备、编码、构建调试、设备验证和发布，说明问题影响、现有办法及用户差异。
准备与接入专题分客户列出需导入的工程／知识／规则；画出头部工具链、能力缺口、调用形式和维护责任；整理Spec复用与鸿蒙补充要求。
竞品与方案验证记录关联用户问题、竞品做法、鸿蒙条件和测试结果，说明改动是否有效及尚未验证的部分。
阶段报告与行动表记录实际参与者、任务、版本、证据、优先建议、负责人、目标节点和下一步验证。

结论如何影响产品

可能发现后续行动
影响关键任务，且有重复行为证据进入近期修复或2027年BP候选，与产品评估范围、依赖和成本，再安排复测。
只在特定客户或工程条件下出现形成专项支持或接入方案，在对应客户验证。
能力已有，但用户找不到或不会用先改入口、说明、示例和准备引导，测试能否独立完成。
方向有价值，但方案或证据不足做原型或定向补访；暂缓结论并写明还缺什么。
旧问题缓解，或新证据不支持假设调整优先级，记录变化条件；未再提及不能直接判定已解决。

每轮结束后怎么继续

与产品一起确认采纳、暂缓或不采纳及原因，更新问题与行动台账；再决定补访、测试、等待修改或结束专题。复访仅联系已同意后续邀请的人。提及次数和任务评分都需标明样本与条件，不推算总体需求比例。

九、启动前待确认

  • 两位交互的实际时间、主持记录分工，以及产品和客户接口人。
  • 首轮重点鸿蒙场景、可用版本、目标用户与招募渠道。
  • BP／版本／展会节点，以及临时任务的取舍规则。
  • 问卷平台、联系与资料管理方式、激励标准及预算来源。
