核心结论

  1. AI 写得快，但底层代码的每一行都必须有人看过。GC 组约 10 人，PR 全组逐行人工 review、SE 最终把关（200 行约 0.5–1 小时，2000 行 2–3 小时）。AI 爱加保底判断和冗余代码，还会自作聪明用没人用过的方案破坏时序，在性能敏感的底层完全不可接受。
  2. 蓝黄双区物理割裂是最大效率摩擦。需求代码（C++）在蓝区 VS Code 远程编写，同步生成黄区 PR 后才能在黄区连真机编译测试；黄区只能用不够聪明的 CodeAgent，出崩溃时需先用自写 skill 解析日志堆栈，再人工搬回蓝区 AI 分析，再回黄区验证，往返极费时。
  3. SDD 交付件在实现变更时成为维护负担。需求代码有 SDD（design / spec / 执行文档），用意是让 AI 更准、测试有依据；但编码中发现设计要改时，回头同步维护 SDD 反而增加负担。
  4. DevEco Studio 仅作「写 demo + 看实时日志」工具，未发现历史日志与 Profiler。抓 trace 靠内部工具或手动命令，分析去内部网站；认为 Studio 日志只能看实时、看不了历史（疑似可发现性问题）。
  5. GUI 有必要，但集成到 IDE 的 AI 必须与 Studio 工具打通。他认为终端 CLI 窄长别扭，希望对话放侧栏与代码并排、AI 改动按「文件—行—改动」逐条对照看；现场体验新版 DevEco Code 后直接发问：「如果没有和 Studio 工具的专有适配（如 MCP），和在终端里开个 CLI 有什么区别？」

受访者与工作方式

背景

OpenHarmony 底层新员工

  • OpenHarmony 4部 ETS Runtime 组，GC 方向约 10 人（稳定性 2–3 人，内存/性能优化各 3–4 人）。
  • 此前仅做过 Java Web 实习，无安卓/iOS 应用开发经验。
  • 产物合并进 HarmonyOS 底层，用户仅感知卡顿或闪退。
工具

多工具并存，偏好 IDE 侧栏

  • 蓝区：VS Code 远程 + OpenCode / Codex + 火山网关（智谱/DeepSeek/千问，有 token 上限）。
  • 黄区：DevEco Studio（写 demo、看实时日志）+ 终端 CodeAgent + 内部 trace/稳定性工具。
  • 重复日志分析沉淀成 skill，一次性任务不沉淀。
节奏

人工把关，极低容错

  • 蓝区 C++ 改动要精确，常手动改；黄区 demo 能跑通即可，多交给 AI。
  • 打字比语音快，很少用图片输入，偏好文字或先让 AI 生成 md 再喂给 AI。
  • PR 必经全组逐行 review 与 SE 拍板。

三项研究目标

① 鸿蒙与通用开发的差异
  • 相比 Java Web，底层开发有三处核心差异：代码质量要求极高、并发等逻辑难度高、验证与门禁流程极严（UT/DT + 长时间整机稳定性压测）。
  • 蓝区开源开发、黄区真机测试的物理隔离是华为内部特有的工作流成本。
② 给 AI 的输入
  • 写测试 demo 靠一段自然语言交代对象量级、GC 开关、按钮流程，并让 AI 参照导师历史 demo。
  • 重复性排错流程（编译命令 → 定位行 → 分析堆栈）会写成 skill；仓库内放规范 Markdown 供 AI 读取。
③ Spec 与验收
  • SDD（design / spec / 执行文档）在设计变更时反而成为同步维护负担。
  • 对 AI 的「放心条件」明确：说明遵守了哪些仓库规范、未引入新方案、沿用既有逻辑时序、编译与 UT 全量通过。
产品反馈（DevEco 相关）
  • DevEco Code GUI：希望放侧边栏与代码并排；拖出窗口后 session 列表脱离体验不好；希望按「文件—行—改动」逐条对照看；质疑若无 Studio 工具专属 MCP 适配则与终端 CLI 无异。
  • 日志与 Profiler：未发现历史日志能力；未用过 DevEco Profiler；MCP/skill 配置对新人不够直观。

王欣迪：

王欣迪：

三、review 退场，门禁兜底

受访者：

主持方：
相当于 AI 来了之后你们加强了很多门禁和 spec 方面的东西，人工 review、互相 review 的环节已经不存在了？

五、鸿蒙工具链缺口：命令行工具与 Rust

主持方：

受访者：
ArkTS 要编译。我本地也会编，但只是验证一下；真要提交代码时一定要到服务端卡一下，不能靠本地环境——AI 可能跟你说「我本地没问题」，你就提上去了。到服务端我不管你怎么「骗」AI，一定要求覆盖率达标、没有问题才能过 MR。
主持方：

受访者：
服务端都是 Docker，Dockerfile 里这些工具都要支持好，但我试下来支持不好。
主持方：
这个工具是 CLI 的？
受访者：
是编译器的命令行。从官方网站登录后下载 command-line tools，在本地把镜像做好，推到集团自己的镜像仓库（Docker Hub 类），构建时在服务器选这个镜像，拉起来就是预置好的。但编的时候发现有的东西没有。
主持方：
所以现在体验最不好的是 command-line tools 这块。
受访者：
对。你要多平台支持，尤其要支持 Linux，因为很多服务器都是 Docker，只支持 Linux。
主持方：
跟四文他们反映后，他们怎么说？
受访者：
也没解决。
主持方：
所以鸿蒙开发里你觉得体验最差的是编译调试这块？
受访者：
调试没有，我们组应该没有人去调试，都交给 AI 了。编译这块是有感知的。中间过程是 AI 在感受，它自己也不说。有时你卡住了，会跟它反复掰扯，然后让它把这个问题写进提示词里，或者写进 harness，有漏的地方就补上。你看我们这里，各种检查都在里面，这些都过了，就可以了。
主持方：
command-line tools 的不好体验，AI 没法弥补，因为你会不断收到报错？
受访者：
AI 很聪明，你跟它说过一次它就不再犯了。比如这次出错了，你让它把规则写进提示词，下次就不会错。我们有各端的 harness，告诉它 iOS 怎么起模拟器、依赖怎么装、怎么测试、怎么构建、怎么操作，写好它就不会错。这对我们来说是团队级的，你不用跟它说什么 DevEco，它不需要了解；你只说「我要起鸿蒙模拟器」，它就会自动调用那一篇。
主持方：

受访者：
对，团队级 harness。另外一层是我们自己设计的很多 harness，比如 API 约定——跟服务端的接口约定，到门禁时跑一遍，检查当前接口和服务端是否对齐。
主持方：
所以 harness 主要是团队层级的，skill 更多是任务层级的？
受访者：
harness 是一个概念，skill 是其中一部分。每次遇到问题就补上，后面补齐了，就不再踩了。

七、三端开发差异与跨平台方案

主持方：
你涉及 iOS、鸿蒙、安卓的开发，几个开发体验比下来差异大的地方在哪？
受访者：
现在做需求时差异都不大，没什么区别，AI 帮你抹掉了。以前用 Flutter 是为了提升效率，但牺牲一部分体验；现在有了 AI，不需要用这个提效，AI 效率就很高了。在提示词里约定好，它就能把功能做成。UI 可能没有 Flutter 那么完全一致，但功能大体一致；多花点时间逐渐走查，UI 也能大体一致。而且原生能紧跟系统特性，Flutter 跟不上，比如液态玻璃这种按钮效果就做不了。iOS 原生是有的。

安卓的问题是国内厂商多、版本特别碎，可以默认它没什么体验。用户系统定制严重、版本碎片化，商店也各不相同，只能靠各家厂商 OS 的努力，各家也没什么新特性。苹果这两年也没什么新特性，AI 也一直没拿出来。〔受访者对 Apple Intelligence 在国内未上线的吐槽，略〕说实话，Siri 还不如小艺。

受访者：
Xcode〔存疑：转写为“他 SO 的”〕里集成了一个它们自己写的 agent，可以调 Claude〔Proco〕的 API，但很难用。界面做得很酷炫，代码会飘起来，但没什么用，情绪价值比较多；模型不行都是白扯。它自己写了一整套 harness，如果你装了 Claude Code 里的 skill，它就跑不起来，换一下技能也装不了。我希望它别改我这个 harness，原生起一个 Claude Code 就行，它自己写不如原生。
受访者：
所以未来 IDE 肯定没什么用了。
主持方：
完全没想到你们这么大的代码量也完全不打开 IDE。
受访者：
我们组、隔壁组的同事基本也都不怎么开。

九、工程管理：Bazel 取代 IDE 工程文件

主持方：
你们也完全不需要看工程目录、README 吗？

主持方：

三项研究目标

① 鸿蒙与通用开发的差异
  • 受访者无职业多端工程经验（安卓项目刚起步），其鸿蒙差异主要体现在平台机制与工具闭环：签名密钥强绑定 DevEco Studio 与 AGC、上架审核规则（版本降级 6.2→6.1、图标一致性、重名驳回）对个人开发者门槛高。
  • 多端适配（手机 / 平板 / 鸿蒙 PC）缺乏轻量验证手段，无真机即无法测。
  • 上架附带外部成本（自购华为云服务器与域名放官网与文档）。
② 给 AI 的输入
  • 纯自然语言 + 强领域约束：不画草图、不写正式 PRD，核心输入是领域规格（华为具体路由器／交换机／防火墙型号、全仓颉优先、适配 4G/8G 低配电脑、API/系统版本 6.1.0）。
  • 先用 DeepSeek 批量查产品型号，再人工筛选后喂给码道；提示词经多轮修改并单独存文档留档。
  • 排错输入高度依赖截图，因华为工具内部分内容无法直接复制给外部 AI。
③ Spec 与验收
  • 拒绝用复杂脚手架或 skill 限制 AI（「能把活干好就行」），但对项目介绍与技术栈架构文档做强审查，偏离即自然语言纠偏。
  • 从 NetLab（自由对话式 vibe coding）到第二个项目（智慧农业），开始自发采用「按文档一步步推进」的规范开发。
  • 验收靠「编译报错 + 真机点跑」；暴露了 AI 在关键打包环节「声称完成实则不可用」的信任缺口。
产品反馈（DevEco 相关）
  • CodeGenie → DevEco Code：早期因响应慢弃用 CodeGenie；新版 Code 入口移到左侧后「看到但不知道怎么用」，缺乏升级引导。
  • 工具割裂：希望在 DevEco Studio 内直接诊断与改代码，不再「Studio 报错 → 截图 → 码道分析 → 回 Studio 操作」。
  • 模拟器与截图：低配电脑跑不动模拟器；强烈建议 DevEco 内置模拟器截图工具，解决上架多端截图耗时问题。
  • AGC 联动：认可签名可直连 AGC，希望进一步直连 AGC 运营数据并由 AI 直接分析。
