输入框上方的场景提示：豆包、WorkBuddy 有，Codex、Claude Code 为什么没有

豆包、WorkBuddy 在输入框上方放一排场景按钮，点进去以后还会给参数和示例提示词；Codex、Claude Code 这类编码 Agent 的输入框上方是空的。本页先把「场景提示」拆成三种形态，看九款产品各用了哪种；再从体验角度解释编码工具不放按钮的原因；最后按 DevEco 的几类开发者判断要不要做、做成什么样。

结论

  1. 编码工具不是没有场景提示，而是换了形态。豆包式的「固定场景按钮 + 场景内表单」它们确实不用；但 Claude Code 的灰色示例取自本仓库的 git 历史，Xcode 的 Coding Tools 跟着选中的代码出现，Codex 和 Android Studio 让用户把常用提示词存成编号预设或提示词库。场景提示从「厂商列给所有人看」变成了「从当前上下文生成」或「由用户自己沉淀」。
  2. 分界线是用户来的时候心里有没有任务，跟产品是不是编码工具关系不大。同一家公司，Claude.ai 首页有 Write / Learn / Code 这类入口，Claude Code 没有。打开豆包的人常常还在想「它能帮我干什么」；打开编码 Agent 的人手里已经拿着报错、需求单或 review 意见，再放一排按钮就是多了一步。
  3. 豆包的场景按钮其实是模式切换。写作、图像、视频、PPT 背后是不同的模型、工具和参数（比例、篇幅、模板），不先选模式，系统就不知道该给哪套参数面板。编码 Agent 只有一种能力，用什么工具由模型自己选，按钮帮不上忙，反而让用户多做一次判断。
  4. 两边在往一处靠：推荐跟着上下文走。WorkBuddy 2026 年下半年的更新集中在「意图识别推荐技能」「对话后下一步问题推荐」「闲置能力提醒」；Claude Code 也在回答后推荐下一句。固定的一排按钮正在被看情况出现的推荐取代。
  5. DevEco 不建议照搬常驻的场景按钮，但比 Codex、Claude Code 更需要场景引导。鸿蒙开发里有一批低频、门槛高、步骤固定的任务：签名证书、上架预检、一多适配、Android 迁移、卡片和元服务、冻屏分析。这些任务开发者一年做不了几次，不知道 Agent 能做，也不知道该怎么描述。最大的用户群是学习者和迁移开发者，他们缺的正是「知道该问什么」。建议做成三件事：新会话的空态给几张按工程状态生成的场景卡，问题出现的地方放情境入口，场景再沉淀成可共享的 / 命令。

各产品

豆包

网页 / App · 大众用户
  • 输入框附近常驻一排技能，覆盖写作、图像、视频、编程、深入研究、翻译等。点进去后输入框挂上场景标签，占位符换成这个场景的引导，出现参数选项（如文体、篇幅、图像比例、风格），再给可直接套用的示例。待确认本次没有拿到可引用的官方界面说明，具体按钮名称和参数项需要实机核对。
  • 从体验上看，这一套本质是「先选模式，再填表」：模式决定调用哪个模型和工具，表单把模糊的需求补成可执行的参数。对第一次用的人，它同时承担了功能目录的作用。

WorkBuddy

桌面端 · 办公 Agent
  • 首页有任务推荐和最佳实践案例（可关闭），可以切换场景，切换时保留已输入的内容；「灵感」可以一键做同款。官方更新日志 5.1.1、5.3.13、5.4.1、5.7.3
  • 场景之外还有专家、技能、连接器三套入口，专家链接会自动带入引导语。官方5.4.4
  • 下半年的更新重心明显移向「看情况推荐」：意图识别推荐内置 Skill / Plugin / Connector（5.3.3），插件推荐更主动（5.5.6），对话前的技能推荐（5.7.0），对话后的下一步问题推荐，可换一条、一键填入（5.8.0）。也出现了反向的设计：闲置能力提醒，一键关闭长期没用的技能（5.6.0）。官方
  • 企业版可以自定义欢迎语和推荐问题（5.3.3），行业 Buddy 有自己的首页、专家和技能（5.5.0）。场景列表由谁来定，正在从厂商转给企业管理员。

编码工具为什么不放场景按钮

下面六条是从用户体验角度给的解释。厂商没有公开说明过取舍，以下为根据产品形态和公开资料做的推断推断，每条附上能观察到的现象。

1. 用户进来时已经带着任务

大众助手面对的是「空白页问题」：用户打开了，但不知道能让它干什么，场景按钮就是功能目录。开发者打开编码 Agent，多半是因为手上有一个报错、一张需求单或一条 review 意见，要做什么已经很清楚，缺的是执行。

豆包先看能做什么，再决定做什么
Claude Code先有任务，再打开工具

2. 上下文本身就是最好的提示词

在仓库里，当前文件、选区、报错、git 改动就能说明用户想做什么。所以编码工具把推荐做成从上下文生成的：Claude Code 的示例取自 git 历史，Xcode 的动作跟着选区，Copilot 自动带入当前文件。一排对谁都一样的按钮，信息量比这些低。

固定按钮对所有人一样
情境建议只对这个工程、这一刻成立

3. 只有一种能力，没有模式要切

豆包的写作、图像、视频、PPT 背后是不同的模型、工具和参数面板，按钮其实是在切模式。编码 Agent 读文件、跑命令、改代码、跑测试，工具由模型自己挑，用户不需要事先声明「我要做测试」。硬加一层模式，等于让用户替模型做一次路由判断。

场景 = 模式 + 表单选错模式结果就错
一个输入框模型自己选工具

4. 编码任务是长尾

写作和图像的需求可以归成十来类；编码任务和项目、语言、框架强相关，六个固定按钮覆盖不了，覆盖到的又往往是最简单、最不需要按钮的任务（「解释这段代码」）。按钮对新手有用，对每天用的人是噪音。侧栏宽度有限，常驻一排按钮还会挤占对话区。

大众场景十来类覆盖大多数需求
编码场景每个项目都不一样

5. 专家习惯用键盘召唤，自己定义

开发者熟悉命令行和快捷键，愿意为高频流程写一条自定义命令。所以编码工具把「场景」做成 / 命令、Skills、预设和提示词库：由用户或团队定义，打字召唤，能放进仓库共享。场景其实一直存在，只是换成了可编辑的文字。

厂商定义点按钮
用户定义/ 命令、预设、提示词库

6. 衡量目标不同

大众助手要靠场景按钮把用户导向新功能、提高功能渗透和留存，WorkBuddy 更新日志里大量是首页推荐、技能推荐、闲置提醒，都是这一类运营动作。编码工具看的是任务做没做成、改动有没有被接受，界面越少打扰越好。

大众助手功能发现、渗透、留存
编码 Agent任务完成率、改动接受率
反例能说明分界线在哪：同为 Anthropic，Claude.ai 有场景入口，Claude Code 没有；面向非开发者的「一句话做网页」类产品（v0、Lovable、Bolt 等）普遍在首页放模板和示例推断。所以决定要不要放按钮的，是用户对任务有多确定、对工具有多熟，不是产品写不写代码。

两边在往一处靠

  • 大众侧在减少固定按钮、增加情境推荐：WorkBuddy 从首页任务推荐，走到意图识别推荐技能（2026-07）、对话前技能推荐（2026-09）、对话后下一步推荐（2026-10），同时加了闲置能力提醒。场景从常驻列表变成「需要时才出现」。
  • 编码侧在补「下一步」：Claude Code 在回答后推荐下一句；Codex 把常用提示词做成编号预设。
  • 场景定义权在下放：WorkBuddy 企业版自定义推荐问题，Android Studio 项目级提示词库，Claude Code 和 Copilot 的 Skill、命令都能随仓库共享。由团队来定义「我们这里常做的事」，比厂商猜更准。

DevEco 的用户要什么

按《DevEco 生态位与体验舆情》§06 的人群拆分，四类和 Agent 输入框关系最大。DevEco 和 Codex、Claude Code 最大的不同在于：鸿蒙有一批「平台特有、低频、门槛高、步骤固定」的任务。开发者不常做，不知道 Agent 能不能做，也说不清该怎么描述。场景引导的价值主要在这些任务上，写日常业务代码时用处不大。

人群来的时候心里有没有任务最可能卡在哪适合的引导形态
学习者 / 转行者数百万人次 / 年常常没有。跟着教程走，不知道 Agent 能做什么不会描述需求；「缺学习资源 / 文档」是鸿蒙开发者第二大顾虑（36.4%）A：空态场景卡 + 进入后的示例；回答后的下一步推荐
跨平台 / Android 迁移开发者存量 App 迁移的主力有，但用的是 Android / iOS 的说法知道要做什么，不知道鸿蒙里叫什么、怎么做：权限、生命周期、一多断点、签名A 的第二层：迁移场景里选源模块、目标形态；B：检测到 Android 工程时出现迁移入口
企业团队承载头部应用与大部分使用时长有，而且团队内高度一致CI / 自动化、规范检查，同一套话每个人都要写一遍C：项目级命令和 Skill，随工程提交共享；管理员可定制推荐
独立开发者舆情最响的一群有，集中在上架前后审核被打回、证书过期、权限申请说明B：在构建失败、签名报错、预检结果旁放「让 Agent 处理」

另一个缺口是能力本身没人知道。DevEco Code 在 OpenCode 之上加了 build_project、start_app、hdc_log、verify_ui、check_ets_files、arkts_knowledge_search 等鸿蒙工具社区，用户不知道它能装机运行、读设备日志、校验界面，就不会这样提问。场景卡能顺带把这些能力讲清楚。

对 DevEco 的建议

不照搬豆包那排常驻按钮：大多数时候用户是带着任务来的，按钮只会占地方。在三个时机给引导：新会话还没输入时、问题刚发生时、一轮回答结束时。

✕ 构建失败：hvigor 签名校验未通过让 Agent 处理

问题发生处的入口：构建输出、Profiler、冻屏报告、预览器旁

  1. 空态场景卡按工程状态生成，最多四张。来源是工程类型、最近一次构建结果、签名和断点配置、日志里有没有冻屏等可检测的状态，而不是厂商写死的列表。没有可用信号时，给新手向的三张（解释这个工程、生成一个页面、跑到模拟器上）。依据：Claude Code 从 git 历史取示例，Xcode 跟着选区。
  2. 场景卡就是 / 命令的可视化入口。点卡片等于在输入框里填好 /命令 和参数，用户能看到、能改，下次可以直接打字。场景和命令是同一套东西，不维护两份。依据：Codex 预设、Copilot 提示词文件。
  3. 进入场景后给槽位，并告诉用户会用到哪些能力。迁移选模块和目标设备，一多选断点，上架预检选签名配置。槽位取代长示例句；列出会调用的鸿蒙工具，让人知道它能装机、能看日志。依据：豆包第二层的参数选项、Android Studio 的 $SELECTION 变量。
  4. 情境入口放在问题发生的地方。构建失败、签名报错、冻屏报告、Profiler 卡顿帧、预览器断点溢出旁边放「让 Agent 处理」，点击后带着现场信息进对话。这比在输入框上方放「修复报错」按钮更准，开发者也不用自己复制日志。
  5. 回答后推荐下一步，接受方式要看得见。一条，可换，旁边标出 Tab。依据：Claude Code 灰字推荐和用户不会接受的反馈（#76591）、WorkBuddy 5.8.0。
  6. 团队可以沉淀自己的场景。项目级命令和 Skill 存在工程目录里随版本库共享，企业团队把「上架前检查」「埋点规范检查」写成一条命令，所有人的空态里都会出现。依据：Android Studio 项目级提示词库、WorkBuddy 企业自定义推荐问题。
  7. 会收起，可关闭。空态卡在有对话后消失；用户关掉后记住选择；一个场景用过几次后改成只显示命令名。依据：WorkBuddy 首页案例的关闭按钮和闲置能力提醒。
输入框本身的九个状态见 DevEco 智能 · 视觉与交互 → 输入框；本页建议的空态卡和槽位输入落地时，需要和那一章的状态机对齐。

待验证

  • 豆包、CodeGenie 的实机界面：豆包技能的名称、第二层参数项，CodeGenie 侧栏空态目前有什么，都需要实机截图核对。
  • 空白输入的比例：在 DevEco Code 和 CodeGenie 里统计新会话第一条消息的长度和类型，以及首条消息前停留的时长。停留长、首条短的比例高，说明空态引导有需求。
  • 低频任务的求助量：签名证书、上架预检、迁移、一多适配在论坛和工单中的占比，用来决定首批场景卡做哪几张。
  • A / B：空态场景卡对学习者和迁移开发者的首轮任务完成率是否有提升，对熟练用户的发送速度是否有影响。
